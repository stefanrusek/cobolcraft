## 1. How to read this document

- Entity ids are the registration order of `EntityTypes.<clinit>` (00-based; 04 states that static-registry ids are assigned in registration order). The id column of the index is therefore "(inferred)" from that rule, but the order itself was read.
- Sizes are width x height in blocks from the `EntityType` builder. Eye height and attachment offsets are given only where an implementation needs them. Where the builder gives no eye height, the default eye height is `0.85 * height`.
- "Tick" is 1/20 s. "Difficulty id" is Peaceful 0, Easy 1, Normal 2, Hard 3.
- Attribute defaults used when a class does not set a value (read from `Attributes`): max health 20, movement speed 0.7 (only meaningful when the class sets its own), attack damage 2, follow range 32 (the `Mob` base sets 16), step height 0.6, armor 0, knockback resistance 0, explosion knockback resistance 0. Every `Monster` adds `attack_damage`; every `Mob` sets follow range 16. A class's "Attributes" row below lists only what it sets on top of that.
- Priority numbers are the numbers passed to the goal selector (lower number is higher priority). "Goal" and "Target" rows give the class and constructor parameters; their behaviour is in 18 framework: goal selector and shared goal classes unless described here.
- `Monster` base: experience reward 5, sound category hostile, and `aiStep` accumulates "no action time" by 2 per tick when the light-dependent brightness at the mob is above 0.5 (18 framework: despawning).

## 3. Shared tables

### 3.1 Damage scaling by difficulty (attack damage against players)

A mob melee or projectile hit whose damage source "scales with difficulty" (`DamageSource.scalesWithDifficulty`) against a player (`Player.hurtServer`) is changed by difficulty before armor: Peaceful 0, Easy `min(d / 2 + 1, d)`, Normal `d`, Hard `d * 3 / 2`, where `d` is the incoming damage. Attack damage attributes below are the values `d` starts from; they do not vary by difficulty by themselves. Armor, enchantments and absorption are in 18 framework: damage.

### 3.2 Effective (local) difficulty, `DifficultyInstance`

Inputs: difficulty id, world game time `T`, chunk inhabited time `I`, moon brightness `M` (0 to 1). Peaceful gives 0. Otherwise:

1. `a = clamp((T - 72000) / 1440000, 0, 1) * 0.25`.
2. `base = 0.75 + a`.
3. `b = clamp(I / 3600000, 0, 1) * (1 if Hard else 0.75)`.
4. `b = b + clamp(M * 0.25, 0, a)`.
5. If Easy, `b = b * 0.5`.
6. Effective difficulty = difficulty id * (base + b).

"Special multiplier": 0 when effective difficulty < 2, 1 when > 4, otherwise `(eff - 2) / 2`. It scales pickup-loot, armor, enchantment, slime-size, and Hard reinforcement and spider-effect chances below. `isHarderThan(x)` means effective difficulty > x.

### 3.3 Brightness and "dark enough to spawn"

- Light-dependent brightness `B(l)` at a position with raw light `l` (0 to 15; sky light already reduced by the current sky-darkness): `f = l / 15`, `v = f / (4 - 3 f)`, result = `v + ambient * (1 - v)` where `ambient` is the dimension's ambient light (0 in the Overworld, so `B = v`; the lerp argument order is inferred). `B > 0.5` is true exactly for `l >= 13`.
- Monster spawn dark check (`Monster.isDarkEnoughToSpawn`), used by `checkMonsterSpawnRules`: fail if sky light at the position > a fresh `nextInt(32)`; fail if the dimension's block-light limit is below 15 and block light exceeds it (Overworld limit 0, so any block light fails); then take the raw brightness (a flat 10 during a thunderstorm in place of the real sky-dependent value) and pass if it is `<=` one sample from the dimension's spawn-light distribution (Overworld: uniform integer 0 to 7 inclusive). `checkMonsterSpawnRules` also requires the standable-block test (3.4) and skips the light test for spawn reasons that "ignore light requirements" (the reason set was not read here; 18 framework: spawn reasons).
- `checkSurfaceMonstersSpawnRules` (husk, parched, camel husk) additionally needs sky access unless the reason is a spawner. `checkAnyLightMonsterSpawnRules` (silverfish, endermite, pillager) has no light test beyond the standable-block test.

### 3.4 Standable-block test (`Mob.checkMobSpawnRules`)

Passes for spawner reasons; otherwise the block below the position must allow spawning on it (`BlockState.isValidSpawn`, 18 framework: spawn placement). Spawn placement type: all Overworld ground mobs here are `ON_GROUND`; Drowned `IN_WATER`; Evoker, Illusioner, Phantom, Vex, Vindicator, Warden `NO_RESTRICTIONS`; heightmap `MOTION_BLOCKING_NO_LEAVES` for all.

### 3.5 Daylight burning (tag `burn_in_daylight`)

Tag members: skeleton, stray, wither skeleton, bogged, zombie, zombie horse, zombie villager, drowned, zombie nautilus, phantom. Husk and parched are not in the tag (Husk also overrides sun sensitivity to false). `Mob.aiStep` calls the burn routine for tagged types every tick:

1. The environment attribute `gameplay/monsters_burn` at the mob's position must be true. In the Overworld this is the `day` timeline track: false from tick 12542 of the 24000-tick day cycle, true from 23460 (so true during [23460, 24000) and [0, 12542) of the day clock).
2. `B` at the block of the mob's eye position must exceed 0.5 (so light >= 13).
3. A random draw `nextFloat() * 30 < (B - 0.4) * 2` must succeed (per-tick probability `(B - 0.4) / 15`; 0.04 at full light).
4. The mob must not be in water or rain or in powder snow (also not "was in powder snow"), and the sky must be visible from the block at its position (`canSeeSky`).
5. If the head slot is empty: ignite for 8 seconds. If the head item is damageable: damage it by `nextInt(2)` (0 or 1) durability and do not ignite. Any other non-empty head item: nothing happens.

### 3.6 Equipment population (`Mob.populateDefaultEquipmentSlots`, used by zombies, skeletons and others via `Monster`)

1. With probability `0.15 * specialMultiplier`: pick tier `t = nextInt(3)` (0 to 2), then make 3 attempts that each add 1 to `t` with probability 0.1087.
2. Slot order is head, chest, legs, feet. The chance `p` to stop after the first slot is 0.1 on Hard and 0.25 otherwise: before each slot except the first, draw a float and stop if it is below `p`.
3. For each slot whose current item is empty: tier 0 leather, 1 copper, 2 golden, 3 chainmail, 4 iron, 5 diamond (a tier above 5 gives nothing).

After that `populateDefaultEquipmentEnchantments`: the main-hand weapon is enchanted with probability `0.25 * specialMultiplier`, each armor slot with `0.5 * specialMultiplier`, using the enchantment provider `minecraft:mob_spawn_equipment` ("by cost with difficulty": enchantments from tag `on_mob_spawn_equipment`, min cost 5, max cost span 17; selection mechanics 18 framework: enchanting helper).

Pickup loot: `finalizeSpawn` sets "can pick up loot" with probability `0.55 * specialMultiplier` (zombies, skeletons, illagers' own rules differ below). `Mob.finalizeSpawn` also adds a follow-range modifier of `triangle(0, 0.11485)` (multiplied-base) once, and with probability 0.05 makes the mob left-handed.

Equipment drop chance per slot defaults to 0.085 (`DropChances`); a stored chance above 1.0 means "guaranteed, preserved" and 2.0 is used for guaranteed drops (pumpkin helmets are set to 0). Death-drop handling is in 18 framework: loot, drops and death.

Experience: `Mob.getBaseExperienceReward` returns the type's reward; when it is above 0 it adds `1 + nextInt(3)` for each armor and hand-held slot item whose drop chance is not above 1.0. Rewards: Monster default 5; Slime and Magma Cube = size; Ravager 20; Evoker 10; Breeze 10; Phantom 5; Warden 5; Vex 3; Endermite 3; Illusioner 5; Creaking 0; baby zombie (all zombie variants) multiplies the reward by 2.5 (truncated); Pillager, Vindicator, Witch, Creeper, Skeleton family, Spider family, Enderman, Silverfish, Giant: 5 (default).

### 3.7 Common entity metadata base indices

Every mob here inherits Entity (indices 0 to 7), LivingEntity (8 to 14) and Mob (15: one byte, the mob flags; its bit meanings are not re-read here, see 18 framework: entity metadata) fields; a class's own fields start at index 16 in static-initializer order, parent first. Counts read: Entity 8 fields, LivingEntity 7, Mob 1, PathfinderMob 0, Monster 0.

### 3.8 Conversion tracker (zombie to drowned, skeleton to stray)

A "conversion tracker" runs on the server each tick while the mob is alive, not no-AI, and the mob's *afflicted* condition holds: it counts afflicted ticks up; when the count reaches the "affliction time" it switches to converting (the synched converting flag turns true) and counts down the conversion time; when the countdown goes below 0 the mob is replaced by the target type (all equipment kept per `convertTo`). If the afflicted condition stops being true at any time, both counters are reset (affliction -1) and the converting flag clears. Parameters: zombie in water (eyes in water): affliction 600, conversion 300; skeleton in powder snow: affliction 140, conversion 300. Save fields: `InWaterTime`/`DrownedConversionTime`, `FreezingTime`/`StrayConversionTime`.

### 3.9 Loot tables (all read from `data/minecraft/loot_table/entities/`)

Tables are in each mob's section. Notation: `U(a..b)` uniform integer; "looting +U(0..1)/level" means `enchanted_count_increase` of uniform 0 to 1 per level. "killed by player" is the `killed_by_player` condition. Mechanics (rolls, conditions, looting math) are 18 framework: loot.

### 3.10 Status events and level events cited

Broadcast entity events (play packet Entity Event, 05a) read from these mobs: 4 attack animation (Ravager, Warden, Creaking; the Evoker fangs entity uses 4 for its bite), 15 witch particles, 16 zombie-villager cure started (sound), 39 Ravager stunned, 61 Warden tendril clicks, 62 Warden sonic-boom charge, 69 Ravager roar. Other events these classes handle are listed in the mob's section when read. Level events (World Event packet, 05b) cited: 1019/1021 door breaking, 1026 zombie converts villager, 1027 villager cured, 1039 phantom swoop, 1040/1041 zombie and husk conversion sounds, 2001 block break particles, 2018 enderman teleport, 3007 shrieker.

**Targets**: 1 hurt-by (alert-others list: `ZombifiedPiglin`; 18 framework); 2 nearest attackable `Player` (must see); 3 nearest `AbstractVillager` (need not see); 3 nearest `IronGolem` (must see); 5 nearest `Turtle` within 10 ticks interval, must see, need not reach, selector "baby turtle on land".

Melee goal numbers (shared `MeleeAttackGoal`, 18 framework): attack interval 20 ticks; re-check spacing 20 game ticks; path recalculation delay base 4 + `nextInt(7)` (+10 if target farther than 32 blocks, +5 if farther than 16, +15 if the path fails); the zombie goal sets "aggressive" while the attack timer has run for 5 ticks and is within half the interval of the next attack.

**Attack**: `doHurtTarget` = base melee with attack damage 3.0 (3.1 scaling). If the hit lands, the zombie's main hand is empty and the zombie is on fire, then with probability `effectiveDifficulty * 0.3` the target is set on fire for `2 * floor(effectiveDifficulty)` seconds.

**Door breaking** (`BreakDoorGoal`): canUse when the mob-griefing rule is true, the difficulty predicate holds and the door is closed; each tick, with 1/20 chance, play level event 1019 and swing; the break progress goes up 1 per tick; the visible stage is `floor(progress / breakTime * 10)` and is sent as block destruction progress; when progress reaches the break time (minimum 240 ticks, `max(240, ...)`) and the predicate still holds the door block is removed (level events 1021 and 2001 with the block id). `Zombie.setCanBreakDoors(true)` also enables the navigation's "can open doors". Vindicators use a 6-tick-interval variant (13.1).

**Spawn setup** (`finalizeSpawn`, 3.6 applies):

1. (not for spawn reason CONVERSION) can-pick-up-loot with probability `0.55 * specialMultiplier`.
2. If no group data: baby with probability 0.05 (and jockeys allowed). If the zombie is baby and jockeys are allowed: with probability 0.05 look for an un-ridden chicken within the box inflated by (5, 3, 5) around the zombie; if one exists, mark it a chicken jockey and ride it. Otherwise (the first 0.05 test failed) with probability 0.05 create a chicken (spawn reason JOCKEY), place it at the zombie, finalize it, mark it a jockey, ride it, add it to the level.
3. Baby zombies get the movement-speed modifier id `baby`: +0.5, multiplied-base.
4. "Can break doors" is set with probability `0.1 * specialMultiplier` (only for entities whose navigation can navigate ground).
5. Unless the reason is CONVERSION: populate default equipment (3.6), then the zombie weapon: with probability 0.05 on Hard and 0.01 otherwise, draw `nextInt(6)`: 0 iron sword, 1 iron spear, otherwise iron shovel, in the main hand; then enchant (3.6).
6. If the head is empty and the date is Halloween (client date check) and `nextFloat < 0.25`: head becomes a carved pumpkin (jack-o'-lantern with probability 0.1), with drop chance 0. (Date source: the world clock's `SpecialDates.isHalloween`, not traced.)
7. `handleAttributes(specialMultiplier, reason)`:
   - Reinforcement chance base value = `nextDouble() * 0.1`.
   - Knockback resistance + `nextDouble() * 0.05` (add-value modifier `random_spawn_bonus`).
   - `x = nextDouble() * 1.5 * specialMultiplier`; if `x > 1`, follow range gets a multiplied-total modifier of `x` (`zombie_random_spawn_bonus`).
   - With probability `0.05 * specialMultiplier` the zombie is a "leader": reinforcement chance + `0.5 + nextDouble() * 0.25` (add-value, `leader_zombie_bonus`), max health multiplied-total modifier `nextDouble() * 3 + 1` (`leader_zombie_bonus`), health set to the new max unless the reason is CONVERSION, LOAD or DIMENSION_TRAVEL, and can-break-doors forced true.

**Reinforcements** (`hurtServer`, only after a successful base hurt): requires world difficulty Hard, a living target (the zombie's target, or the attacker if the zombie has none), `nextFloat < reinforcements chance attribute value`, and `ServerLevel.isSpawningMonsters` (game rules `spawn_mobs` and `spawn_monsters`). Then up to 50 attempts: pick a position offset from the zombie on each axis by `nextInt(7..40) * nextInt(-1..1)` (so 0 is possible); a try succeeds when all hold: the spawn position passes the entity type's placement check, `checkSpawnRules` with reason REINFORCEMENT passes, no living player within 7 blocks, no entity or block collision, and not in liquid unless the type allows liquids. The new zombie of the *same type* (`getType`) has the attacker as target, is finalized with reason REINFORCEMENT and added; the caller's reinforcement chance is lowered by 0.05 (modifier `reinforcement_caller_charge`, accumulating) and the callee gets `reinforcement_callee_charge` -0.05.

**Kill a villager** (`killedEntity`): when world difficulty is Normal or Hard and the victim is a `Villager`: on Hard always, on Normal only if `nextBoolean()`: the villager is converted to a `ZombieVillager` (4.2) with villager data, gossips, offers and xp copied (level event 1026 unless silent) and the villager does not drop. On Easy the villager dies normally.

**Pickup**: zombies never pick up glow ink sacs; babies riding something do not hold eggs. They pick up loot when allowed by 3.6 and the mob-griefing rule.

**Drops** (`entities/zombie`): rotten flesh `U(0..2)` + looting `U(0..1)`/level; red mushroom `U(0..1)` + looting when riding a `zombie_horse`; if killed by player, one of {iron ingot, carrot, potato (smelted to baked potato if the zombie was on fire or the killer's main-hand item has an enchantment from `#smelts_loot`)} with chance 0.025 (looting: 0.035 + 0.01 per level above the first); if killed by player and the zombie is a baby riding a chicken, one `music_disc_lava_chicken`. XP 5, x2.5 truncated for babies (plus equipment bonus 3.6).

### 4.2 Zombie villager

### 6.2 Explosion algorithm (`ServerExplosion`)

Input: center, power `R` (float), source entity, interaction (NONE, KEEP, DESTROY, DESTROY_WITH_DECAY, TRIGGER_BLOCK), fire flag. `ServerLevel.explode` maps the interaction `MOB` to: when the mob-griefing rule is true, block destruction, with loot decay (each drop survives with probability `1/R`) when the `mob_explosion_drop_decay` rule is true and without it otherwise (`getDestroyType`: rule true gives DESTROY_WITH_DECAY, false gives DESTROY); when mob griefing is false, KEEP (damage and knockback only, no block changes). NONE maps to KEEP. `BLOCK` uses the `block_explosion_drop_decay` rule; `TNT` uses `tnt_explosion_drop_decay`; a trigger interaction (wind charges) is TRIGGER_BLOCK (all rules per 18 framework: game rules). The game event `explode` is emitted first.

**Block selection** (`calculateExplodedPositions`): for each of the 16 x 16 x 16 grid cells `(i, j, k)` that lie on the surface of the cube (at least one of i, j, k is 0 or 15; loops in order i outer, j middle, k inner), form the direction `(i/15*2 - 1, j/15*2 - 1, k/15*2 - 1)` and normalize it. The ray starts at the center with strength `R * (0.7 + nextFloat() * 0.6)` (one random float per ray, taken at ray start). While strength > 0: take the block at the current position (floored); if it is air and has no fluid, nothing; otherwise the blast resistance of the block or fluid (the larger of block resistance and fluid resistance; for an entity-based calculator it is further adjusted by the entity) `r` reduces the strength by `(r + 0.3) * 0.3`; if the strength is still > 0 and the block may explode (`shouldBlockExplode`, always true for the default calculator), add the block position to the set. Then advance the position by `direction * 0.3` and subtract 0.225 (read as `0.22500001f`) from the strength. A ray ends if the position leaves the world bounds.

**Entity damage** (`hurtEntities`): nothing happens when `R < 0.00001`. The damage radius is `2R`: entities whose bounding boxes intersect the box from `center - (2R + 1)` to `center + (2R + 1)` (each corner floored/ceiled to block coordinates) are considered (`getEntities(source, box)` excludes the explosion's source entity, so a creeper never damages itself), except those that ignore explosions. For each: `dist = distance(entity position, center) / (2R)` (entity feet position; for a primed TNT its position); skip if `dist > 1`. The *exposure direction* is `normalize(eyePosition(or position for TNT) - center)`. `seen` (fraction of rays that reach the entity, below) is computed when the calculator allows damage to the entity (always true by default) or the knockback multiplier is nonzero, and is 0 otherwise. If damage is allowed and teams allow it, the entity is hurt with damage = `((s*s + s) / 2 * 7 * (2R) + 1)` with `s = (1 - dist) * seen`, delivered as the explosion damage source (damage after 3.1 scaling for players). Knockback strength `= (1 - dist) * seen * knockbackMultiplier * (1 - explosionKnockbackResistance)` (multiplier 1 by default, resistance attribute for living entities, 0 otherwise); the entity's velocity is increased by `direction * strength` (`pushFromExplosion`). Each entity then also receives `onExplosionHit(source)` (a no-op with the default calculator). Each hit player that is not a spectator and not (creative and flying) is recorded with its knockback vector so that the client applies it (Explode packet 05a 0x24, sent to players within 64 blocks of the center (distance squared < 4096)). Redirectable projectiles (tag `redirectable_projectile`) that are `Projectile`s get the explosion's damage-source entity as owner and are never added to the hit-player map.

**Seen fraction** (`getSeenPercent(center, entity)`): with the entity's bounding box extents `ex, ey, ez` (max minus min on each axis) the per-axis steps are `sx = 1 / (2 * ex + 1)`, `sy = 1 / (2 * ey + 1)`, `sz = 1 / (2 * ez + 1)`; the horizontal offsets are `ox = (1 - floor(1 / sx) * sx) / 2` and `oz = (1 - floor(1 / sz) * sz) / 2` (there is no vertical offset). The result is 0 when any step is negative. Otherwise sample parameters `tx`, `ty`, `tz` each run from 0 to 1 inclusive in increments of their step (x outermost, then y, then z innermost); each sample point is `(lerp(tx, minX, maxX) + ox, lerp(ty, minY, maxY), lerp(tz, minZ, maxZ) + oz)`; a ray is cast from the sample point to the explosion center with the collider block context and no fluids; a sample counts as unobstructed when the ray result is a miss. The result is `unobstructed samples / total samples` as a float.

**After blocks** (`interactWithBlocks`, when the interaction is not NONE/KEEP): the positions are shuffled; each block's `onExplosionHit` runs: air is skipped; for TRIGGER_BLOCK interactions triggerable blocks react (not traced); for DESTROY(_WITH_DECAY): the block's loot table is rolled with the explosion origin at the block center, an empty-hand tool, the block entity and the source entity, plus the explosion radius parameter when decay applies (the `explosion_decay` condition passes with probability `1 / R`); the block is replaced by air (neighbors updated) and `wasExploded` runs; dropped stacks are merged by `addOrAppendStack` and spawned. Fire (when the fire flag is set, not for creepers): about one in three of the exploded positions that are now air above a solid-render block becomes fire.

**Charged creeper**: power 6 instead of 3 changes `2R` from 6 to 12, so it reaches farther (worked example 20.1).

### 10.1 Cube-mob move control, jump power and the "aggressive" flag (resolved; classes `AbstractCubeMob$CubeMobMoveControl`, `$CubeMobAttackGoal`, `$CubeMobRandomDirectionGoal`, `Mob.setSpeed`, `LivingEntity.getJumpPower`)

All of this applies to Slime and Magma Cube (the Sulfur Cube's move control `SulfurCube$SulfurCubeMobMoveControl` runs the base cube-mob tick below only while the cube's BODY equipment slot is empty (`hasBodyItem()` false) and does nothing at all while it holds a body item; its other rules are in 18.2 and 44-5 §4). The move control has three fields: `yRot` (the wanted yaw in degrees; the constructor initialises it to `180.0 * mob.yRot / 3.1415927` computed in float arithmetic, as read; it is 0 for a mob created with yaw 0, and until the first `setDirection` the cube turns towards this value because step 1 below runs every tick), `jumpDelay` (starts at **0**) and `isAggressive` (false).

**What sets the fields.**

| Caller | Call | Effect |
|---|---|---|
| Attack goal (`CubeMobAttackGoal`, every tick, `requiresUpdateEveryTick`): after `lookAt(target, 10, 10)` | `setDirection(mob.yRot, mob.canDealDamage())` | `yRot` = the mob's own current yaw (the look-at turns it towards the target at most 10 degrees per tick), **`isAggressive` = `canDealDamage()`**: Slime `size > 1` (not tiny) and effective AI; Magma Cube effective AI only (10 above) |
| Random-direction goal (when it fires: every `40 + nextInt(60)` ticks, no target, on the ground or in liquid or levitating) | `setDirection(nextInt(360) as float, false)` | `yRot` = a random whole number of degrees, `isAggressive` = false |
| Keep-on-jumping goal (any tick it runs, not a passenger) | `setWantedMovement(1.0)` | `speedModifier` 1.0, operation MOVE_TO |
| Float goal (in liquid, every tick) | `setWantedMovement(1.2)` plus a jump request with probability 0.8 | `speedModifier` 1.2 |
| Attack goal's `setWantedMovement` | none: the attack goal only turns the mob; the movement comes from the keep-on-jumping goal | |

So **"aggressive" is true exactly while a cube mob that is able to hurt (Slime of size 2 or more, any Magma Cube) is running its attack goal, and false after a random-direction draw**. It is not a stored entity field and it is not saved. The flag keeps whatever value was written last; the attack goal writes it every tick it runs, so while hunting it tracks `canDealDamage()`.

**`CubeMobMoveControl.tick`, in this order every server tick (the control is ticked from `Mob.serverAiStep`, after the goals):**
1. `mob.yRot = rotlerp(mob.yRot, yRot, 90)` (turn towards the wanted yaw by at most 90 degrees); head yaw and body yaw are set equal to `mob.yRot`.
2. If the operation is not MOVE_TO: `zza` (forward input) is set to 0 and the tick ends (no jump countdown, `jumpDelay` is not touched).
3. The operation is set to WAIT (the goals must request MOVE_TO again on the next tick).
4. If the mob is **on the ground**:
   a. `setSpeed(speedModifier * movementSpeedAttribute)` (as a float). `Mob.setSpeed` also writes the same value to `zza`, so this sets both the speed and the forward input.
   b. `jumpDelay` is decremented by 1; if the new value is **above 0** (a tick between jumps): `xxa = 0`, `zza = 0` and **`setSpeed(0)`** (this overwrites step a: the cube has no forward input and no speed between jumps) and the tick ends.
   c. Otherwise (a jump tick): `jumpDelay = mob.getJumpDelay()` = `10 + nextInt(20)` (one random draw from the mob's own generator, 10 to 29), then, if `isAggressive`, `jumpDelay = jumpDelay / 3` with integer division (3 to 9), then a jump request to the jump control, then the jump sound if `doPlayJumpSound()` (`AbstractCubeMob`: size above 0). Speed and forward input stay at the values of step a for this tick.
5. If the mob is **not on the ground** (in the air or in a fluid): `setSpeed(speedModifier * movementSpeedAttribute)` (speed and forward input = that value; `jumpDelay` is not decremented in the air).

Consequences (derived): the first on-ground tick with MOVE_TO jumps at once (`jumpDelay` starts at 0, so step b yields -1); the interval between jumps is `jumpDelay` ticks, so 10 to 29 ticks for a calm cube and 3 to 9 ticks for an aggressive one (the decrement happens on the jump tick too, so a drawn value `d` gives a jump `d` ticks after the previous jump tick, counted on ground ticks only: ticks spent in the air do not count down). Between jumps the cube does not move horizontally except by momentum and friction.

**Jump velocity** (`AbstractCubeMob.jumpFromGround`): the vertical velocity is **set** to `getJumpPower()` (x and z are kept; there is no sprint boost). `Magma Cube.jumpFromGround` sets it to `getJumpPower() + 0.1 * size`. `getJumpPower()` = `jump_strength` attribute (base **0.42**, stored as 0.41999998688697815, registered range 0 to 32; the Slime and Magma Cube set no override, they use the monster defaults) x `blockJumpFactor` + the Jump Boost bonus `0.1 * (amplifier + 1)` when the effect is present (0 otherwise). `blockJumpFactor` is the `jumpFactor` of the block at the mob's block position, or, when that factor is exactly 1.0, the factor of the block below that affects movement; the default factor is 1.0 and the only block in `Blocks` that sets another is `honey_block` (0.5, together with speed factor 0.4). `getJumpPower()` is computed in float arithmetic (`jump_strength` narrowed to float, times the float factor, plus the float bonus) and the result is widened when stored as the vertical velocity; the Magma Cube adds the float `size * 0.1f`. Worked values: a size-1 slime on stone jumps with vertical velocity 0.42; on honey 0.21; a size-4 magma cube on stone jumps with `0.42 + 0.4 = 0.82`; with Jump Boost I (amplifier 0) a slime gets `0.42 + 0.1 = 0.52`.

**Horizontal motion after the jump** is the ordinary living-entity ground and air travel (44-5 §4.2) driven by `zza = speed = speedModifier * movementSpeedAttribute` (speed attribute `0.2 + 0.1 * size`, 10 above; speedModifier 1.0 normally, 1.2 in liquid, an explicitly requested value otherwise).

### 12.1 Flying travel: what the 0.2 does (resolved; `Phantom.travel`, `LivingEntity.travelFlying`, `LivingEntity.aiStep`, `Entity.moveRelative`, `Entity.getInputVector`)

`Phantom.travel(input)` is the single call `travelFlying(input, 0.2)`; the two-argument `travelFlying(input, a)` forwards to the four-argument form with `(waterSpeed 0.02f, lavaSpeed 0.02f, airSpeed a)` (floats: 0.02f = 0.019999999552965164, 0.2f = 0.20000000298023224), so the phantom's `0.2` is the **air** speed. The four-argument `travelFlying(input, waterSpeed, lavaSpeed, airSpeed)` does exactly this (no block friction, no gravity, no climbing, no levitation handling are in this path):

| Medium of the mob (tested in this order) | `moveRelative` speed | Velocity factor after the move |
|---|---|---|
| in water (`isInWater`) | `waterSpeed` 0.02f | 0.800000011920929 (the float 0.8 widened) |
| else in lava (`isInLava`) | `lavaSpeed` 0.02f | 0.5 |
| else (air) | `airSpeed` 0.2f | 0.9100000262260437 (the float 0.91 widened) |

Steps: (1) `moveRelative(speed, input)` adds `rotate(yaw, input * speed)` to the velocity when the input vector's squared length is at least 1e-7 (the input is first normalised if its squared length exceeds 1; with a smaller squared length the added vector is zero); (2) `move(SELF, velocity)` (normal collision against blocks for the phantom); (3) the velocity is multiplied (all three axes, in double arithmetic) by the factor of the table. The derived numbers below use 0.91 for readability; a bit-exact tick simulation must use 0.9100000262260437.

The input vector is `(xxa, yya, zza)` of the mob. A phantom never sets those fields (its move control writes the velocity directly, step 8 of the move control above, and the goals set no forward input; `Mob.setSpeed` and `Mob.setZza`, the writers of the forward input of mobs, are not called by any phantom class; searched: `Phantom` and all seven nested classes for `setSpeed`, `setZza`, `setXxa`, `setYya` and direct field writes), and `LivingEntity.applyInput` multiplies `xxa` and `zza` by 0.98 each tick, so they stay 0. **So for a phantom the 0.2 has no effect at all and the only forces are the move control's velocity blend and the damping factor**; it is not a friction coefficient (the value 0.2 coincides with the 0.2 blend factor of the move control, step 8, which is a separate constant).

Per-tick order for a phantom in air (the order of `LivingEntity.aiStep`, then `Mob.serverAiStep`): goals and `customServerAiStep` first, then the move control (changes the velocity: `v += (target_v - v) * 0.2`), then `travel` (position `+= v`, then `v *= 0.91`). Derived values (arithmetic on the constants, not separately observed): with a constant wanted velocity vector `T` the steady state before the move is `v* = 0.182 T / (1 - 0.728) = 0.6691 T` and the displacement per tick is `0.8 v* + 0.2 T = 0.7353 T`; for the cruise speed 1.8 of the move control the steady displacement is about 1.3235 blocks per tick, and the velocity left after the damping is about 1.2044 per tick; at the minimum turning speed 0.2 the displacement is about 0.147 blocks per tick. Example (derived, one axis): start at rest with a constant wanted velocity of 1.8 along +x; each tick is `v' = v + 0.2 (1.8 - v)`, displacement `v'`, then `v = 0.91 v'`. Tick 1: `v' = 0.36`, `v = 0.3276`. Tick 2: `v' = 0.6221`, `v = 0.5661`. Tick 3: `v' = 0.8129`, `v = 0.7397`. Tick 4: `v' = 0.9518`, `v = 0.8661`. (In the real move control the wanted vector is re-derived every tick from the move target point and the speed field, so this is the response to a constant vector only.)

#### 13.4.1 Vex flying speed and move control (resolved; `Vex$VexMoveControl`, `Vex.tick`, `LivingEntity.travelInAir`)

The vex has **no flying-speed attribute**: its attributes are only max health 14 and attack damage 4.0 (the movement speed attribute is not read by its code). Its flight is the following, per server tick.

**Order inside the entity tick.** `Vex.tick` sets `noPhysics = true`, runs the superclass tick (which includes the goals, the move control and `travel`, in the order of 12.1: goals, then controls, then travel), then sets `noPhysics = false` and `setNoGravity(true)`, then, only when `hasLimitedLife`, decrements `limitedLifeTicks` (13.4 above). While the vex moves it therefore ignores blocks completely: `Entity.move` with `noPhysics` set adds the movement to the position without collision. The vex constructor sets no no-gravity flag (read: `Vex.<init>` sets only the move control and the experience reward), and the flag is set after the superclass tick of every tick, so during the first tick of a new vex gravity still applies once: the movement of that tick uses the velocity before gravity, then the vertical velocity becomes `(0 - 0.08) * 0.98` = -0.0784 (derived, 44-5 §4.2 step 3 to 4) and carries into the second tick, whose move control and damping act on it; from the second tick on the flag is set.

**`VexMoveControl.tick`** (acts only when the operation is MOVE_TO, set by `setWantedPosition(x, y, z, speedModifier)` from the goals: charge attack 1.0, random move 0.25; nothing clears it except step 2 below):
1. `v = wanted - position` (3D vector from the vex's position, its feet, to the wanted point), `d = |v|`.
2. If `d < boundingBoxSize`, where `boundingBoxSize` is the average of the three edge lengths of the vex's box, `(0.4 + 0.8 + 0.4) / 3 = 0.5333...`: the operation becomes WAIT and the velocity is multiplied by 0.5. Nothing else happens this tick.
3. Otherwise `v * (speedModifier * 0.05 / d)` is added to the velocity, an acceleration of magnitude `0.05 * speedModifier` (blocks per tick per tick) along the line to the wanted point: 0.05 for the charge, 0.0125 for a random move.
4. Orientation: if the vex has **no attack target** (`getTarget()` null): yaw = `-atan2(vx, vz) * 57.295776` using the **velocity just updated**; otherwise yaw = `-atan2(dx, dz) * 57.295776` where `(dx, dz)` is the horizontal vector from the vex to its target (not to the wanted point). Body yaw is set equal to the yaw in both cases; head yaw and pitch are not set here. (`atan2(x, z)` takes its arguments in that order. The arithmetic is, in both branches: `A = (float) Mth.atan2(first, second)` (the double result of the custom approximation of 10 §16.4 narrowed to float; not the library `Math.atan2`, see 44-residual-mob-questions-x1 §11.1 for its bit-exactness and tolerance), then the yaw is `(-A) * 57.295776f` as a float product (`fneg` then `fmul`), written with `setYRot`, and `yBodyRot` is then set to the new `getYRot()`; read in `Vex$VexMoveControl.tick`. Example: velocity `(vx, vz) = (0, 1)` (moving along +z): `atan2(0, 1)` = 0, yaw 0; `(vx, vz) = (1, 0)`: `atan2(1, 0)` is about 1.5708, yaw about -90.)

**Travel** (`LivingEntity.travel`, not overridden by the vex): when the vex is in neither water nor lava it runs `travelInAir`; the vex never writes `xxa`, `yya` or `zza`, so the input is zero; the position moves by the velocity left by the move control (no collision), the effective gravity is 0 (no-gravity), and then the velocity is damped by the air factors of 44-5 §4.2 with the default attribute values (friction modifier and air drag modifier 1): horizontal factor `f * computeModifiedFriction(0.91f, 1)` with `f = 1.0` in the air, which is the float 0.91 widened, **0.9100000262260437**, and vertical factor the float 0.98 widened, **0.9800000190734863** (the vex is not an "omnidirectional air mover": only Bee, Parrot and Sulfur Cube override that, searched over `net/minecraft/world/entity`). The numbers below use 0.91 and 0.98 for readability.
**In a fluid** (`shouldTravelInFluid`: the vex is in a liquid, is affected by fluids and cannot stand on the fluid; the vex overrides none of these) `travelInFluid` replaces `travelInAir`: in water (`isInWater`): `slowdown = getWaterSlowDown()` = the float 0.8 (0.800000011920929; 0.9f when sprinting, which a vex never does); the attribute `water_movement_efficiency` (default 0.0) is first **halved when the entity is not on the ground**, and only when the result is above 0 does it change `slowdown` (blend toward the float 0.54600006) and the move speed (blend toward the entity's speed); the rule "horizontal collision while on a climbable block sets the vertical velocity to 0.2" cannot happen for a vex (no collisions while `noPhysics`); the effect Dolphin's Grace sets `slowdown` to the float 0.96f (it applies only if the vex has that effect); `moveRelative(0.02f, input)` adds nothing (zero input); `move(SELF, velocity)` (no collision, `noPhysics`); then the velocity is multiplied by `(slowdown, 0.800000011920929, slowdown)`, i.e. 0.800000011920929 on all three axes; `getFluidFallingAdjustedMovement` returns the velocity unchanged when the effective gravity is 0 (its first test), as it is for the vex; `jumpOutOfFluid` acts only after a horizontal collision (none while `noPhysics`). In lava: `moveRelative(0.02f, input)` (nothing), `move`, then the velocity is multiplied by 0.5 on all axes, or by `(0.5, 0.800000011920929, 0.5)` when the lava is shallow (fluid height at most the fluid jump threshold, the eye height 0.51875), then the falling adjustment (identity at gravity 0); the extra `-gravity / 4` term is skipped at gravity 0. So in water the vex's displacement is still the velocity left by the move control and the damping is 0.8 instead of 0.91 and 0.98; the steady displacement of the charge in water is `a / 0.2` = 0.25 per axis.

Derived numbers (arithmetic on the constants only): with a constant acceleration `a = 0.05 * speedModifier` along one axis the per-tick sequence is `v' = v + a` (move control), displacement `v'`, then `v = 0.91 v'` (horizontal) or `0.98 v'` (vertical). The steady displacement per tick is `a / 0.09` horizontally and `a / 0.02` vertically: for the charge (`a = 0.05`) 0.5556 blocks per tick horizontally and 2.5 blocks per tick vertically; for a random move (`a = 0.0125`) 0.1389 and 0.625. The vex stops accelerating when `d < 0.5333` and halves its velocity every tick while waiting. Example (horizontal, from rest, charge along +x): tick 1 `v' = 0.05` (displacement 0.05, `v = 0.0455`); tick 2 `v' = 0.0955` (displacement 0.0955, `v = 0.0869`); tick 3 `v' = 0.1369` (displacement 0.1369).

## 14. Raid system and patrols

### 14.1 Patrols (`PatrolSpawner.tick`, Overworld, per server tick)

Requires the `spawn_patrols` game rule. A counter `nextTick` is decremented each call and while above 0 the spawner returns. When it reaches 0 or below it increases by `12000 + nextInt(1200)` ticks. Then: it must be bright outside (`isBrightOutside`, daytime); `nextInt(5) == 0` must pass; at least 1 player must exist; pick one player at random; a spectator ends the attempt; a player within 2 chunks-of-village distance (`isCloseToVillage(pos, 2)`: false when the argument exceeds 6, otherwise true when the POI manager's section distance from the position's section to the nearest village is at most 2 sections; `isVillage(pos)` is the same test with 1) ends the attempt; offsets: `x = (24 + nextInt(24)) * (+1 or -1 by nextBoolean)`, `z` likewise; the position is the player's block moved by `(x, 0, z)`; all chunks within +-10 blocks of that position must be loaded; the environment attribute `can_pillager_patrol_spawn` must be true at the position (in the early game timeline: false for the first 120000 game ticks (100 minutes), true afterwards, "and"-combined; biome `mushroom_fields` sets it false); the member count is `ceil(effectiveDifficulty at the position) + 1`; for each member `i` the y is set to the MOTION_BLOCKING_NO_LEAVES heightmap and `spawnPatrolMember(leader = i == 0)` is tried (stop at the first failure), then x and z are moved by `nextInt(5) - nextInt(5)` each. `spawnPatrolMember` needs `isValidEmptySpawnBlock` for a pillager, `checkPatrollingMonsterSpawnRules` (13.2), creates a pillager (spawn reason PATROL), makes it patrol leader when requested (and calls `findPatrolTarget`), places it, finalizes (reason PATROL) and adds it with passengers.

### 14.2 Raid lifecycle (`Raid`, `Raids`)

State: status ONGOING, VICTORY, LOSS, STOPPED; `started`, `active`, `groupsSpawned` (waves spawned so far), `raidCooldownTicks` (initial 300), `ticksActive`, `postRaidTicks`, `raidOmenLevel` (max 5), `totalHealth`, per-wave raider sets, per-wave leader, heroes-of-the-village set, a boss bar (red, notched 10, name "Raid", with " - Victory"/"Defeat" or "N raiders remaining" when 2 or fewer remain), center position, `waveSpawnPos`.
Number of waves by difficulty: Peaceful 0, Easy 3, Normal 5, Hard 7. A bonus wave exists when `raidOmenLevel > 1` (`hasBonusWave`) and is the wave after the final one.

**Starting**: Bad Omen comes from consuming an ominous bottle (the pillager captain drop): the item's amplifier component (`ominous_bottle_amplifier`, integer 0 to 4, default 0 on the item; the captain drop sets `U(0..4)`) is applied on consumption as Bad Omen for 120000 ticks at that amplifier (flags read as false, false, true: ambient, particles, icon); the bottle itself plays the `ominous_bottle_dispose` sound after consumption. `BadOmenMobEffect.applyEffectTick` (each tick): if the player is a server player, not a spectator, the difficulty is not Peaceful and the player's block is in a village (`isVillage`): if a raid exists at that position and its omen level is already at the maximum (5) nothing happens (the effect stays); otherwise the player gets Raid Omen for 600 ticks, `raidOmenPosition` is stored, and the Bad Omen effect ends (the method returns false). `RaidOmenMobEffect` acts when the effect has exactly 1 tick left: if the entity is a server player, not a spectator, with a stored raid omen position: `Raids.createOrExtendRaid(player, position)`, then the stored position is cleared. `createOrExtendRaid` returns nothing when the player is a spectator, the `raids` game rule is false, or the environment attribute `can_start_raid` is false at the player's position. Otherwise: the point-of-interest manager returns occupied POIs of POI type tag `village` within 64 blocks of the position; the raid center is the average (sum / count) of their block positions, or the position itself when there are none; `getOrCreateRaid(level, center)` returns the raid at that center or a new one; when the raid has not started and is not yet in the manager it is added under a new unique id; when the raid has not started or its omen level is below the maximum, `absorbRaidOmen(player)` runs and the manager is marked dirty. `absorbRaidOmen` returns false when the player has no Raid Omen effect; otherwise `raidOmenLevel = clamp(raidOmenLevel + amplifier + 1, 0, 5)` where `amplifier` is the player's Raid Omen amplifier, and if the first wave has not yet spawned the `raid_trigger` statistic and the raid-omen advancement trigger are awarded to the player.
**Raids.tick** (each tick): each raid is ticked unless the `raids` game rule is false (then it is stopped and removed when stopped); the manager is marked dirty every 200 ticks.

**Raid.tick** (while status is ONGOING; the checks run in this order): the raid is "active" while its center chunk is loaded; Peaceful stops it (status STOPPED) and ends the tick; an inactive raid does nothing further (the boss bar visibility follows `active`). If the center is not a village: it is moved by `moveRaidCenterToNearbyVillageSection` (the nearest, by squared distance to the old center, village section within the cube of radius 2 sections around the center's section; its center becomes the new center), and if the center is still not a village the status becomes LOSS when `groupsSpawned > 0`, else the raid stops. `ticksActive` then increments; at 48000 the raid stops and the tick ends. Then, when no raiders are alive and more waves remain (`hasMoreWaves`: a bonus wave exists and has not spawned, or the final wave has not been reached): if `raidCooldownTicks > 0`: when `waveSpawnPos` is absent every 5th cooldown value (or when it is present but not entity-ticking) it is recomputed with `getValidSpawnPos`; players are refreshed when the cooldown is 300 or divisible by 20; the cooldown decreases by 1; the boss bar progress becomes `clamp((300 - cooldown) / 300, 0, 1)`; execution then continues to the wave-spawn check below in the same tick (so the tick on which the cooldown reaches 0 can spawn). If the cooldown is 0 and `groupsSpawned > 0` it is set back to 300, the bar name reset to "Raid" and the tick ends (this is the pause after a wave has been cleared). On every tick not ended by the cases above, when `ticksActive % 20 == 0`: players are refreshed, raiders are refreshed (below), and the boss bar name shows the raid name followed by an "N raiders remaining" text when between 1 and 2 raiders are alive, else just the raid name. **Raider refresh** (`updateRaiders`): for every raider of every wave: it is marked for removal from the raid when it is removed, or in another dimension, or the squared distance between the raid center and its block is at least 12544 (112 blocks); otherwise, if its `tickCount` is at most 600 the remaining checks are skipped for it; otherwise it is marked if its UUID no longer resolves to a level entity; then, if its block is not in a village and its no-action time is above 2400, its `ticksOutsideRaid` is incremented by 1 (it is never reset here); and it is marked when `ticksOutsideRaid >= 30`. Marked raiders are removed from the raid (`removeFromRaid(raider, true)`), and a removed patrol leader also clears its wave's leader entry. **Wave spawning** (each tick, a loop with a failure counter starting at 0): while `shouldSpawnGroup` holds, namely `raidCooldownTicks == 0`, no raiders are alive, and (`groupsSpawned < numGroups`, or the bonus-group condition: the final wave has been reached, no raiders alive, and the raid has a bonus wave): take `waveSpawnPos` or a new `getValidSpawnPos`; if a position exists: `started = true`, `spawnGroup`, and on the first success of this call `playSound` (horn) is called; if no position exists the failure counter is incremented, and when it is above 5 (the 6th consecutive failed search) the raid stops. The same condition applies to ordinary and bonus waves. **Horn** (`playSound(level, pos)`): constants 13.0 and 64; one random long is drawn per call as the sound seed; for each player in the level: `d` = horizontal distance between the player and the block center of `pos` (x and z only); the packet is sent when `d <= 64` or the player is in the boss-bar player set; it is a `raid_horn` sound, neutral source, volume 64.0, pitch 1.0, at x = `player.x + 13 / d * (pos.x + 0.5 - player.x)`, z likewise, y = the player's own y. **Victory**: after the first wave has spawned (`started`), when no more waves remain and no raiders are alive, `postRaidTicks` counts up to 40; then the status becomes VICTORY and every hero of the village (players recorded by `addHeroOfTheVillage` that are still alive entities, living and not spectators) gets Hero of the Village for 48000 ticks with amplifier `raidOmenLevel - 1` (constructor flags read as false, false, true: ambient, particles, icon), the `raid_win` statistic and the raid-win advancement. **After the raid is over** (VICTORY or LOSS): each tick `celebrationTicks` increments; at 600 the raid stops; every 20 celebration ticks players are refreshed, the boss bar is made visible and (victory) its progress is set to 0 and its name to the raid-bar victory component, or (loss) its name to the raid-bar defeat component (the component strings were not read).

**Valid spawn position** (`getValidSpawnPos` calls `findRandomSpawnPos(level, 8)`): let `n = raidCooldownTicks / 20` (integer division) and `f = 0.22 * n - 0.24` (as a float). Choose a start angle `nextFloat * 2 pi`. For attempt `i` from 0 to 7: angle `a = start + pi * i / 8`; `x = center.x + floor(cos(a) * 32 * f) + nextInt(3) * floor(f)`, `z = center.z + floor(sin(a) * 32 * f) + nextInt(3) * floor(f)` (the two `nextInt(3)` draws happen in that order, x first); `y` = the WORLD_SURFACE height at `(x, z)`. Reject the attempt if `|y - center.y| > 96`; reject if the position is in a village and `n > 7`; reject if any chunk in the box +-10 blocks around is not loaded; reject if the position is not entity-ticking. Accept when the ravager's spawn placement type accepts the position, or when the block below is snow and the block at the position is air. The first accepted position is returned; if none, no position. At cooldown 300 (`n = 15`) `f = 3.06`, so positions lie about 98 blocks out; the radius shrinks as the countdown falls, and for `n = 0` `f` is negative, which mirrors the offsets through the center (a consequence of the formula as read).

### 14.3 Wave composition (`spawnGroup`, `Raid$RaiderType`)

A raid spawns wave number `w = groupsSpawned + 1` (read directly; the bonus wave is therefore `w = numGroups + 1`). `spawnGroup` first resets `totalHealth` to 0, computes the difficulty instance at the spawn position and evaluates the bonus-group condition once. For each raider type in the order vindicator, evoker, pillager, witch, ravager: `count = default[type][index] + bonus(type)`, where `index = w` for an ordinary wave and `index = numGroups(difficulty)` for the bonus wave (the flag is the bonus-group condition evaluated once at the start of the call: the final wave has been reached, no raiders are alive, and a bonus wave exists). Default spawns per wave (`spawnsPerWaveBeforeBonus`, indices 0 to 7; wave number = index):

| Type | w0 | w1 | w2 | w3 | w4 | w5 | w6 | w7 |
|---|---|---|---|---|---|---|---|---|
| Vindicator | 0 | 0 | 2 | 0 | 1 | 4 | 2 | 5 |
| Evoker | 0 | 0 | 0 | 0 | 0 | 1 | 1 | 2 |
| Pillager | 0 | 4 | 3 | 3 | 4 | 4 | 4 | 2 |
| Witch | 0 | 0 | 0 | 0 | 3 | 0 | 0 | 1 |
| Ravager | 0 | 0 | 0 | 1 | 0 | 1 | 0 | 2 |

(Easy raids use waves 1 to 3, Normal 1 to 5, Hard 1 to 7.) **Bonus count** `bonus(type)`: let `max` be: for Vindicator and Pillager: Easy `nextInt(2)` (a first draw), Normal 1, Hard 2; for Witch: 0 on Easy or when the wave is 1, 2 or 4, else 1; for Ravager: 1 if the difficulty is not Easy and this is the bonus group, else 0; Evoker 0. If `max > 0` the bonus is `nextInt(max + 1)` (a second draw), else 0. (The Witch rule is: not Easy, `w > 2` and `w != 4`, with `w` the wave number above, so on Normal the bonus wave `w = 6` can add a witch; the Ravager rule uses the same bonus-group flag as the table index; the two random draws are in the order stated.)
For each of the `count` raiders of a type: create it (spawn reason EVENT; if creation fails the rest of that type is skipped); if no leader has been chosen yet *within this `spawnGroup` call* (a local flag that persists across the raider types; the raid's recorded leaders of earlier waves play no part) and the raider can be a leader, it becomes the wave's leader (`setPatrolLeader`, `setLeader`: the wave's leader is recorded, the ominous banner placed on its head with drop chance 2.0); `joinRaid(wave, raider, spawnPos, false)` (the first call with `exists = false` applies position, finalize with reason EVENT, raid buffs, on-ground and adds it with passengers). For a ravager (a counter of ravagers created in this call is kept; it increments after every ravager, with or without a rider): a rider is created: if `w == 5` (`getNumGroups(NORMAL)`, the value is 5 on every difficulty) a pillager; else if `w >= 7` (`getNumGroups(HARD)`): the first ravager of the call (counter 0) gets an evoker, later ravagers a vindicator. Consequences: on Normal the bonus wave (`w = 6`) gets no rider; on Hard the bonus wave (`w = 8`) gets evoker and vindicator riders; on Easy (waves 1 to 3, bonus `w = 4`) no ravager has a rider; on Hard wave 5 ravagers carry pillagers; the rider joins the raid, is snapped to the ravager's position (yaw and pitch 0) and starts riding. After the loop `waveSpawnPos` is cleared, `groupsSpawned++`, the boss bar and the saved data are updated.
**Raid buffs** (`applyRaidBuffs(level, wave, isLeader)`): `enchantOdds` by raid omen level: 2 gives 0.1, 3 gives 0.25, 4 gives 0.5, 5 gives 0.75, any other level 0 (so a raid with omen level 1 never enchants). Vindicator: always holds an iron axe; if `nextFloat <= enchantOdds` (the comparison is "random below odds" as read from `ifgt`) the axe is enchanted with provider `raid/vindicator` (Sharpness 1) when the wave is at most the Normal wave count (5), else `raid/vindicator_post_wave_5` (Sharpness 2); main hand set to it. Pillager: crossbow; same odds; provider `raid/pillager_post_wave_5` (Quick Charge 2) when the wave is above 5, else `raid/pillager_post_wave_3` (Quick Charge 1) when the wave is above 3 (Easy wave count), else none. Evoker, Witch, Ravager, Illusioner: none.
Raiders' boss bar health counts: `totalHealth` is the sum of raider health added when they join; the bar progress is `clamp(sum of living raiders' health / totalHealth, 0, 1)`.

Roar: roar behaviour (anger +20 on the roar target, `ROARING` pose, roar sound delayed 25 ticks). Setting the roar target belongs to the `SetRoarTarget` step (idle activity priority 10, investigate and sniff activities priority 5).
**Melee**: `doHurtTarget`: entity event 4, `attack_impact` sound, sets the sonic boom cooldown to 40 ticks, then the base melee (30 damage, knockback 1.5 with the target's resistance).

### 15.1 How a vibration reaches the warden (resolved; `Warden$VibrationUser`, `Warden.tick`, `Warden.updateDynamicGameEventListener`; generic rules in 30 §2 to §3)

1. **Listener and position.** The warden owns a `DynamicGameEventListener` around a `VibrationSystem$Listener` (data class `VibrationSystem$Data`, saved under the key `listener`, user class `Warden$VibrationUser`). The framework registers it in the chunk section of the warden's position on a server level and re-registers it when the warden changes section (30 §2.2, "moving listeners"). The listener's position source is an `EntityPositionSource(warden, yOffset)`: position = the warden's position plus `(0, yOffset, 0)`, where `yOffset` is the float `getEyeHeight()` read **once when the user object is built in the constructor**, i.e. the standing eye height: the warden's `EntityTypes` entry sets the size 0.9 x 2.9 and no eye height, so the default `0.85f * height` applies, the float product 2.4650001525878906 (about 2.465); `Warden.getDefaultDimensions` replaces the dimensions only while digging or emerging (width x 1.0), which does not matter here because the offset was captured earlier. It does not change when the pose changes.
2. **Dispatch range** (30 §2.1): the listener is offered an event when the squared block distance between `BlockPos.containing(listener position)` and the event's block is at most `16^2` (listener radius `GAME_EVENT_LISTENER_RADIUS` = 16); the event's own notification radius (16 for nearly all events, 32 for `shriek`, 10 for the jukebox events) only chooses which chunk sections are scanned. The warden's listener is not `BY_DISTANCE`, so it is called at once in visiting order.
3. **Filters, in order** (the first failure drops the event; 30 §3.3 to §3.6 give the generic steps, the warden-specific parts are):
   - a vibration is already in flight: ignored;
   - **validity** (30 §3.5): the event must be in tag `warden_can_listen`, which is the 55 events of tag `vibrations` **except `flap`**, plus `shriek` and (through the nested tag `shrieker_can_listen`) `sculk_sensor_tendrils_clicking`; a spectator source is invalid; a sneaking source with an event in `ignore_vibrations_sneaking` is invalid (the `avoid_vibration` advancement can trigger, because the warden's user answers `canTriggerAvoidVibration` true); a source whose `dampensVibrations()` is true is invalid (this includes the warden itself: it never hears its own events; also dropped wool items); an affected block state in tag `dampens_vibrations` (wool) is invalid;
   - **`canReceiveVibration`** (warden rule, in this order, all must pass): not no-AI; not dead or dying; memory `vibration_cooldown` absent; not digging or emerging; the event's block position inside the world border; and, **when the source entity is a `LivingEntity`, `canTargetEntity(source)` must hold** (creative and spectator players, allies, armor stands, other wardens, invulnerable and dying entities are therefore ignored); a source that is not a living entity (an item entity, a projectile, a block change with no entity, no entity at all) passes;
   - **occlusion** (30 §3.6): all six rays between the block centres blocked by `occludes_vibration_signals` (wool) drops the event;
   - otherwise the event becomes a candidate (30 §3.4) with the float distance from the event position to the listener position and the current game time.
4. **Timing** (30 §3.4): the ticker picks the candidate in the first tick strictly after the event's tick, the travel time is `floor(distance)` ticks (distance = event `Vec3` to listener `Vec3`), and the vibration arrives in tick `T + max(floor(distance), 1)` for an event posted in tick `T`, provided the 3 by 3 chunks around the warden's block are loaded and ticking (otherwise it waits and retries every tick). The ticker is run by `Warden.tick` on the server **before** the superclass tick of that same tick (so a vibration arriving in tick `t` is seen by the brain in tick `t`); the same method refreshes the dig cooldown when the warden requires persistence (`isPersistenceRequired` or `requiresCustomPersistence`, for example a named warden), which keeps a persistent warden from ever digging away.
5. **On arrival** `onReceiveVibration` of 15 runs (cooldown 40 ticks, entity event 61, `tendril_clicks` sound, anger and disturbance rules). The sound pitch is `Warden.getVoicePitch()`, which the warden does not override: `LivingEntity.getVoicePitch` for a non-baby is `(nextFloat() - nextFloat()) * 0.2f + 1.0f` (two draws from the warden's own random source, the first minus the second), and 1.5f instead of 1.0f for a baby.

Worked example (derived, Normal difficulty): a survival player walks on stone 10 blocks east of a calm warden and at the same height; the `step` event (frequency 1 is irrelevant to the warden) is posted in tick `T` at the player's position. Listener position = warden feet + 2.465, so the float distance is `sqrt(10^2 + 2.465^2)` = 10.30 and the travel time is 10: the warden is told in tick `T + 10`, sets `vibration_cooldown` for 40 ticks, anger +35 on the player (a second vibration inside those 40 ticks is not received) and, because it is not ANGRY and the anger manager had no active entity, the disturbance location becomes the player's block (INVESTIGATE for up to 100 ticks, 15.4). A player sneaking on the same stone with `step` posts no vibration that the warden accepts (the event is in `ignore_vibrations_sneaking`).

### 15.2 The Darkness pulse: `(id + tickCount) % 120` and who receives it (resolved; `Warden.customServerAiStep`, `Warden.applyDarknessAround`, `MobEffectUtil.addEffectToPlayersAround`, `Entity.commonTick`, `Level.getNextEntityId`)

- **`tickCount`** is `Entity.tickCount`, the number of ticks the entity has been ticked on this run. It starts at 0 when the entity object is created, is raised by 1 in `Entity.commonTick`, which `ServerLevel` calls **before** `Entity.tick` on every entity tick (so inside `customServerAiStep` of the first tick its value is already 1), and it is **not saved**: a warden loaded from a chunk starts counting again from 0.
- **`id`** is `Entity.getId()`, the runtime network id taken at construction from a process-wide counter (`Level.getNextEntityId`, an `AtomicInteger` starting at 0 whose `incrementAndGet` is called for every entity created in any dimension; the first entity gets id 1; the id is not saved and is not reused). Saved entities get a fresh id on every load.
- **Pulse rule**: in `customServerAiStep` (server only, runs every tick of the warden after the brain tick and `Monster.customServerAiStep`, whatever its pose) the pulse happens when `(id + tickCount) mod 120 == 0`. For a given warden the pulses are exactly 120 ticks apart, and its first pulse is at the `tickCount` `t` in 1 to 120 with `t == (-id) mod 120` (when `id mod 120 == 0` that is `t = 120`). The id staggers the pulse phase of different wardens; nothing else depends on it.
- **Effect**: `applyDarknessAround(level, warden position, warden, 20)` builds the effect instance Darkness, duration **260** ticks, amplifier 0, not ambient, **no particles** (visible false), and calls `MobEffectUtil.addEffectToPlayersAround(level, source = warden, centre = the warden's position (feet), radius 20.0, effect, displayLimit 200)`. A player is selected when **all** hold: `player.gameMode.isSurvival()` (the game types **survival and adventure** only: `GameType.isSurvival` is `this == SURVIVAL || this == ADVENTURE`; **creative and spectator players never receive the effect**); the source warden is not allied to the player (`isAlliedTo`, team rules); the player's position (feet) is within the radius of the centre (`Vec3.closerThan(playerPos, 20)`: squared distance below 400, strict); and (the player does not have Darkness, or the player's Darkness amplifier is lower than the new amplifier 0 (never true), or the player's current Darkness `endsWithin(200 - 1)` i.e. has at most 199 ticks left and is not infinite). Each selected player receives a copy of the instance via `addEffect(copy, warden)`.
- Consequences: a survival player standing in range keeps Darkness without interruption: a pulse every 120 ticks leaves 140 ticks of the previous effect, which is within the 199-tick limit, so every pulse renews it to 260; a player who walks into range gets it at the next pulse (at most 120 ticks later). The sculk shrieker (20 §15 spawning, 44-x2) uses the same helper with source null (no ally test), centre = the block centre and radius 40, and the same survival/adventure filter. A creative player standing next to a warden gets no new Darkness; a Darkness effect applied earlier while the player was in survival simply runs out.

### 15.3 Sonic boom damage type (resolved; `data/minecraft/damage_type/sonic_boom.json` and `tags/damage_type/*.json`)

`sonic_boom`: `exhaustion` 0.0, `scaling` `always`, `message_id` `sonic_boom` (no `effects`, default death message). Tag membership, resolved through nested entries (`bypasses_shield` contains the nested entry `#minecraft:bypasses_armor`): **`bypasses_armor`**, **`bypasses_enchantments`**, **`bypasses_shield`** (nested; a shield does not block it, 17 §4.12), `panic_causes` and `witch_resistant_to` (a witch takes 15%, 11). It is **not** in `bypasses_effects` (its only member is `starve`) or `bypasses_resistance` (`out_of_world`, `generic_kill`), so the Resistance effect still applies; not in `bypasses_invulnerability` (an invulnerable victim, including a creative player, takes nothing), `bypasses_cooldown` (the tag is empty: the victim's post-hit invulnerability time applies as for any other source), `is_projectile`, `no_impact` or `no_knockback` (the damage call's own knockback happens in addition to the extra velocity push of the behaviour, 15 above). The warden calls `hurtServer(level, sonicBoom(warden), 10.0)` (direct and causing entity: the warden).
Scaling: only `Player.hurtServer` applies difficulty scaling (3.1; searched `net/minecraft/world/entity` for `scalesWithDifficulty`: only `Player` calls it), and `scaling always` makes it apply regardless of the cause. So against a **player**: Peaceful 0 (3.1), Easy `min(10 / 2 + 1, 10)` = 6, Normal 10, Hard 15, then the armor and enchantment steps are skipped (bypass tags), then Resistance, absorption and the rest of the player damage steps apply. Against a non-player living entity the damage is 10.0 unscaled. Example: a Hard-difficulty player with full diamond armor, no shield effect and no potion effects takes 15.0 (the armor does not reduce it); the same player with Resistance I (-20%) takes 12.0.

### 15.4 Activity entry and exit rules (resolved; `WardenAi`, `ActivityData`, `Brain.setActiveActivity`, the behaviours named)

**How the activity is chosen.** At the end of `customServerAiStep` (after the brain tick, `Monster.customServerAiStep`, the Darkness pulse and the 20-tick anger tick) the warden calls `updateActivity`, which picks the **first valid** activity in the order EMERGE, DIG, ROAR, FIGHT, INVESTIGATE, SNIFF, IDLE (`setActiveActivityToFirstValid`; an activity is valid when all of its condition memories hold; IDLE has none). The choice takes effect for the **next** tick's behaviour start phase. CORE is always active. When the chosen activity is **not already active**, `Brain.setActiveActivity` first erases, for every currently active activity other than the new one, that activity's "memories to erase when stopped" (below), then makes the new one (plus CORE) the active set. **Running behaviours are not stopped by the switch**: `tickEachRunningBehavior` keeps ticking every running behaviour until its own `canStillUse` or maximum duration ends it (`Behavior.tickOrStop`), so for example an 84-tick `Sniffing` that was started continues to its end even if INVESTIGATE has since become active.
The `ActivityData.create(activity, startPriority, behaviours, memory)` form used for EMERGE, ROAR, FIGHT, INVESTIGATE and SNIFF means: the condition is "`memory` present" **and** `memory` is erased when the activity stops being the active one. DIG uses the condition-set form (no erase). Priorities inside an activity: consecutive from `startPriority` in list order.

| Activity | Valid when | Erased when it stops | How it is entered | How it ends |
|---|---|---|---|---|
| EMERGE | `is_emerging` present | `is_emerging` | `finalizeSpawn` with spawn reason TRIGGERED (sculk shrieker): pose EMERGING, `is_emerging` set for 134 ticks (20 §15 spawning) | the memory expires after 134 ticks (and `Emerging` has maximum duration 134); `Emerging.stop` sets the pose STANDING when it is still EMERGING (44-5 §3.4). ### 15.5 The touch rule (`Warden.doPush`)

Read in `Warden.doPush`, its caller `LivingEntity.pushEntities` and the selector `EntitySelector.pushableBy` (artifact of `README.md`). The vibration and anger numbers it uses are in the Anger paragraph above; the disturbance-location procedure is 15.6.

**Which entities reach `doPush`.** Every living entity runs `pushEntities` once per tick in its `aiStep` (after the auto-spin-attack bookkeeping, immediately before the end of the push profiler section). It asks the level for the entities whose bounding box overlaps the warden's own bounding box (no inflation) that pass `EntitySelector.pushableBy(warden)`, and calls `doPush(entity)` for each one in the order the level returns them (a `List` from the level's entity query; the order is the query order, not distance). The selector, in order: (1) the warden's team collision rule `NEVER` selects nothing at all; (2) the candidate must not be a spectator; (3) the candidate's `isPushable()` must be true (for a living entity: it is alive, is not a spectator, is not on a climbable block, and, when it is not always-ticking, its block position is entity-ticking; the base `Entity.isPushable` returns false, so entity classes that do not override it, such as item entities, experience orbs and arrows, are never candidates; `AbstractBoat` and `AbstractMinecart` override it to return true and `ArmorStand` to return false; `Bat` returns false, `Parrot` returns true, `Creaking` returns the base monster rule (`LivingEntity.isPushable`) and its synced `CAN_MOVE` flag (so a frozen creaking is not a candidate), and `AbstractHorse` returns true only when it has no passenger (`!isVehicle()`, a ridden horse is not a candidate)); (4) the candidate's own team collision rule `NEVER` rejects it; (5) with the two teams allied the rules `PUSH_OWN_TEAM` (either side) and `PUSH_OTHER_TEAMS` (either side) reject or accept as their names say. A creative-mode player is a candidate (creative is not tested here).

**What `doPush(entity)` does, in order.**

1. When the warden has no AI (`NoAI`) nothing below the base push happens. When the memory `touch_cooldown` is present nothing below the base push happens.
2. Otherwise (no `NoAI`, memory absent): set the brain memory `touch_cooldown` (value `Unit`) with an expiry of 20 ticks; call `increaseAngerAt(entity)` (35 anger, with the listening sound; it is itself ignored when `canTargetEntity(entity)` fails, see the Anger paragraph, and the cooldown is started regardless); then call `WardenAi.setDisturbanceLocation(warden, entity.blockPosition())` (15.6).
3. In every case (whether or not the cooldown was active) the base `Monster.doPush` then runs (the ordinary entity push of the two bodies; its numbers are 18 section 3.3).

**Rules.**

- The cooldown starts for **any** pushed entity: there is no filter in `doPush`. The only filters are those of the candidate list above, and `NoAI`. A non-living pushable entity (a boat, a minecart), a creeper, a villager, a baby, another warden (when it is not digging or emerging, `Warden.isPushable`) and a player in creative mode all start the cooldown. Only the anger increase afterwards depends on `canTargetEntity` (it must be a living entity in the same level, not creative or spectator, not allied to the warden, not an armor stand, not another warden, not invulnerable, not dying, inside the world border).
- The cooldown is a **brain memory**: key `touch_cooldown` (`MemoryModuleType.TOUCH_COOLDOWN`, in the warden's memory-type list), `Unit` value, expiry 20. Brain memories with an expiry lose one tick per brain tick (the warden's `customServerAiStep` ticks its brain once per server tick it is ticked), so the memory is present for the next 20 brain ticks after being set; a second touch within that window changes nothing but the base push. There is no separate counter field (`TOUCH_COOLDOWN_TICKS` is the constant 20 only).
- The entity that gets the anger and the disturbance is **the pushed entity itself**, whichever one the loop reached first while the memory was absent; entities visited later in the same `pushEntities` call (the memory is now present) get only the base push. So at most one touch per 20 ticks, and with several overlapping entities the first in query order wins.
- The disturbance location is set at the **block position of the pushed entity** (`blockPosition()`, the block containing its position, not a centre) subject to the conditions of 15.6. Because `increaseAngerAt` ran first, a touch that lifts the anger of the pushed entity to ANGRY (80 and above, for example 35 + 35 + 35 = 105 after three touches 20 ticks apart without decay) makes `getEntityAngryAt` present, so the disturbance location of that very touch is then **not** set (15.6 condition 2).
- When the pushed entity is the current attack target: the anger increase happens if `canTargetEntity` allows it (the dig cooldown is refreshed if present, and, only when the entity is a player, the warden's previous target was not a player and the new level is ANGRY, the attack target is erased); the disturbance location is not set because an attack target memory is present (15.6 condition 3).
- The touched anger amount is 35 with `playSound` true (`increaseAngerAt(entity)` is `increaseAngerAt(entity, 35, true)`; the sound is the listening sound for the current anger level).

Example (inputs and expected outputs; anger decay, 1 per 20-tick manager step, is ignored). A survival player, not allied, walks into a calm warden (no attack target, empty anger table) at tick `T`: at `T` the memory `touch_cooldown` is set with expiry 20, the player's anger becomes 35 (level CALM, because AGITATED starts at 40), the listening sound plays, `disturbance_location` is set to the player's block position for 100 ticks together with a 100-tick look target and sniff cooldown, the walk target is erased and the base push runs. At `T + 5` with the player still overlapping: the base push only. At `T + 21` (memory expired): another 35 is added (70, level AGITATED) and the location is written again. At about `T + 42`: another 35 (105, level ANGRY): the anger is raised, the listening sound plays, and no disturbance location is written because the warden is now angry at an active entity (15.6).

### 15.6 Disturbance location and dig cooldown helpers

`WardenAi.setDisturbanceLocation(warden, pos)`, read in full: 1. return at once when `pos` is outside the world border; 2. return at once when `warden.getEntityAngryAt()` is present (that is, when the anger level is ANGRY and `AngerManagement.getActiveEntity()` has a living top suspect; `getEntityAngryAt` is empty at lower levels); 3. return at once when the `attack_target` memory is present; 4. otherwise, in order: `setDigCooldown`, set `sniff_cooldown` (`Unit`, expiry 100), set `look_target` (a `BlockPosTracker` on `pos`, expiry 100), set `disturbance_location` (`pos`, expiry 100), erase `walk_target`. The callers are the vibration handler (Vibrations paragraph above, which adds its own pre-conditions), the touch rule (15.5) and the sniff end (Sniff in the Brain constants).

`WardenAi.setDigCooldown(entity)`: when the entity's brain already holds the `dig_cooldown` memory it is set again with a 1200-tick expiry; when it holds no such memory nothing happens. `increaseAngerAt(entity, amount, playSound)` calls it after its guards (it also never creates the memory). The places that create the memory are the spawn path (`finalizeSpawn`) and the end of a fight (see also 44 part 5, section 3.3, remarks).

### 16.1 Brain wiring: idle, stop-attacking and where `breeze_shoot` comes from (resolved; `BreezeAi`, `BreezeAi$SlideToTargetSink`, `StartAttacking`, `StopAttackingIfTargetInvalid`, `Sensor`, `Shoot`, `LongJump`, `Slide`, `ShootWhenStuck`)

**Activity choice.** `Breeze.customServerAiStep` runs `Brain.tick`, then `BreezeAi.updateActivity`, which picks the first valid of `[FIGHT, IDLE]`. FIGHT is valid when `attack_target` is present **and** `walk_target` is absent (the plain condition-set form of `ActivityData`, no memory is erased on a switch). IDLE has no condition. CORE (always active): `Swim` 0.8 (priority 0) and `LookAtTargetSink` 45/90 (priority 1).
Because FIGHT needs `walk_target` absent, every time a behaviour of FIGHT sets a walk target (`Slide`) the active activity becomes IDLE for as long as the walk target exists, and IDLE's `SlideToTargetSink` is what walks it.

**IDLE list** (explicit priorities): 0 `StartAttacking` with the finder "memory `nearest_attackable`"; 1 `StartAttacking` with the finder "the entity of memory `hurt_by` (a damage source) if it is a living entity"; 2 `SlideToTargetSink(20, 40)`; 3 a random-one-of group: `DoNothing(20, 100)` (weight 1), `RandomStroll` at speed 0.6 (weight 2).
`StartAttacking` (a one-shot): requires `attack_target` **absent** (and `cant_reach_walk_target_since` registered); asks its finder; when an entity is returned and `breeze.canAttack(entity)` holds (the breeze rule, players and iron golems only, 16 table) it sets `attack_target` to it and erases `cant_reach_walk_target_since`. The sensor `BreezeAttackEntitySensor` writes `nearest_attackable` every 20 ticks (44-5 §7).
`SlideToTargetSink(20, 40)` is `MoveToTargetSink` (18 framework) with the run duration drawn uniformly from 20 to 40 ticks per run; additionally **on start** it plays the `breeze_slide` sound and sets the pose SLIDING, and **on stop** it sets the pose STANDING and, when `attack_target` is present, sets `breeze_shoot` for **60 ticks**.

**FIGHT list** (priorities 0 to 4): `StopAttackingIfTargetInvalid`, `Shoot`, `LongJump`, `ShootWhenStuck`, `Slide`. Each behaviour is tried every tick in that order when it is not running (`startEachNonRunningBehavior`), its own memory conditions first and then its extra start condition; several can run together when their conditions allow, but all of them require `walk_target` absent or set their own, so in practice one runs at a time.

**Stop-attacking rule** (priority 0 of FIGHT; `StopAttackingIfTargetInvalid.create(condition)`, i.e. no callback and the "tired of trying to reach" option **on**). Every tick, with `T` = the attack target, `attack_target` is erased when any of these holds: (1) `breeze.canAttack(T)` is false; (2) memory `cant_reach_walk_target_since` is present and `gameTime - thatValue > 200` (200 ticks of failing to path to a walk target); (3) `T` is not alive; (4) `T` is in another level; (5) the stop condition: **not** `wasEntityAttackableLastNTicks(breeze, 100)`. That last predicate wraps "`T` is attackable ignoring line of sight" in a counter shared by the whole brain (one counter per breeze, not per target): when the inner test is true the counter is set to 100 and the predicate is true; when it is false the counter is decremented first and the predicate is true while the counter is still `>= 0`. The counter starts at 0. So the breeze keeps a target that is attackable (ignoring line of sight and, because `T` is the current attack target, ignoring invisibility) and for 100 further failed evaluations (about 100 ticks, one evaluation per tick while FIGHT is active) after that; a target that was never attackable on the breeze's brain is dropped on the first check. "Attackable ignoring line of sight" is the framework's combat targeting test (`TargetingConditions.forCombat()` with `ignoreLineOfSight` and the range set to the breeze's follow range 24, updated at every sensor scan, 18 §4.3). `LongJump.canRun` also erases `attack_target` when the target is not within the follow range (`closerThan(T, 24)`, 3D, strict).

**Sources of `breeze_shoot`.** Searching every class under `net/minecraft/world/entity` for the memory found exactly these writers (plus the memory registration):

### 16.2 The shot and `Projectile.shoot` (resolved; `Shoot.tick`, `Projectile.spawnProjectileUsingShoot`, `Projectile.getMovementToShoot`, `RandomSource.triangle`)

Timeline of one `Shoot` run (constants are `Math.round(15.0)`, `Math.round(4.0)`, `Math.round(10.0)` = 15, 4, 10): the behaviour's maximum duration is `15 + 1 + 4` = 20 ticks and it stops earlier when the target or `breeze_shoot` disappears. **Start** (tick `s`): pose SHOOTING (when the target memory is present), memory `breeze_shoot_charging` for 15 ticks, sound `breeze_inhale` (volume 1.0, pitch 1.0). **Every tick**: `lookAt(EYES, target position)` (the target's feet position as the point looked at). While `breeze_shoot_charging` or `breeze_shoot_recovering` is present nothing else happens. On the first tick where neither is present (tick `s + 15`, derived from the 15-tick expiry rule of 18 framework) it sets `breeze_shoot_recovering` for 4 ticks and fires **one** charge; the following ticks only look. **Stop**: pose STANDING if it is SHOOTING, `breeze_shoot_cooldown` 10 ticks, erase `breeze_shoot`.
**Start condition**: required memories `attack_target` present, `breeze_shoot_cooldown`, `breeze_shoot_charging`, `breeze_shoot_recovering` and `breeze_jump_target` absent, `breeze_shoot` present, `walk_target` absent; extra: pose STANDING and the squared distance between the breeze's position and the target's position below 256 (when this test fails for the current target the `breeze_shoot` memory is erased, so an out-of-range breeze must arm it again).
**Spawn and aim**: the `BreezeWindCharge` is created with the breeze as owner at `(breeze.x, firingY, breeze.z)`, `firingY = breeze.y + bbHeight / 2 + 0.30000001192092896` (the float constant 0.3 widened). `dx = target.x - breeze.x`, `dz = target.z - breeze.z` (feet positions) and `dy = target.getY(f) - firingY` with `target.getY(f) = target.y + f * target.bbHeight` (times the entity scale) and `f = 0.8` when the target is a passenger, else 0.3. Then `spawnProjectileUsingShoot(charge, level, empty stack, dx, dy, dz, power 0.7f, uncertainty u)` calls `charge.shoot(dx, dy, dz, 0.7f, u)` and adds the entity. The power is the float 0.7f, which the vector scaling widens to the double **0.699999988079071**; `u` is the float `(float)(5 - 4 * difficultyId)` (an int converted to float), and each error component is `0.0172275 * (double) u` (the double literal 0.0172275) used as the spread of `triangle`; the two target-height fractions 0.3 and 0.8 are double literals (`target.getY(f) = target.y + bbHeight * f`, `bbHeight` a float widened) and the 0.30000001192092896 of `firingY` is the float 0.3f widened. Sound `breeze_shoot` (volume 1.5, pitch 1.0) at the breeze. The target's own velocity is **not** used (no lead).
**`Projectile.shoot(dx, dy, dz, power, uncertainty)`** (`getMovementToShoot`): `v = normalize(dx, dy, dz) + (ex, ey, ez)` then `v = v * power`, where each error component is `triangle(0, 0.0172275 * uncertainty)` and `RandomSource.triangle(c, s) = c + s * (nextDouble() - nextDouble())` (two `nextDouble` calls per component, in the order x, y, z, so six calls from the **projectile entity's own** random source; the first call of each pair is the added term). The vector is not renormalised, so the speed is `0.699999988079071 * |normalize(d) + e|`, usually just above 0.7. Because `s` may be negative and the distribution of `nextDouble() - nextDouble()` is symmetric, a negative `uncertainty` gives the same distribution as its absolute value. Rotation (`Projectile.shoot`): with the new velocity `v` and `h = v.horizontalDistance()`, yaw = `(float)(Mth.atan2(v.x, v.z) * 57.2957763671875)` and pitch = `(float)(Mth.atan2(v.y, h) * 57.2957763671875)` (both products in double arithmetic, then narrowed to float; no negation), where `Mth.atan2` is the custom approximation of 10 §16.4 (44-residual-mob-questions-x1 §11.1), not the library function; the previous-tick rotations `yRotO` and `xRotO` are set to the new values, and the entity is marked for a sync. Example: `v = (0, 0, 0.7)`: yaw 0, pitch 0; `v = (0.7, 0, 0)`: yaw about 90; `v = (0, 0.7, 0)` (so `h = 0`): pitch about 90.
**Uncertainty by difficulty**: `u = 5 - 4 * difficultyId`: Peaceful (0) 5 (a breeze does not exist in Peaceful), Easy (1) **1**, Normal (2) **-3**, Hard (3) **-7**. Largest error per component `0.0172275 |u|`: Easy 0.0172 (0.99 degrees of angle at most per axis), Normal 0.0517 (2.96 degrees), Hard 0.1206 (6.9 degrees); the distribution of each component is triangular on `[-0.0172275 |u|, +0.0172275 |u|]` with standard deviation `0.0172275 |u| / sqrt(6)`: Easy 0.0070, Normal 0.0211, Hard 0.0492.

### 16.3 Wind charge flight, hit and explosion (resolved for the breeze charge; shared rules also in 44-8 §6 and §8)

`breeze_wind_charge` (id 18, box 0.3125 x 0.3125 placed 0.15 below the entity position, tracking 4, update interval 10, 21 §8.18). It extends `AbstractHurtingProjectile` with `accelerationPower = 0`.
- **Flight**: the velocity set by `shoot` never changes. `applyInertia` computes `(v + normalize(v) * 0) * inertia` with `getInertia() = 1.0` and `getLiquidInertia() = getInertia() = 1.0` (the base class's water value 0.8 is overridden), so there is **no drag in air or in water**; the tick never applies gravity (the hurting-projectile tick has no gravity step; searched `AbstractHurtingProjectile` and `AbstractWindCharge` for gravity: none), so the path is a **straight line at constant velocity**: displacement per tick equals the velocity (about 0.7 blocks, 14 blocks per second). Each tick the hit test (44-8 §6.2) runs along `P` to `P + v`; a block hit moves the charge to the hit point.
- **Lifetime**: there is no age counter and no time limit. The charge ends only by: hitting an entity or a block (it explodes and is discarded); the owner entity being removed (the breeze dies or is discarded) or the chunk at its block position being unloaded (`discard`, no explosion); or its block y exceeding `level.maxY + 30` (it explodes there and is discarded; this check runs before the normal tick). A charge that is deflected by a player keeps flying (`redirectable_projectile`, 44-8 §6.3).
- **Entity hit** (server): the entity must pass `canHitEntity`: not another wind charge, not an end crystal, pickable, and not the breeze's own vehicle companion while the owner has not left (44-8 §6.1). Then: `owner.lastHurtMob = target` for a living owner; `target.hurtServer(level, windCharge(charge, owner), 1.0)`; if it landed and the target is living, the post-attack enchantment effects run; then in every case `explode(charge position)` and the charge is discarded. Damage type `wind_charge`: exhaustion 0.1, scaling `when_caused_by_living_non_player` (a breeze is a living non-player, so the 1.0 is scaled for **player** victims: Easy `min(1/2 + 1, 1)` = 1.0, Normal 1.0, Hard 1.5), message id `mob`; member of the tags `always_kills_armor_stands`, `is_projectile`, `panic_causes`, `sulfur_cube_with_block_immune_to`; not in `bypasses_armor` (armor points reduce it) nor `no_knockback` (the hit itself knocks back).
- **Block hit**: `explode(hitLocation + faceNormal * 0.25)` then discard.
- **Explosion** (`BreezeWindCharge.explode`): `Level.explode` with: source = the charge, explicit damage source none, the shared calculator `EXPLOSION_DAMAGE_CALCULATOR`, the centre x, y, z, radius **3.0**, fire false, interaction TRIGGER, small particle `gust_emitter_small`, large particle `gust_emitter_large`, an empty extra-sound list, burst sound `breeze_wind_charge.wind_burst`. The calculator is `SimpleExplosionDamageCalculator(explodesBlocks true, damagesEntities **false**, knockback multiplier **absent**, immune blocks = tag `blocks_wind_charge_explosions`)`: **the explosion itself deals no damage to any entity**; the only damage of a breeze shot is the 1.0 direct hit above (plus fall damage the knockback may cause). Blocks are only triggered, never destroyed (20 §6.2, TRIGGER_BLOCK).
- **Knockback** (20 §6.2 applied with `R = 3.0`): entities within the box `centre +- (2R + 1)` = 7 and within `2R` = **6 blocks** of the centre (feet distance) that do not ignore explosions are pushed; the source entity (the charge) is excluded from the query, the breeze and other mobs are not. For each: `dist = distance / 6`; `seen` = the fraction of unobstructed sample rays (20 §6.2); `strength = (1 - dist) * seen * m * (1 - explosion_knockback_resistance)`, with the knockback multiplier `m` = **1.0** (the calculator's multiplier is absent so the base value 1.0 applies; it returns 0 for a player whose abilities have `flying` true, 44-8 §8, and then `seen` is not even computed); the velocity of the entity increases by `normalize(eyePosition - centre) * strength` (the eye position for living entities, the position for primed TNT). Players that are not spectators and not (creative and flying) get the pushed vector in the Explode packet (distance squared below 4096 from the centre). Compared with the player's own wind charge (radius 1.2, multiplier 1.22, 44-8 §8) the breeze charge reaches 6 blocks, not 2.4, with multiplier 1.
Worked numbers (derived, `seen` = 1, no resistance, flying false): a player 3 blocks from the burst centre gets `strength = 1 - 3/6` = 0.5 added along the direction from the burst to his eyes; at 1 block 0.8333; at 5.5 blocks 0.0833; at 6 blocks or more nothing. For a charge that hits an entity the burst centre is the charge's position at the hit (next to the victim, `explode(this.position())`), so the victim itself is within a block of the centre and receives a large push (`strength` above 0.83) along the vector from the centre to its eyes; the push on bystanders follows the same formula.

### 16.5 `randomPointBehindTarget`, the middle-circle point and `getPosAway` (resolved; `BreezeUtil`, `Slide`, `DefaultRandomPos`)

**`randomPointBehindTarget(T, random)`** (used by the long jump and by the slide): draws, in this order, `g = nextGaussian()` (double, narrowed to float) then `u = nextFloat()`. `yaw = T.yHeadRot + 180.0f + (float) g * 90.0f / 2` (float arithmetic, degrees: the multiplication by 90.0f comes before the division by 2, so the angle behind the target with a normal deviation of 45 degrees), `dist = Mth.lerp(u, 4.0f, 8.0f)` (float) = `4 + 4 u`. The direction is `Vec3.directionFromRotation(0, yaw)`: with `r = 0.017453292f` (= 0.01745329238474369), the float `a = -yaw * r - 3.1415927f` and the pitch factors `cp = -Mth.cos(-pitch * r)`, `sp = Mth.sin(-pitch * r)`, the result is `(Mth.sin(a) * cp, sp, Mth.cos(a) * cp)`, where `Mth.sin`/`Mth.cos` return floats, `cp` is a float and the two products are float products widened when the `Vec3` is built; for pitch 0 this equals `(-sin(yaw), 0, cos(yaw))`. `Mth.sin` and `Mth.cos` are the table functions (10 §16.3), called with the float argument widened to double. The point is `T.position + direction * dist`, with no height adjustment (the surface snap of 16.4 handles height). Example: the target looks along +z (`yHeadRot` 0): yaw 180 plus the deviation, direction about `(0, 0, -1)`, so the point is 4 to 8 blocks behind it, on the -z (north) side of the target's feet.
**`randomPointInMiddleCircle(breeze, T)`** (slide only): `r = nextDouble()`, `m = |T.position - breeze.position| - lerp(r, 8.0, 4.0)` where `lerp(r, 8, 4) = 8 - 4 r`; the point is `breeze.position + normalize(T.position - breeze.position) * m`: on the line from the breeze to the target, stopping `8 - 4 r` blocks (4 to 8) short of the target (it can be behind the breeze when the target is closer than that band).
**`Slide.start`** (single tick behaviour; requires `attack_target` present, `walk_target`, `breeze_jump_cooldown` and `breeze_shoot` absent; extra: on the ground, not in water, pose STANDING; `canStillUse` is the default false): with `T` the attack target: `inner = withinInnerCircleRange(T.position)` (`Vec3.atCenterOf(breeze block).closerThan(pos, 4.0, 10.0)`: horizontal distance below 4 and absolute height difference below 10). Candidate `c` starts null. If `inner`: `a = DefaultRandomPos.getPosAway(breeze, 5, 5, T.position)` (18 §4.2 and 44-3 for the sampling: a direction within pi/2 of "away from the target", horizontal range 0 to 5, vertical range 5, up to 10 candidates; each valid candidate is scored by `getWalkTargetValue(pos)`, which the breeze inherits from `Monster`: `0.5 - lightLevelDependentMagicValue(pos)`, i.e. `-(getPathfindingCostFromLightLevels)`, so darker positions score higher; the highest score wins and the earliest candidate wins ties); if `a` is non-null, has line of sight from the breeze (the 16.4 test with the breeze's feet position, limit `max(50, follow range)`) and `T.distanceToSqr(a) > T.distanceToSqr(breeze)` then `c = a`. If `c` is still null: `nextBoolean()` (breeze's random): true gives `randomPointBehindTarget(T, random)`, false gives `randomPointInMiddleCircle`. The walk target is `WalkTarget(BlockPos.containing(c), speed 0.6f (0.6000000238418579), completion distance 1)`.

   e. when `creaking.isLookingAtMe(P, 0.5, false, true, [yEye, yBody, yMid])` (the viewer is `P`, the receiver is the creaking; the viewer's yaw is its `yHeadRot`, 17.1.1) with `scale = creaking.getScale()` (a float, widened), `yEye = creaking.getEyeY()`, `yBody = creaking.getY() + 0.5 * scale`, `yMid = (creaking.getEyeY() + creaking.getY()) / 2.0` (all double arithmetic; the tolerance 0.5, the distance bound 144.0 and the line-of-sight bound 128.0 are double constants): if `A` return **false** (stay frozen, no distance limit other than the 128 of the line-of-sight test); else if `P.distanceToSqr(creaking) < 144` (3D, position to position, 12 blocks) call `activate(P)` and return **false**; else go on with the next player.
3. If `found` is false and `A`: `deactivate()`. Return **true**.
`activate(P)`: set memory `attack_target` to `P`, game event `entity_action`, sound `creaking_activate`, `IS_ACTIVE` true. `deactivate()`: erase `attack_target`, game event `entity_action`, sound `creaking_deactivate`, `IS_ACTIVE` false.
Consequences: (a) activation needs the player within 12 blocks **and** looking; after activation any player who looks at it from up to 128 blocks keeps it frozen; (b) it deactivates only when no attackable, non-allied player is in `L` at all (a player in `L` that does not look leaves it active and mobile); (c) because `L` is refreshed only every 20 ticks (17.2) a player who has just come within range or just left is acted on late.

#### 17.1.1 `isLookingAtMe(viewer, tolerance, scaleByDistance, visualObstruction, yValues)` (`LivingEntity`)

Receiver `R` = the entity the method is called on (the creaking); `viewer` = the player. Let `V = normalize(viewer.getViewVector(1.0))`. `Entity.getViewVector(1.0)` is final: it calls the virtual `getViewXRot(1.0)` and `getViewYRot(1.0)` and then `calculateViewVector(pitch, yaw)`. `getViewXRot(1.0)` is the viewer's `xRot`; `LivingEntity.getViewYRot(1.0)` is **`yHeadRot`**, not `yRot` (for another partial tick it is `Mth.rotLerp(partial, yHeadRotO, yHeadRot)`). For a player, `Player.aiStep` sets `yHeadRot = getYRot()` at its very end (read: right after the `Avatar.aiStep` call) and `ServerPlayer` assigns the head rotation only in the relative-teleport path (`teleportTo`), so on the server the yaw seen by the creaking test is the player's yaw as copied at the end of that player's last `aiStep`: a yaw change that arrived in a movement packet reaches the test only after the player's next `aiStep`, which can be one tick late depending on whether the level ticks the creaking before or after that player (the entity tick order was not traced). With the floats `a = pitch * 0.017453292f` and `b = -yaw * 0.017453292f` (0.017453292f = 0.01745329238474369) the vector is `(Mth.sin(b) * Mth.cos(a), -Mth.sin(a), Mth.cos(b) * Mth.cos(a))`, where `Mth.sin` and `Mth.cos` are the lookup-table functions of 10 §16.3 called with the float argument widened to double and returning floats, and the products are **float products** widened to double only when the `Vec3` is built (this form has **no offset by pi**; the pi offset belongs to `Vec3.directionFromRotation`, 16.5). For example `yHeadRot` -90 (facing +x), pitch 0 gives approximately `(1, 0, 0)`. The rest of the test below (the offsets, the length, the normalisation, the dot product and the comparison) is in double precision. For each `y` of `yValues` **in the given order**:
1. `w = (R.x - viewer.x, y - viewer.eyeY, R.z - viewer.z)`, `len = |w|`, `u = w / len`.
2. Angle test: `dot(V, u) > 1 - tolerance / D`, with `D = len` when `scaleByDistance` is true and `D = 1` otherwise. For the creaking `tolerance = 0.5` and `scaleByDistance` is false, so the test is **`dot > 0.5`, a cone of half-angle 60 degrees (120 degrees wide) around the view direction, at every distance**.
3. If the angle test passes: `viewer.hasLineOfSight(R, shape source, no fluids, y)` (the block ray is specified in 17.1.2): false when the two entities are in different levels or when the straight distance between the points `(viewer.x, viewer.eyeY, viewer.z)` and `(R.x, y, R.z)` is **greater than 128**; otherwise a block ray from the first point to the second is cast with the shape source selected by `visualObstruction`: **VISUAL** (`BlockStateBase.getVisualShape`) when true, COLLIDER (`getCollisionShape`) when false; fluids are ignored; the test passes when the result is a miss. Entities never block it (including the creaking's own body: the ray ends on its axis line at the height `y`).
4. The first `y` for which both tests pass makes the result **true**; if none does the result is false.
**Visual shapes** (what blocks the VISUAL ray): by default the same as the collision shape; the exceptions read in `BlockBehaviour` and the block classes that override `getVisualShape`: the `TransparentBlock` family (`TransparentBlock` itself, used for plain glass, and its subclasses `StainedGlassBlock`, `TintedGlassBlock` and `WaterloggedTransparentBlock`) returns the **empty** shape (`HalfTransparentBlock`, its superclass, does not); `IronBarsBlock` (iron bars, glass panes, and the subclasses `StainedGlassPaneBlock` and `WeatheringCopperBarsBlock`, which inherit it without overriding `getVisualShape`; the waxed copper bars are built by a lambda that returns `IronBarsBlock`, so they are plain `IronBarsBlock`) returns empty; `PowderSnowBlock` returns empty; `FenceBlock` returns its **outline** shape (`getShape`) instead of the 1.5-high collision shape; `SoulSandBlock` and `MudBlock` return the **full block** instead of their lowered collision shape; `SnowLayerBlock` returns the shape of its layer count (`SHAPES[layers]`). Everything else, including leaves, blocks the ray if its collision shape is hit.
Worked example: the viewer's eyes at `(0.5, 65.62, 0.5)` with `xRot` 0 and `yHeadRot` -90 (looking along +x); a creaking of scale 1 stands at `(10.5, 64, 0.5)` (eye `y = 64 + 2.3 = 66.3`): the sample heights are `yEye = 66.3`, `yBody = 64.5`, `yMid = 65.15`. For `yEye`: `w = (10, 0.68, 0)`, `len = 10.023`, `dot = 10 / 10.023 = 0.9977 > 0.5` and a clear line gives **true**. If the viewer instead looks along +z, `dot = 0` for every sample and the result is false; looking 59 degrees away from the creaking (`dot = 0.515`) is still true and 61 degrees (`dot = 0.485`) is false (horizontal angles, same height). A pane of glass between them does not block the ray (empty visual shape); a stone block in the line blocks a sample unless the ray passes over it (the three samples are at different heights, so a low obstacle can hide some of them and not others).

#### 17.1.2 The block ray `Level.clip` (read in `BlockGetter.clip`, `BlockGetter.traverseBlocks`, `VoxelShape.clip`, `AABB.clip`, `AABB.getDirection`, `AABB.clipPoint`, `ClipContext`; no other document specifies it)

`clip(context)` walks the cells of the segment from `from` to `to` (the original, unadjusted endpoints held by the context) and returns the result of the first cell that yields a hit, or a MISS.
- **Walk** (`BlockGetter.traverseBlocks(from, to, context, perCell, onMiss)`):
  1. When `from` equals `to` (`Vec3.equals`), `onMiss(context)` is returned at once.
  2. The adjusted segment: `s = from - 1.0E-7 * (to - from)` and `e = to + 1.0E-7 * (to - from)` per axis (`Mth.lerp(-1.0E-7, from, to)` and `Mth.lerp(-1.0E-7, to, from)`): both endpoints are moved **outward** by 1e-7 of the segment. `d = e - s`.
  3. The start cell is `floor(s)` on each axis and `perCell(context, cell)` is evaluated for it first; a non-null result ends the walk.
  4. Per axis with `sign` = `Mth.sign(d)` (-1, 0 or 1): the step parameter is `1 / |d|` (`sign / d`) when the sign is not 0, and the largest double (1.7976931348623157E308) when it is 0. The parameter of the first crossing is `step * (1 - frac(s))` for a positive component and `step * frac(s)` otherwise, with `frac(x) = x - floor(x)`. So a **zero component whose start coordinate is an exact integer gives the first-crossing parameter 0** (the largest double times 0).
  5. Loop while at least one of the three crossing parameters `tx`, `ty`, `tz` is `<= 1` (a crossing exactly at 1 is still taken; the walk ends when all three are above 1): choose the axis **x only if `tx < ty` and `tx < tz`** (both strict); **otherwise y if `ty < tz`** (which, once x was not chosen, means `ty <= tx` and `ty < tz`); **otherwise z**. Ties therefore prefer z, then y, then x: `x == y` goes to y when `y < z` and to z otherwise, `x == z`, `y == z` and all-equal go to z. The chosen cell coordinate moves by the axis sign, that axis's parameter increases by its step, and `perCell` is evaluated for the new cell; a non-null result ends the walk. (With the zero-component quirk of step 4 the chosen axis may have sign 0: the cell does not change, so **the same cell, normally the start cell, is evaluated a second time**, and that axis parameter then jumps to the largest double.)
  6. When the loop ends, `onMiss(context)` is returned.
- **`perCell`** (`lambda$clip$0`) uses the context's **original** `from` and `to`, not the adjusted ones: the block state and fluid state at the cell are read; the block shape is the one chosen by the context's shape source (COLLIDER, OUTLINE, VISUAL or FALLDAMAGE_RESETTING, 33 §8.2 for the last; the getter receives the entity collision context of the viewer) and is clipped by `VoxelShape.clip(from, to, pos)` (below); when that gives a hit, the block's **interaction shape** is clipped the same way and if its hit is nearer (smaller squared distance from `from`) the result takes the interaction hit's face direction (`clipWithInteractionOverride`; the point stays the block shape's point). The fluid shape (the shape of the fluid state when the context's fluid mode selects it; mode NONE gives the empty shape, so fluids never hit for the line-of-sight tests) is clipped the same way. The result is the block hit or the fluid hit, whichever has the smaller squared distance from `from`; **the block hit when the two distances are equal**; null when neither exists.
- **`onMiss`** (`lambda$clip$1`): a MISS result located at `to` (original), direction `Direction.getApproximateNearest(from - to)` (the vector from `to` towards `from`), block position `BlockPos.containing(to)`. The result type of the miss is MISS; every hit has type BLOCK.
- **`VoxelShape.clip(from, to, pos)`** (positions are world coordinates, the shape is in cell-local coordinates):
  1. An empty shape gives no hit.
  2. `delta = to - from`; when `|delta|^2 < 1.0E-7` there is no hit.
  3. **Start-inside rule**: the probe point `p = from + 0.001 * delta`. For each axis the index of the discrete voxel containing `p - pos` is found by `findIndex(axis, coordinate)`: a half-open binary search `[0, size + 1)` over the `size + 1` boundary coordinates with indices 0 to `size`, for the first index `i` whose boundary coordinate is **greater than** the coordinate, returning `size + 1` when none is greater, then minus 1 (so the results run from -1, below the shape, to `size`, above it; `Mth.binarySearch` is the lower bound of Open question 35). When `DiscreteVoxelShape.isFullWide(ix, iy, iz)` holds (each index in `0 .. size - 1` and the voxel filled) the result is an immediate hit at **`p`** (not at `from`), face `getOpposite(getApproximateNearest(delta))`, block position `pos`, `inside = true`.
  4. Otherwise `AABB.clip(boxes, from, to, pos)` over the shape's boxes (`toAabbs()`, cell-local, each moved by `pos`).
- **`AABB.clip(boxes, from, to, pos)`**: `t = 1.0` (a one-element array), `face = null`, `delta = to - from`. Every box, moved by `pos`, is given to `getDirection`, which may lower `t` and set `face`. When no box set a face the result is null. Otherwise the hit point is `from + t * delta` (each component `from + t * delta_c`), the face is `face`, `inside = false`.
- **`AABB.getDirection(box, from, t[], face, dx, dy, dz)`**: for each axis in the order x, y, z, only the face that looks towards `from` is tried, and only when the segment moves across that axis by more than 1e-7: x with `dx > 1.0E-7` the face at `minX` (direction WEST), x with `dx < -1.0E-7` the face at `maxX` (EAST); y with `dy > 1.0E-7` the face at `minY` (DOWN), `dy < -1.0E-7` the face at `maxY` (UP); z with `dz > 1.0E-7` the face at `minZ` (NORTH), `dz < -1.0E-7` the face at `maxZ` (SOUTH). A zero or tiny component skips its axis; back faces are never tried.
- **`AABB.clipPoint(t[], face, da, db, dc, faceCoord, lo1, hi1, lo2, hi2, faceDir, fromA, fromB, fromC)`** for one face (`a` is the axis of the face, `b` and `c` the other two axes in the cyclic orders (y, z) for x, (z, x) for y, (x, y) for z; `lo1/hi1` is the range on axis `b`, `lo2/hi2` on axis `c`): `u = (faceCoord - fromA) / da`; `pb = fromB + u * db`; `pc = fromC + u * dc`. The face is accepted when **`0 < u`** and **`u < t[0]`** (strict: a face the segment starts on, `u = 0`, is not hit, and an equal `u` does not replace an earlier face) and **`lo1 - 1.0E-7 < pb < hi1 + 1.0E-7`** and **`lo2 - 1.0E-7 < pc < hi2 + 1.0E-7`** (strict, rectangle widened by 1e-7 on each side); on acceptance `t[0] = u` and `faceDir` is returned, else the incoming `face` is returned unchanged. All of this is double arithmetic. The first box (in the order of `toAabbs`) and the first axis in the order x, y, z win equal `u` values.
Worked example: a segment from `(0.5, 65.62, 0.5)` to `(10.5, 66.3, 0.5)` against a full stone block at cell `(5, 65, 0)`: the cell walk reaches the cell when the x crossing passes 5.0; `VoxelShape.clip` finds `p` outside the block, so the box clip runs: only x has `dx = 10 > 1e-7`, the face is `minX` = 5.0, `u = (5.0 - 0.5) / 10 = 0.45` (about 0.45 of the segment), the point on the face has `y` = 65.62 + 0.45 * 0.68 = 65.926 inside `[65, 66]` and `z` = 0.5 inside `[0, 1]`, so the hit is at `(5.0, 65.926, 0.5)` with face WEST and the line of sight is blocked.

### 17.2 The nearest-player list (resolved; `PlayerSensor`, `Sensor`, `Brain`)

The creaking brain has the sensors `NEAREST_LIVING_ENTITIES` and `NEAREST_PLAYERS` (the `PlayerSensor` class; its other three memories, `nearest_visible_player` and the two attackable-player memories, are written too and are not used by `checkCanMove`). `Sensor.tick` runs its scan when an internal countdown reaches 0 or less and then resets it to the scan rate **20** (the default constructor; the creaking's sensor type does not override it), and the countdown is started at a random integer from 0 to 19 when the brain is created (`randomlyDelayStart`). So the list is refreshed once every 20 ticks, at an offset that differs per creaking. One scan: take every player of the server level (`ServerLevel.players()`), keep those that are not spectators (`EntitySelector.NO_SPECTATORS`) and are within the creaking's **follow range** (attribute, 32 for the creaking) by `closerThan(player, range)` (3D squared distance below `range^2`), sort ascending by squared distance to the creaking, and store the list in `nearest_players` (an empty result leaves the memory empty or absent; `checkCanMove` treats both as an empty list). Creative players **are** in the list (they are removed later by `canAttack`, 17.1). The brain tick runs after `checkCanMove` in a tick (`aiStep` before `customServerAiStep`), so `checkCanMove` always uses the list stored by the previous scan, which can be up to 20 ticks old.

### 17.3 `gameplay/creaking_active` values (resolved; `data/minecraft/timeline/day.json`; the timeline system is in 33 and 12 §3.2)

Attribute type boolean, default false (23 §8). The timeline `day` (clock `overworld`, `period_ticks` 24000) has the track `minecraft:gameplay/creaking_active` with modifier `or` and two keyframes: `(ticks 12600, value true)` and `(ticks 23401, value false)`. Boolean tracks are step functions (the earlier keyframe's value is held until the next keyframe tick, 33), cyclic over the period, and the modifier `or` combines the sampled value with the running value (default false). The track is sampled at the integer game tick of the overworld clock modulo 24000, so the attribute is **true for time-of-day ticks 12600 to 23400 inclusive (10801 ticks) and false for 23401 to 24000 (that is 0) and 0 to 12599** (13199 ticks). The `day` timeline belongs to the tag `in_overworld`; no other timeline, dimension type or biome file in the jar sets the attribute (all `timeline`, `dimension_type` and `worldgen/biome` JSON were searched), so in the Nether and the End it stays at its default false. Examples: time 12599 false; 12600 true (the night marker `night` is at 13000, `midnight` 18000); 23400 true; 23401 false. The only readers are the creaking heart block and block entity (31-block-entities-5, 44-5 §8): they set the heart to AWAKE at the first state update after the attribute becomes true and to DORMANT after it becomes false, and the block entity removes a protector that does not require persistence once the attribute is false. The value does not depend on weather or on the sky light.

### 17.4 Heart binding: a worked case (derived from 44-5 §8 and 17; Overworld, Normal difficulty)

Set-up: a creaking heart at `H = (100, 64, 100)` whose two neighbours along its axis are pale oak logs with the same axis (`hasRequiredLogs`), no link, state AWAKE or UPROOTED-free; a survival player `P` stands 20 blocks away; the time of day is 14000 (attribute true).
1. **Ticker.** The heart's server tick runs the state body every 22 to 26 ticks (44-5 §8 step 3). At the first body run after the heart was placed: state update: attribute true and logs present give AWAKE.
2. **Spawn.** The same body run, with no link and state AWAKE: monsters allowed and difficulty not Peaceful, and a non-spectator player within 32 blocks of `H` (here `P` at 20, creative players count) pass, so `spawnProtector` runs `SpawnUtil.trySpawnMob(creaking, SPAWNER, level, H, 5 attempts, 16 horizontal, 8 vertical, ON_TOP_OF_COLLIDER_NO_LEAVES, true)`: up to 5 random positions within +-16 in x and z and +-8 in y of `H`, the first on top of a collider that is not leaves where the creaking fits. On success: entity event 60 and game event `entity_place`, the creaking is transient with home `H` (`home_pos` set), the heart stores the link, the creaking's spawn sound and the heart's `creaking_heart_spawn` (volume 1, pitch 1) play. If all five positions fail, nothing is spawned and the next body run (22 to 26 ticks later) tries again.
3. **Binding effects** (17 above): the creaking cannot use portals; if `H` no longer lists it as protector its `tick` sets its health to 0; its path evaluator treats positions farther than 32 blocks from `H` as blocked; its health is 1.0 and a hit on it is redirected through the heart (`creakingHurt`: 20 particle bursts, 2 or 3 resin spreads while the heart is AWAKE, then the 100-tick hurt effect).
4. **Fighting.** When `P` looks at it from under 12 blocks it activates and stays frozen while any non-disguised player looks at it (17.1); when nobody looks at it, the FIGHT activity walks to `P` at speed modifier 1.0 on the speed attribute 0.4 and attacks with cooldown 40 ticks and 3.0 damage (scaled by difficulty for players, 3.1).
5. **Release.** At time of day 23401 the attribute becomes false. The first body run after that sets the heart to DORMANT (step 4) and, because a link exists, the protector does not require persistence and the attribute is false, removes it with `removeProtector(null)` (`tearDown`: the 45-tick teardown with `IS_TEARING_DOWN`, then the creaking is removed). The same removal happens earlier when the creaking is more than 34 blocks from `H`, or when it reports that a player is stuck in it. The delay between the attribute change and the removal is therefore 0 to 26 ticks plus the body-run phase (at most `R + 2` = 26 ticks).
6. **Respawn.** With the link cleared and the heart DORMANT no creaking is spawned; at the next day-to-night change (time of day 12600) the heart becomes AWAKE at its next body run and step 2 repeats.

### 19.4 Despawning

`Mob.checkDespawn` (18 framework: despawning): in Peaceful, a type that is not allowed in Peaceful is discarded at each check. The types built with `notInPeaceful` (read from the builders) are: blaze, bogged, breeze, cave spider, creaking, creeper, drowned, elder guardian, enderman, endermite, evoker, ghast, giant, guardian, hoglin, husk, illusioner, magma cube, parched, phantom, piglin brute, pillager, ravager, silverfish, skeleton, slime, spider, stray, vex, vindicator, warden, witch, wither, wither skeleton, zoglin, zombie, zombie villager, zombified piglin; `sulfur_cube`, `zombie_horse`, `zombie_nautilus` and `camel_husk` are not on the list. Otherwise, when a player exists, with the nearest player at distance `d`: for a mob that is not persistent and does not require custom persistence: if `d^2 > 128^2` (the monster category's despawn distance) and `removeWhenFarAway` is true it is discarded (the check then continues); then, if its no-action counter is above 600, `nextInt(800) == 0` is drawn (only for such non-persistent mobs, whenever the counter exceeds 600 and before the distance test) and if it succeeds and `d^2 > 32^2` (the no-despawn distance) and `removeWhenFarAway`, it is discarded; and for every mob (persistent ones included) when `d^2 < 32^2` the counter is reset to 0. Overridden `removeWhenFarAway`: Warden false; zombie villager false while converting; raiders with a raid false; a patrolling `PatrollingMonster` true only beyond 128 blocks (16384 squared); `requiresCustomPersistence` adds carrying-block endermen, raiders with a raid, converting mobs and body-item sulfur cubes.

## 20. Worked examples

### 20.1 Creeper blast damage to a player

Creeper (power 3, not charged): `2R = 6`. Player on Normal at 2 blocks (feet to center), fully exposed (`seen = 1`): `dist = 2 / 6 = 0.3333`, `s = 0.6667`, damage `= (0.6667^2 + 0.6667) / 2 * 7 * 6 + 1 = 24.33`; scaled by difficulty (3.1): Easy 13.17, Normal 24.33, Hard 36.5 (before armor). Knockback strength `0.6667 * 1 * (1 - 0) = 0.6667` along the direction from the center to the player's eye.
Other distances (exposure 1, Normal): 0 blocks 43.0; 1 block 33.08; 3 blocks 16.75; 5 blocks 5.083 (strength 0.1667); 6 blocks 1.0 (strength 0); beyond 6 blocks nothing.
Charged creeper (power 6, `2R = 12`) at 2 blocks: `dist = 0.1667`, `s = 0.8333`, damage `65.17` (Easy 33.58, Hard 97.75); at 6 blocks: 32.5 (strength 0.5); the radius reaches 12 blocks.
Exposure: a player half behind a wall with `seen = 0.5` at 2 blocks from a normal creeper: `s = 0.3333`, damage `(0.1111 + 0.3333)/2 * 42 + 1 = 10.33`.

### 20.2 Slime splitting

A natural slime is size 1, 2 or 4. Size 4: 16 health, speed 0.6, attack damage 4, XP 4. On death it spawns 2 to 4 size-2 slimes (each: health 4, speed 0.4, attack 2, XP 2); each size-2 slime on death spawns 2 to 4 size-1 slimes (health 1, speed 0.3, attack-damage attribute 1 but it deals no contact damage because tiny slimes cannot deal damage, XP 1; the only ones that drop slime balls, `U(0..2)` + looting). Minimum total descendants (counting all spawned): 2 + 2*2 = 6; maximum 4 + 4*4 = 20 (16 size-1 slimes at the end). Child `i` offsets: with parent width `w` (size 4 -> 2.08) and `w/2 = 1.04`: children at `((i % 2) - 0.5) * 1.04` in x and `((i / 2) - 0.5) * 1.04` in z: `(-0.52, -0.52)`, `(+0.52, -0.52)`, `(-0.52, +0.52)`, `(+0.52, +0.52)` for i = 0 to 3, y + 0.5. Spawn-size probabilities: with special multiplier 0 (effective difficulty below 2): size 1 with 1/3, 2 with 1/3, 4 with 1/3; with multiplier 1: `nextInt(3)` of 0 or 1 is bumped with probability 0.5: size 1 with probability 1/6, size 2 with 1/3, size 4 with 1/2 (the draw 0 or 1 is bumped up by one with probability 0.5 each; 2 stays).

### 20.4 Zombie reinforcement chance

A zombie spawned on Hard with effective difficulty 3 (special multiplier 0.5): base chance `nextDouble * 0.1` (mean 0.05); leader chance `0.05 * 0.5 = 0.025`: leader adds 0.5 to 0.75 chance. When a zombie is hurt on Hard: spawns reinforcements if `nextFloat < chance`; the caller's chance drops by 0.05 each time (never below the attribute minimum 0 in the read range 0 to 1: the attribute clamp is in 18 framework).

### 20.5 Phantom insomnia

A player with `time_since_rest` of 144000 ticks (2 hours) at night, effective difficulty 3 on Hard: `nextFloat * 3 < 3` almost always passes; the rest check `nextInt(144000) >= 72000` passes with probability 0.5; if it passes a group of `1 + nextInt(4)` phantoms (Hard) appears 20 to 34 blocks above, within +-10 blocks horizontally. With a rest time of 72000 or less the check can never pass.

### 20.6 Sunburn probability

A zombie at full sky light (15) at noon with sky visible: `B = 1.0`; per tick probability `(1.0 - 0.4) * 2 / 30 = 0.04`; expected ignition after 25 ticks; then the zombie burns for 8 seconds and re-ignites. At light 13 (`B = 13/15 / (4 - 3*13/15) = 0.8667 / 1.4 = 0.619`): probability `(0.619 - 0.4) * 2 / 30 = 0.0146` per tick. At light 12: `B = 0.8 / 1.6 = 0.5` which is not above 0.5: never burns.

## 21. Validation

An implementation can check itself against these cases:

1. Explosion damage table 20.1 for radii 3 and 6 at distances 0 to 6, exposure 1, all difficulties: exact to 3 decimals.
