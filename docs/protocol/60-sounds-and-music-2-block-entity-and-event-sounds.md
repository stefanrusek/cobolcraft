## 1. The block sound type

### 1.1 The class

`net.minecraft.world.level.block.SoundType` holds seven values: `volume` and `pitch` (floats) and five sound events: break, step, place, hit and fall. The class declares **131 constants** (table in §1.2; 24-1 §8.4 states the same count and lists 21 non-standard rows; this table is complete). A block has one sound type, set by `BlockBehaviour.Properties.sound(...)`; the default is `STONE`. A block state returns its block's type through `BlockState.getSoundType()`; the **only** override of the per-state lookup in the block classes is `DecoratedPotBlock`: its type is `DECORATED_POT_CRACKED` when the state property `cracked` is true, else `DECORATED_POT` (the `decorated_pot` entry of `Blocks` itself carries the default `STONE`, which is never used).

The constants `EMPTY` (all five events are `intentionally_empty`, a registered event that `sounds.json` maps to nothing) and the rows whose events are `intentionally_empty` (`CACTUS_FLOWER`, `RESIN`, `DRIED_GHAST`, `SHELF_MUSHROOM`, `RED_SHRUB`) play silence for that action (the event is looked up and skipped, 59 §2.4 item 4).

### 1.3 Constructors that override the sound of the entry

Nine block classes call `Properties.sound(...)` in their own constructor, so the sound given in the `Blocks` entry is replaced (this is why 24-3 and 24-5 call their column "effective"): `ButtonBlock`, `DoorBlock`, `TrapDoorBlock` and `BasePressurePlateBlock` (and all their subclasses: pressure plates, weighted plates, the weathering copper doors and trapdoors) take **`BlockSetType.soundType()`**; `FenceGateBlock`, `StandingSignBlock` and `WallSignBlock` take **`WoodType.soundType()`**; `CeilingHangingSignBlock` and `WallHangingSignBlock` take **`WoodType.hangingSignSoundType()`**. The values:

## 2. Block sound events a level or an item plays (rules)

### 2.1 Placing a block (`BlockItem.place`)

After the block state is set (`placeBlock`) and, when the block at the clicked position is the placed block, the item's block-state tag and block entity data are applied, `setPlacedBy` is called and the advancement trigger (`placed_block`, server players only) is fired, the item reads the **state at the clicked position** (after the tag update) and plays `level.playSound(player, pos, getPlaceSound(state), BLOCKS, (v + 1) / 2, p x 0.8)` where `v` and `p` are the volume and pitch of `state.getSoundType()`; the position overload of `Level.playSound` plays at **(x + 0.5, y + 0.5, z + 0.5)** of the block position. The place event comes from **`BlockItem.getPlaceSound(state)`**, a protected method subclasses may override: it returns `getSoundType().getPlaceSound()`; **`SolidBucketItem.getPlaceSound` returns its own stored `placeSound` field** instead of the sound type's place event. The only `SolidBucketItem` in the jar is the powder snow bucket (`Items` builds it with the powder snow block and the event `item.bucket.empty_powder_snow`), so placing powder snow plays `item.bucket.empty_powder_snow` with volume `(1.0 + 1) / 2 = 1.0` and pitch `1.0 x 0.8 = 0.8` (the powder snow type's volume and pitch). The excluded entity is the placing player: the server sends the Sound packet to the other players only (the client of the placer plays its own prediction because the same code runs there, 59 §2.2). The game event `block_place` follows, then the stack is reduced by one.

**Bucket path.** `SolidBucketItem.emptyContents` (the `DispensibleContainerItem` method; the dispenser behaviour `DispenseItemBehavior$3` calls it with a null entity and a null hit result) acts only when the position is inside the world and the block there is air (otherwise it returns false and plays nothing): on a server it sets the block (`defaultBlockState`), then emits the game event `fluid_place` and plays the stored `placeSound` (`item.bucket.empty_powder_snow`) through `Level.playSound(entity, pos, ...)` with BLOCKS, **volume 1.0 and pitch 1.0**, at (x + 0.5, y + 0.5, z + 0.5) (no excluded entity for the dispenser). Which dispenser registrations use that behaviour was not read.

### 2.2 Breaking a block (level event 2001)

The client handler for level event **2001** (`LevelEventHandler`; event data = the block state id of the destroyed state, `Block.stateById`) plays **no sound when the state is air**; otherwise it plays `playLocalSound(pos, breakSound, BLOCKS, (v + 1) / 2, p x 0.8, distanceDelay = false)` for the break event, volume and pitch of the destroyed state's sound type, at **(x + 0.5, y + 0.5, z + 0.5)** of the block position (the `BlockPos` overload of `Level.playLocalSound` adds 0.5 on each axis). The destroy-particle call follows in both cases (whether it filters air itself was not read). The decoration sounds of special blocks (decorated pot shatter, which is the `DECORATED_POT_CRACKED` type's break event) work through the same rule. Event **3008** (brush completed) plays the block's `getBrushCompletedSound()` instead (source PLAYERS, volume 1, pitch 1).

### 2.3 Hitting a block while mining

The hit sound (`SoundType.getHitSound()`) is played by `ClientLevel.addBreakingBlockEffects(pos, direction, playSound)`: nothing happens when the block at `pos` is air; when `playSound` is true it plays, through the sound manager, a `SimpleSoundInstance(hitSound, BLOCKS, (v + 1) / 8, p x 0.5, an unseeded random, pos)` (fixed position **(x + 0.5, y + 0.5, z + 0.5)** of the block position, set by the `BlockPos` constructor of `SimpleSoundInstance`; LINEAR attenuation; `v` and `p` are the volume and pitch of the block's sound type); then, unless the state's render shape is INVISIBLE or it does not spawn terrain particles, the breaking particles are added. A block type whose hit event is `intentionally_empty` is silent.

Exactly two kinds of caller pass `playSound` (scan of the jar for the method name: `MultiPlayerGameMode`, `LevelEventHandler` and `ClientLevel` itself):

1. The lambda that `MultiPlayerGameMode.startDestroyBlock` builds passes **true**: the digger's own client plays the hit sound **once, at once, when the dig starts** (the same lambda sends the start packet). `continueDestroyBlock` has no call to the sound manager or to this method.
2. **Level events 2019 and 2020** (`LevelEventHandler`, one shared case body): the direction is `Direction.values()[clamp(data, 0, length - 1)]` and the call is `addBreakingBlockEffects(pos, direction, playSound = (id == 2020))`: the hit sound plays for **2020**, and 2019 adds the particles only.

**The hit sound repeats while mining.** `ServerPlayerGameMode.tick` (once per server tick) increments `gameTicks` **first**; then, while a block is being dug (`isDestroyingBlock`, tested only when no delayed destroy is pending: the delayed-destroy branch comes first and sends no event; if the dug position has become air the dig is cancelled instead: a destroy-progress packet with stage -1 is sent), it computes `n = gameTicks - destroyProgressStart` (`destroyProgressStart` was set to `gameTicks` when the dig started), picks the id **2020 when `n` is divisible by 4, else 2019**, updates the break progress, and calls `ServerLevel.levelEvent(null, id, destroyPos, destroyDirection.ordinal())`. That call sends a Level Event packet (05b) to **every player of the dimension whose squared distance from the block position (its integer coordinates, no 0.5 offset) is less than 64 x 64, with no excluded player**: the digger receives it too. So one event arrives per tick while digging; **the first 2020 comes 4 ticks after the dig starts** (`n` is 1 on the first tick after the start, because the counter is incremented before the modulo test) and then every 4 ticks (0.2 s): the digger hears the hit sound at tick 0 (the client-side start sound above) and again at ticks 4, 8, 12, ...; other players within 64 blocks hear it at ticks 4, 8, 12, ... only, because the start sound is local. The 2001 handler (block break) does not call this method: it calls `addDestroyBlockEffect` (particles only, 2.2).

**Sniffer digging (the other user of a hit sound).** `Sniffer.tick` calls `emitDiggingParticles` (and `dropSeed`) in the state `DIGGING` (ordinal 5 of `Sniffer$State`: IDLING 0, FEELING_HAPPY 1, SCENTING 2, SNIFFING 3, SEARCHING 4, DIGGING 5, RISING 6) and `playSearchingSound` in the state `SEARCHING`. `emitDiggingParticles` acts only while the dig animation time `(tickCount - startTick) x 50` ms is strictly between 1700 and 6000 (animation ticks 35 to 119), with the block state below the sniffer's head block (`getHeadBlock().below()`) and only when that state's render shape is not INVISIBLE: it adds 30 `block` particles at the head block centre with y offset -0.65 and no velocity, and when `tickCount` mod 10 is 0 it plays the **hit event** of that state's sound type through `Level.playLocalSound(entity, event, the sniffer's sound source, 0.5, 0.5)`: the volume and pitch are the constants 0.5 and 0.5, **not** scaled by the type's volume and pitch. That overload does nothing in `Level`; on a client (`ClientLevel`) it starts an entity-bound sound instance that follows the sniffer, with the seed `nextLong` of the client level random. `playSearchingSound` runs on the client only, when `tickCount` mod 20 is 0, and plays `entity.sniffer.searching` at volume 1.0 and pitch 1.0 through the same overload.

### 2.4 Walking: step sounds (`Entity.move` and its helpers)

After the collision step, `Entity.move` (when the entity was not removed) calls `applyMovementEmissionAndPlaySound(emission, delta, legacyPos, legacyState)` when all three hold: the level is not the client's, or `isLocalInstanceAuthoritative()` holds (the test is not evaluated on a server level: the server simulates every entity; on a client level it is `isLocalClientAuthoritative`: for an `Entity` it is true when the controlling passenger is itself locally client-authoritative, for a `Player` it is `isLocalPlayer`, true only for the local player's own entity; so a client also makes the step sounds of a mount or vehicle that the local player controls, and of no other entity); the movement emission (`getMovementEmission()`) emits anything; and `isPassenger()` is false (a rider makes no step sounds). `delta` is the movement the move actually applied after collisions (the vector `collide` returned); `legacyPos` = `getOnPosLegacy()` = `getOnPos(0.2)` and `legacyState` is its state.

**Movement emission** (read in all 18 classes that define `getMovementEmission`). The enum has four values: `NONE` emits neither sounds nor game events, `SOUNDS` sounds only, `EVENTS` game events only, `ALL` both; no class returns `SOUNDS`. The default (`Entity`) is `ALL`. **`NONE`**: experience orbs, end crystals, falling blocks, item entities, primed TNT, shulkers, fishing hooks and arrows (`AbstractArrow` and its subclasses). **`EVENTS`** (no step sound, but the `step` and `swim` game events): bats, squids (glow squids inherit), endermites, guardians (elder guardians inherit), silverfish, breezes, boats (`AbstractBoat`) and minecarts (`AbstractMinecart`). **The player** (`Player.getMovementEmission`): `NONE` when `abilities.flying`, or when `onGround()` and `isDiscrete()`; `ALL` otherwise; `isDiscrete()` is `isShiftKeyDown()` (`Entity`; the player classes do not override it). So a sneaking player on the ground makes no step sound and no game event, and a sneaking player in the air does.

Per move:

1. `walk = (float)(|delta| x 0.6000000238418579)` (the 3-D length) and `hwalk = (float)(horizontal length of delta x 0.6000000238418579)`; the constant is the float 0.6 widened to double.
2. `onPos = getOnPos()` (= `getOnPos(1.0E-5)`) and `state` = the block state there. `getOnPos(h)` (`h` a float) is: when a main supporting block position is known, then if `h <= 1.0E-5` that position; if `h > 1.0E-5` that position is kept when **any** of these holds for its state: (`h <= 0.5` and the state is in the tag `fences`); the state is in the tag `walls`; the block is a `FenceGateBlock` (only the fence test depends on `h`); when none holds the answer is that position with its y replaced by `floor(feetY - h)`. When no supporting block is known: `(floor(x), floor(y - h), floor(z))` of the entity position. `climbing = isStateClimbable(state)` = the state is in the tag `climbable` (ladder, vine, scaffolding, weeping vines and their plant, twisting vines and their plant, cave vines and their plant) **or** is powder snow.
3. `moveDist = moveDist + (climbing ? walk : hwalk)` and `flyDist = flyDist + walk` (floats). `moveDist` starts at 0 and `nextStep` is initialised to the constant **1.0** by the constructor.
4. If `moveDist > nextStep` **and** `state` is not air: `same` = (`onPos` equals `legacyPos`). Run the block effect routine (step 5) for `legacyPos` and `legacyState` with sounds enabled iff the emission emits sounds and the game event enabled iff `same`. If not `same`, run it a second time for `onPos` and `state` with sounds **disabled** and the game event enabled iff the emission emits events, and or the two results. If the result is true: `nextStep = (float)((int) moveDist + 1)` (`nextStep()`). Otherwise, if the entity is in water (`isInWater`): `nextStep` is set the same way, the swim sound plays if the emission emits sounds (`waterSwimSound`, 2.6), and the game event `swim` fires if it emits events.
   If the test of this step fails and `state` is air, `processFlappingMovement` runs (so the flapping branch runs on every move whose on-state is air, whatever `moveDist` is). If `state` is not air and `moveDist <= nextStep`, nothing happens.
   `processFlappingMovement`: when `isFlapping()` is true, `onFlap()` runs and then, when the emission emits events, the game event `flap` fires. The defaults are `isFlapping` false and an empty `onFlap`. `isFlapping` is overridden by eight classes: `Bat` (not resting and `tickCount` mod 10.0 is 0), `Allay` (not on the ground), `Bee` (flying and `tickCount` mod 2 is 0; the period `TICKS_PER_FLAP` is `ceil(1.4959966)` = 2), `Chicken` and `Parrot` (`flyDist` greater than the field `nextFlap`), `EnderDragon` (the cosine of 2 pi x `flapTime` is at least -0.3 while the cosine of 2 pi x `oFlapTime` is at most -0.3), `Phantom` (`getUniqueFlapTickOffset` + `tickCount`, mod 25, is 0; 25 is `ceil(24.166098)`) and `Vex` (`tickCount` mod 4 is 0; 4 is `ceil(3.9269907)`). Only three classes override `onFlap`: **`Parrot`** plays `entity.parrot.fly` at volume 0.15 and pitch 1.0 through `Entity.playSound` and sets `nextFlap = flyDist + flapSpeed / 2`; **`Chicken`** only sets `nextFlap = flyDist + flapSpeed / 2` (no sound); **`EnderDragon`** plays `entity.ender_dragon.flap` on the client only and not when silent, through `Level.playLocalSound(x, y, z, event, its sound source, volume 5.0, pitch 0.8 + 0.3 x nextFloat(), distanceDelay false)` (one draw of the dragon's random). `flapSpeed` is a field of Parrot and Chicken that was not read.
5. The block effect routine (`vibrationAndSoundEffectsFromBlock(pos, state, sounds, events, delta)`): false at once when `state` is air. Otherwise it is true when (`onGround`, or `isStateClimbable(state)` of the state passed to the routine, or (`isCrouching` and `delta.y == 0`), or `isOnRails`) **and not** `isSwimming`; then, if `sounds`, `walkingStepSound(pos, state)` plays, and if `events` the game event `step` is emitted at the entity position with the entity and the state as context.
6. `walkingStepSound(pos, state)` calls `playStepSound(pos, state)` and then, when the state is in the tag `crystal_sound_blocks` (`amethyst_block`, `budding_amethyst`) and `tickCount >= lastCrystalSoundPlayTick + 20`, the chime of 2.5.

`Entity.playStepSound(pos, state)` plays, through `Entity.playSound` (which is silent when `isSilent()`; source = `getSoundSource()`; position = the entity's position; no excluded entity), the **step event** of the state's sound type with **volume = type volume x 0.15 and pitch = type pitch**. Overrides:

- **Player** (`Player.playStepSound`): in water (`isInWater`): `waterSwimSound()` then `playMuffledStepSound(state)`. Otherwise `p2 = getPrimaryStepSoundBlockPos(pos)`: if `p2` equals `pos` the base routine above runs for `pos` and `state`; if not, `state2` = the state at `p2`: when `state2` is in the tag `combination_step_sound_blocks` the player plays `playCombinationStepSounds(state2, state)` (the step event of `state2` at volume x 0.15 and pitch x 1, then `playMuffledStepSound(state)`); otherwise the **base routine (`Entity.playStepSound`, which `Avatar` does not override) runs with `p2` and `state2`**. `playMuffledStepSound(state)`: the state's step event, **volume x 0.05, pitch x 0.8**.
- **`getPrimaryStepSoundBlockPos(pos)`** is declared on `Entity`, not on the player class: it returns `pos.above()` when the block state at `pos.above()` is in the tag `inside_step_sound_blocks` or in the tag `combination_step_sound_blocks`, else `pos`. The tags (read from the jar): `inside_step_sound_blocks` = powder snow, sculk vein, glow lichen, lily pad, small amethyst bud, pink petals, wildflowers, leaf litter; `combination_step_sound_blocks` = the tag `wool_carpets` (the 16 coloured carpets), moss carpet, pale moss carpet, snow, nether sprouts, warped roots, crimson roots, resin clump. Example: a player walks on a carpet that lies on stone and the routine is run for the stone position: the block above it is a carpet (in `combination_step_sound_blocks`), so `p2` is the carpet position, `state2` the carpet, and the player hears the carpet's step (wool: volume 0.15, pitch 1.0) and then the stone's step muffled (volume 0.05, pitch 0.8). For a lily pad or leaf litter above (an `inside_step_sound_blocks` member that is not in the combination tag) the player hears that block's own step at the base volume 0.15 and nothing of the block below.
- Mobs with their own `playStepSound` (zombie family, pig, cow, llama, iron golem, horses, and so on): the table of §4 lists the event and the volume and pitch constants; where the column says "block" the entity uses the base routine; "silent" means the override plays nothing (allay).
- The horse family `AbstractHorse.playStepSound` has its own decision tree, given in 4.3a.

### 2.5 The crystal chime

On a step onto a state of the tag `crystal_sound_blocks` (`amethyst_block`, `budding_amethyst`) with `tickCount >= lastCrystalSoundPlayTick + 20` (the test is made in `walkingStepSound`; `crystalSoundIntensity` and `lastCrystalSoundPlayTick` both **start at 0** for a new entity, so **the first chime needs `tickCount >= 20`**): `crystalSoundIntensity = (float)(crystalSoundIntensity x 0.997^(tickCount - lastCrystalSoundPlayTick))` (`Math.pow`), then `crystalSoundIntensity = min(1.0, crystalSoundIntensity + 0.07)`; one draw `r = nextFloat()` of the entity's random; pitch `0.5 + intensity x r x 1.2`, volume `0.1 + intensity x 1.2`; `Entity.playSound(block.amethyst_block.chime, volume, pitch)`; `lastCrystalSoundPlayTick = tickCount`. The chime is played after the normal step sound. Worked example: the first chime of a fresh player (intensity 0): intensity 0.07, volume 0.1 + 0.07 x 1.2 = 0.184, pitch 0.5 + 0.084 r (0.5 to 0.584); the next chime 20 ticks later: intensity 0.07 x 0.997^20 + 0.07 = 0.1359, volume 0.263.

### 2.6 Swimming and splashing

- **Swim sound** (`waterSwimSound`, called from step 4 above and by the player in water): `controller` = the controlling passenger if any, else the entity; `k = (controller == entity) ? 0.35 : 0.4`; `speed` = the controller's delta movement `(dx, dy, dz)`; **volume = min(1.0, sqrt(0.2 x dx^2 + dy^2 + 0.2 x dz^2) x k)** (the dx and dz terms are multiplied by the double constant 0.20000000298023224, the float 0.2 widened: `dx x dx x 0.2 + dy x dy + dz x dz x 0.2`; the square root is taken in double and cast to float before it is multiplied by `k` and clamped; `k` is a float); `playSwimSound(volume)` plays `getSwimSound()` with that volume and **pitch `1.0 + (r1 - r2) x 0.4`**. Default swim event: `entity.generic.swim`; the entity table lists the overrides (player `entity.player.swim`, hostile `entity.hostile.swim`, and so on).
- **Splash** (`doWaterSplashEffect`, entering water): `controller` as above; `k = (controller == entity) ? 0.2f : 0.9f` (floats); the same speed formula with `k` gives `volume = min(1.0, ...)`; if `volume < 0.25` the sound is `getSwimSplashSound()`, else `getSwimHighSpeedSplashSound()` (defaults both `entity.generic.splash`; player `entity.player.splash` and `entity.player.splash.high_speed`); pitch `1.0 + (r1 - r2) x 0.4`; then bubble and splash particles and the game event `splash`.

### 2.7 Landing, fall damage and the voice

- **Landing** (`Entity.checkFallDamage(yDelta, onGround, state, pos)`, called from `move` with the vertical movement applied): when the entity is not in water and `yDelta < 0`, `fallDistance = fallDistance - (double)(float) yDelta` (the distance grows by the downward movement); when `onGround`: if `fallDistance > 0`, `Block.fallOn(level, state, pos, entity, fallDistance)` of the block landed on runs and the game event `hit_ground` fires (only those two are gated by "> 0"); **`fallDistance` is reset to 0 on every call with `onGround` true**, whatever its value. The default `Block.fallOn` calls `entity.causeFallDamage(fallDistance x (1 - getFallDistanceReduction()), 1.0, damage type fall)`; `getFallDistanceReduction` is the block property `fallDistanceReduction` (default 0): the `Blocks` initialiser sets 0.5 for the 16 beds (one shared properties lambda) and for `shelf_mushroom`, each together with `bounceRestitution` 0.75; `slime_block` sets only `bounceRestitution` 1.0. The seven overrides of `Block.fallOn` (all read; sounds are the entity's `playSound` unless noted):
  - `HayBlock`: `causeFallDamage(fallDistance, 0.2, fall)`.
  - `SlimeBlock`: unless `isSuppressingBounce`, `causeFallDamage(fallDistance, 0.0, fall)` (damage 0, so no fall sound); it plays nothing itself.
  - `HoneyBlock`: `block.honey_block.slide` at 1.0/1.0; on a server level the entity event 54 is broadcast to the clients; then `causeFallDamage(fallDistance, 0.2, fall)`; when that returns true (own damage above 0) the honey type's fall event plays at volume x 0.5 and pitch x 0.75 (in addition to `playBlockFallSound` inside `causeFallDamage`).
  - `PowderSnowBlock`: only when `fallDistance >= 4.0` and the entity is a `LivingEntity`: its small fall sound when `fallDistance < 7.0`, else its big one (`getFallSounds`), at 1.0/1.0; no damage and no call of the default.
  - `FarmlandBlock`: on a server level, when `nextFloat() < fallDistance - 0.5`, the entity is a `LivingEntity`, the permission holds (a player: not under spawn protection; another entity: the game rule `mob_griefing`) and width x width x height is above 0.512, `turnToBaseBlock` runs; then always the default. (Its own sounds were not read.)
  - `TurtleEggBlock`: unless the entity is a `Zombie`, `destroyEgg(..., 3)` runs; then the default. (`destroyEgg` was not read.)
  - `PointedDripstoneBlock`: with the tip direction UP and thickness TIP, `causeFallDamage(fallDistance + 2.5, 2.0, stalagmite)`; otherwise the `SpeleothemBlock` default.
- **Fall damage** (`LivingEntity.causeFallDamage(fallDistance, damageMultiplier, source)`). **A player whose `abilities.mayfly` is true takes no fall damage and plays no fall sound** (`Player.causeFallDamage` returns false at once; `GameType.updatePlayerAbilities` sets `mayfly` for creative and spectator mode and clears it for the other modes). For a living entity: `LivingEntity.causeFallDamage` first (after the impulse adjustment below) calls `Entity.causeFallDamage`, which returns at once for types of the tag `fall_damage_immune` and otherwise calls `propagateFallToPassengers`: every passenger gets `causeFallDamage` with the same distance and multiplier and so falls by its own rules (sound and damage) before the vehicle's own damage is computed; the method returns true exactly when the entity's own damage is above 0. When it is flagged to ignore fall damage from its current impulse (set by code not read), the distance used is `min(fallDistance, impulseY - y)`. `calculateFallDamage` is **0 for entity types in the tag `fall_damage_immune`** (copper golem, iron golem, snow golem, shulker, allay, bat, bee, blaze, cat, chicken, ghast, happy ghast, phantom, magma cube, ocelot, parrot, wither, breeze) and otherwise **`floor((fallDistance + 1.0E-6 - safeFallDistance) x damageMultiplier x fallDamageMultiplier)`**, with `safeFallDistance` the value of the attribute `safe_fall_distance` (default **3.0**, range -1024 to 1024) and `fallDamageMultiplier` the value of the attribute `fall_damage_multiplier` (default 1.0, range 0 to 100). The horse family's attribute supplier sets safe fall distance 6.0 and fall damage multiplier 0.5, the fox sets safe fall distance 5.0, and the Jump Boost effect adds an attribute modifier (operation ADD_VALUE, base amount 1.0) to `safe_fall_distance` (its per-level scaling is not read). When the damage is **greater than 0**, in this order: the impulse context is reset; **the fall sound** plays through `Entity.playSound` at **volume 1.0 and pitch 1.0**: the **big** sound when the damage is **greater than 4**, else the **small** one (`getFallDamageSound(damage)` over `getFallSounds()`: default `entity.generic.small_fall` and `entity.generic.big_fall`, the player `entity.player.small_fall` and `entity.player.big_fall`, other families in the entity table); then `playBlockFallSound`; then `hurt(source, damage)`. A fall with damage 0 plays **no** fall sound here. With the default attributes: a fall of 3 blocks or less does nothing; damage 1 starts at `fallDistance` 4 - 1.0E-6; the big sound starts at damage 5, that is `fallDistance` 8 - 1.0E-6. Examples: `fallDistance` 5.0 gives `floor(5.000001 - 3) = 2` (small sound); 9.0 gives `floor(6.000001) = 6` (big sound).
- **Elytra into a wall** (`LivingEntity.handleFallFlyingCollisions(speedBefore, speedAfter)`, server only, called after each fall-flying move with the horizontal speeds before and after the move): when the entity has a horizontal collision, `damage = (float)((speedBefore - speedAfter) x 10 - 3)`; when it is greater than 0 the entity plays `getFallDamageSound((int) damage)` (the same rule: big when `(int) damage` is greater than 4; volume 1.0, pitch 1.0) and is hurt by the damage type `fly_into_wall`; **no block fall sound** plays on this path.
- **`playBlockFallSound`**: not when silent; the block is the one at `(floor(x), floor(y - 0.2), floor(z))` (the 0.2 is the float widened to double); if it is not air its type's **fall** event plays with **volume = type volume x 0.5 and pitch = type pitch x 0.75**.
- **Voice**: `LivingEntity.makeSound(event)` plays the event (when not null) through `Entity.playSound` with `getSoundVolume()` (default **1.0**; overrides in the entity table, for example 0.4 for the allay, cow, wolf, slime and magma cube, 0.8 for the equines and llama) and `getVoicePitch()`: **adults `1.0 + (r1 - r2) x 0.2`, babies `1.5 + (r1 - r2) x 0.2`** (r1 and r2 two successive `nextFloat()` of the entity's own random source; the baby test is `isBaby()`). Baby mobs of some families use a separate baby sound event instead of (and as well as) the higher pitch (§4.3).
- **Hurt and death**: `LivingEntity.playHurtSound(source)` = `makeSound(getHurtSound(source))`; the defaults are `entity.generic.hurt` and `entity.generic.death`; every family overrides them (§4). The thorns hit plays a second sound (`LivingEntity.playSecondaryHurtSound`): when the damage type is `thorns`, `enchant.thorns.hit` is played at the entity's position through `Level.playSound(null, x, y, z, event, source)` (source PLAYERS for a player, else HOSTILE; the overload without volume and pitch passes **1.0 and 1.0**, read).

### 2.8 Equipping, item breaking, eating and drinking

**Equip sound** (`LivingEntity.onEquipItem(slot, oldStack, newStack)`). It is called by every write of an equipment slot of a living entity (`LivingEntity.setItemSlot`, with the stack the slot held before) and by the player menu's armour and off-hand slots (`ArmorSlot.setByPlayer`, the off-hand slot of `InventoryMenu`); skeletons add a weapon-goal refresh on the server. It does **nothing on the client and nothing for a spectator**, and it returns at once when the old and the new stack are the same item with the same components or when it is the entity's first tick (equipment set while the entity is being created is silent). Otherwise, when the entity is not silent and the new stack has the data component `equippable` **whose `slot` is the slot just written**, the server plays `Level.playSeededSound(null, x, y, z, equipSound, the entity's sound source, volume 1.0, pitch 1.0, seed)` at the entity's position: no excluded entity (the wearer hears it too) and the seed is `nextLong()` of the entity's random. The game event `equip` (the new stack has an `equippable` component) or `unequip` follows whenever `doesEmitEquipEvent(slot)` holds, whether or not the sound above played: the `LivingEntity` default returns true, and only `Player` overrides it (no other class of the jar declares the method), returning true only when the slot's type is HUMANOID_ARMOR (head, chest, legs and feet), so a player gets no equip or unequip game event for the main hand, the off hand, the body slot or the saddle slot. `equipSound` is `getEquipSound(slot, stack, equippable)`: by default the `equip_sound` member of the component (its default is `item.armor.equip_generic`, in the codec and in the builder; the registry has 12 `item.armor.equip_*` events: `chain`, `copper`, `diamond`, `elytra`, `generic`, `gold`, `iron`, `leather`, `nautilus`, `netherite`, `turtle`, `wolf`). Overrides, all for the SADDLE slot only (every other slot falls back to the superclass): `Pig` `entity.pig.saddle`, `AbstractHorse` `entity.horse.saddle`, `Camel` `entity.camel.saddle` (camel husk `entity.camel_husk.saddle`), `Strider` `entity.strider.saddle`, and `AbstractNautilus` `item.nautilus_saddle_underwater_equip` when `isUnderWater`, else `item.nautilus_saddle_equip`. Which item carries which `equip_sound` is item data that was not read (Open question 1).

**Item break sound** (`LivingEntity.breakItem`, client side). When `ItemStack.hurtAndBreak` (server) takes the last durability, the stack is copied and reduced by one, and `onEquippedItemBroken(copy, slot)` broadcasts an **entity event** for the slot (47 main hand, 48 off hand, 49 head, 50 chest, 51 legs, 52 feet, 65 body, 68 saddle) and stops the location-based effects of the item. The client handler of the event calls `breakItem` with **the client's own stack in that slot**. For a non-empty stack whose component `break_sound` is set, when the entity is not silent, it plays `Level.playLocalSound(x, y, z, sound, the entity's sound source, volume 0.8, pitch 0.8 + nextFloat() x 0.4, distanceDelay false)` at the entity's position (one draw of the entity's random), then adds 5 item particles. Every item gets the default `break_sound` **`entity.item.break`** from `DataComponents.COMMON_ITEM_COMPONENTS` (the common item component set built in the `DataComponents` initialiser, which `Item.Properties` copies into every item; `Item.Properties` itself names no default). Only two writes of the component exist in the item code (the classes of the jar that name `DataComponents.BREAK_SOUND` are `DataComponents`, `Items`, `Item.Properties` and `LivingEntity`, and no data file of the jar names `break_sound`): the shield (`Items.SHIELD`) sets **`item.shield.break`** and `Item.Properties.wolfArmor` (used by the wolf armor item) sets **`item.wolf_armor.break`**; every other item keeps the default.

**Eating and drinking** (data component `consumable`, class `Consumable`; the nutrition is the separate component `food`, `FoodProperties`). The members are `consume_seconds` (default 1.6), `animation` (default EAT, DRINK for drinks), `sound` (default `entity.generic.eat`), `has_consume_particles` (default true) and a list of on-consume effects. The ready-made constants of `Consumables`: `DEFAULT_FOOD` (1.6 s, EAT, `entity.generic.eat`, with particles), `DEFAULT_DRINK` (1.6 s, DRINK, `entity.generic.drink`, no particles), `HONEY_BOTTLE` (a drink of 2.0 s with the sound `item.honey_bottle.drink`), `DRIED_KELP` (a food of 0.8 s) and `OMINOUS_BOTTLE` (`DEFAULT_DRINK` plus the builder method `soundAfterConsume(item.ominous_bottle.dispose)`, which adds one `play_sound` on-consume effect: see On completion; the item `ominous_bottle` uses it, read in `Items`); the other constants add effects only. Which other item uses which constant is item data that was not read (Open question 1). The use time is `consumeTicks = (int)(consume_seconds x 20)` (32 for 1.6 s) and the counter of remaining use ticks starts at that value.

- **While using.** `LivingEntity.updateUsingItem` calls `ItemStack.onUseTick(level, entity, remaining)` every tick, on the client and on the server, with the counter before its decrement. The consume sound routine runs when **both** `consumeTicks - remaining > (int)(consumeTicks x 0.21875)` and `remaining mod 4 = 0` hold, with a particle count of 5. For 32 ticks the threshold is 7 and the routine runs six times, at `remaining` 24, 20, 16, 12, 8 and 4 (8, 12, 16, 20, 24 and 28 ticks after the start).
- **The routine** (`Consumable.emitParticlesAndSounds(random, entity, stack, particleCount)`). Three draws of the entity's random in this order, whatever the animation: `b = nextBoolean()`, then `r1` and `r2` (two `nextFloat()`, the `triangle(1.0, 0.2)` call), then `r3 = nextFloat()` (`Mth.randomBetween(0.9, 1.0)`). **Eating** (every animation except DRINK): volume 0.5 when `b` is true, else 1.0; pitch `1.0 + (r1 - r2) x 0.2`. **Drinking** (animation DRINK): volume 0.5, pitch `0.9 + r3 x 0.1`. When `has_consume_particles` is true the entity spawns `particleCount` item particles. The sound is the component's `sound`, except that an entity class implementing `Consumable$OverrideConsumeSound` picks it from the stack: only the wandering trader does (`entity.wandering_trader.drink_milk` for a milk bucket, else `entity.wandering_trader.drink_potion`). It is played through `LivingEntity.playSound(sound, volume, pitch)`: for a mob that is `Entity.playSound` (the entity's sound source, no excluded entity), for a player `Player.playSound`, which **excludes the player himself** on the server (the local client plays its own copy from its own use ticks, 59 §2.2).
- **On completion** (server only: the counter reaches 0; `Consumable.onConsume`), in this order: the routine again, with 16 particles (one more consume sound); the use statistic and the `consume_item` advancement trigger for a server player; every component of the stack that is a consume listener (`FoodProperties` is one): **it plays the component's `sound` once more** through `Level.playSound(null, x, y, z, sound, NEUTRAL, volume 1.0, pitch 1.0 + (r1 - r2) x 0.4)` (`triangle(1.0, 0.4)`: two `nextFloat()` of the entity's random; no excluded entity, so the eater hears it) and, **for a player only**, feeds the food data and plays `entity.player.burp` (PLAYERS, volume 0.5, pitch `0.9 + r x 0.1`, one draw, no excluded entity); then, on a server level, the on-consume effects of the consumable in list order (each `ConsumeEffect.apply(level, stack, entity)`); then the game event `drink` (animation DRINK) or `eat`; then the stack shrinks by one. The five effect types are `apply_effects`, `remove_effects`, `clear_all_effects`, `teleport_randomly` and `play_sound`; the first three name no sound event and play nothing (read: their classes name no `SoundEvents` field and call no `playSound`). **`play_sound`** (`PlaySoundConsumeEffect`, built by `soundAfterConsume`; the ominous bottle's is `item.ominous_bottle.dispose`) plays its sound once through `Level.playSound(null, the entity's block position, sound, the entity's sound source, volume 1.0, pitch 1.0)`: the position is the **centre of the block** (`blockPosition` x, y, z each plus 0.5, read in the `BlockPos` overload of `Level.playSound`), no entity is excluded (the drinker hears it) and there is no random draw. **`teleport_randomly`** (`TeleportRandomlyConsumeEffect`, the chorus fruit) plays, only after one of its up to 16 teleport attempts succeeded (25-6 has the attempts), at the entity's position after the move, `Level.playSound(null, x, y, z, event, source)` with volume 1.0 and pitch 1.0 (the overload without volume and pitch): `item.chorus_fruit.teleport` in the source PLAYERS, or `entity.fox.teleport` in the source NEUTRAL when the consumer is a fox. So a player who finishes a default food item hears, in this order, the routine's sound (volume 0.5 or 1.0), the food listener's sound (volume 1.0) and the burp (volume 0.5); the on-completion sounds of an ominous bottle are the routine's drink sound (volume 0.5, pitch `0.9 + r3 x 0.1`, played as above), then `item.ominous_bottle.dispose` (volume 1.0, pitch 1.0, at the block centre, no excluded entity), with no food-listener sound and no burp (the item has no `food` component, and its consume listener `OminousBottleAmplifier` adds the bad omen effect and plays nothing).

## 3. The player's hurt sound

**The player's hurt sound (read).** `Player.getHurtSound(source)` returns `source.type().effects().sound()`: the sound is **data-driven by the damage type registry** (the `effects` member of each `data/minecraft/damage_type/*.json`, default `hurt` when the member is absent), not a fixed event. The six `effects` values, their events and the 51 damage types are in 4.3b; the same sound plays for every hurt of the player (2.7 `playHurtSound`), with voice volume 1.0 and pitch 1.0. `Player.getDeathSound` is the constant `entity.player.death`. The thorns hit adds `enchant.thorns.hit` (2.7). The player row of the table in 4.2 refers to 4.3b.

The equip, item-break, eating and drinking sounds are in 2.8.

## 4. Entity sounds

### 4.1 Where an entity's sounds come from and the defaults

The sound of an entity action is the result of one overridable method of its class chain (`getAmbientSound`, `getHurtSound`, `getDeathSound`, `playStepSound` or `getStepSound`, and the few other methods named in the last column). The table of §4.2 shows, for **every one of the 161 registered entity types**, the value of the **most derived** definition in the class chain (the class named in the second column and its ancestors up to `LivingEntity`) **for these methods only**: the ambient, hurt, death, step, swim, splash and fall sounds and the few extras of the last column. It is **not** a list of every sound an entity class plays: the entity-class sound events outside those columns are not in it (the count is in §7), and 4.5 gives the call sites decoded so far. Reading rules:

- `-` in the ambient column: the type is not a `Mob` (the non-living entities, the armor stand, the mannequin and the player), so the ambient rule of 4.3 never runs for it. **`none`** in the ambient column: the type is a `Mob` and its `getAmbientSound` returns null for every state (the `Mob` default or an override that returns null): nothing is played and the sound makes no random draw, but the interval draw of 4.3 is still made every tick. A cell that says `no sound (null)` for a condition means the same for that case. For the hurt and death columns `-` means the type is not a living entity (arrows, items, vehicles) and makes no hurt or death sound.
- Hurt and death default: `LivingEntity` returns `entity.generic.hurt` and `entity.generic.death`; the columns show the actual value for the type.
- "baby X; adult Y": the method picks by `isBaby()`; "A / B (chosen by ...)": the method picks by the named condition (a state, water, tame, and so on); the conditions are the methods or fields the method reads, in the order read, the first sound in the list is chosen when the condition is true (`isBaby`, a water test) as written, otherwise the second; for sounds picked by data (`getSoundSet` / sound variants) see §4.4.
- Step: `block` means the base `Entity.playStepSound` of §2.4 is used; otherwise the override's event and `[volume, pitch]` constants; `silent` means the override is empty.
- The last column names further sounds: `Eating`, `Angry`, `Swim`, `SwimSplash`, `SwimHighSpeedSplash`, `Falls` (small / big fall sounds), `AmbientInterval` (ticks, default 80), `Volume` (the voice volume, default 1), `VoicePitch`, `Jump`.
- `(by Class)` after a step cell names the ancestor class that defines the step method that was read. After a pair of sounds, `when P` or `(chosen by P)` names the predicate method or field the method tests; the first sound is the one for a true predicate. A cell that says `no sound (null)` means the method returns no event for that condition, so nothing is played and no random number is drawn for it.
- A cell whose method makes a random draw before the choice says so (fox, bat, parrot, cat and wolf in 4.4); the draws are from the entity's own random unless the cell says otherwise.

### 4.3 The ambient sound rule, baby pitch and the angry sound

**Ambient interval** (`Mob.baseTick`). The counter runs in the entity's tick on the **server** (and for entities simulated locally); a client hears the result only through a Sound or Sound Entity packet (59 §2.2). While the mob is alive, **every tick**, in this order: one draw `r = nextInt(1000)` of the mob's own random source; the counter `ambientSoundTime` (starts at 0) is read and then incremented by one; if `r` is **less than the value read before the increment**, the counter is set to **`-getAmbientSoundInterval()`** (the reset comes after the increment, so it wins) and `playAmbientSound()` runs (`makeSound(getAmbientSound())`: nothing when the sound is null or `EMPTY`). The draw is made in every tick of a living mob, also one whose ambient sound is null, and before the sound's own random draws. **`Mob.playHurtSound` also sets the counter to `-getAmbientSoundInterval()` before it plays the hurt sound** (read), so a mob that was just hurt stays quiet for about its interval. The default interval is **80** ticks (`Mob`); overrides are in the `AmbientInterval` column (`Animal` default 120, 400 for the equines and llamas, the happy ghast 120, or 720 while it carries a passenger, and so on).

Consequences, computed: after a reset at tick 0 the value read in tick `t` is `-I + t - 1`, so no sound is possible up to tick `I + 1`; in tick `I + 1 + s` (s = 1, 2, ...) the chance is `s / 1000`, which is 1 at s = 1000, so the wait is at most `I + 1001` ticks. Summing the survival probabilities of that sequence gives an expected wait of **`I + 40.3` ticks** from the reset to the tick of the sound (computed numerically: 120.3 ticks for I = 80, 160.3 for I = 120, 440.3 for I = 400; the 40.3 is independent of `I`). A freshly spawned mob starts at 0, not at `-I`, so its first sound comes after about 40 ticks. The sound uses the voice volume and pitch of 2.7.

**Voice pitch.** `getVoicePitch()` (2.7): adults `1.0 + (r1 - r2) x 0.2`, babies `1.5 + (r1 - r2) x 0.2`; r1 and r2 are two successive `nextFloat()` draws (r1 first), so the offset is the difference of two uniform numbers, a triangular spread over -0.2 to +0.2, not a uniform one. It applies to every `makeSound` including hurt and death. **Overrides read**: `zombie_villager` babies `2.0 + (r1 - r2) x 0.2`, adults `1.0 + (r1 - r2) x 0.2`; `parrot` `1.0 + (r1 - r2) x 0.2` at every age; `bat` the inherited value x 0.95; `happy_ghast` and `player` the constant 1.0; the cube mobs (slime, magma cube, sulfur cube) do not override `getVoicePitch` but have their own `getSoundPitch` (table).

**Horse family angry sound.** `AbstractHorse.getAngrySound()` returns null (no sound); it is overridden by `Horse` (baby `entity.baby_horse.angry`, adult `entity.horse.angry`), `Donkey` (`entity.donkey.angry`), `Mule` (row `mule`), `ZombieHorse` (`entity.zombie_horse.angry`) and `Llama` (`entity.llama.angry`) (rows above); the `skeleton_horse` row has no `Angry` entry because nothing in its class chain overrides it (null: nothing is played); the eating sounds are in the same column. The sound is played by **`AbstractHorse.makeMad()`**: when the horse is **not already standing** (`isStanding()` false) **and the level is not the client's** it calls `standIfPossible()` (when `canPerformRearing()` holds and the horse is effectively AI-controlled or the level is not the client's: `setStanding(20)`, the rearing animation timer) and then `makeSound(getAngrySound())` (the voice volume and pitch of 2.7). `makeMad` is called by `RunAroundLikeCrazyGoal.tick` and by `mobInteract` of `Horse`, `ZombieHorse` and `AbstractChestedHorse`; the conditions inside those four callers were not read (Open question 2).

### 4.3a The horse family step sound (`AbstractHorse.playStepSound`)

Inputs: the step position, `state` (the state the entity stands on) and the block above (`pos.above()`). In this order:

1. If `state` is a liquid: **no sound**.
2. `type` = the sound type of `state`; if the block above is a **snow layer** (`Blocks.SNOW`) `type` is the sound type of that snow block instead.
3. If the horse **has a passenger** (`isVehicle`) **and** `canGallop` (a field, initial true): `gallopSoundCounter` is incremented; then if the counter is **greater than 5 and divisible by 3** the gallop sound is played (below); else if the counter is **5 or less** `entity.horse.step_wood` is played with **volume = type volume x 0.15 and pitch = type pitch**; else (counter above 5, not divisible by 3) nothing. (The counter is set to 0 again in `tickRidden` when the forward component of the rider's input is 0 or less, **and only when `isLocalInstanceAuthoritative()` holds**: always on a server level, on a client level only for a horse the local player controls, 2.4.)
4. Otherwise: if `type` is one of the wood-like types `WOOD`, `NETHER_WOOD`, `STEM`, `CHERRY_WOOD`, `BAMBOO_WOOD` (`isWoodSoundType`): `entity.horse.step_wood`; else `entity.baby_horse.step` when `isBaby`, else `entity.horse.step`; volume = type volume x 0.15, pitch = type pitch.

The gallop sound is `entity.horse.gallop` with volume = type volume x 0.15 and pitch = type pitch; `Horse` (the horse itself) overrides it to play that sound and then, when `nextInt(10)` of its random is 0, also `entity.baby_horse.breathe` (baby) or `entity.horse.breathe` with volume = type volume x 0.6 and pitch = type pitch. No other class declares `playGallopSound` (scan of the jar: only `AbstractHorse` and `Horse` do), so the donkey, mule, zombie horse and skeleton horse use the base gallop sound. The volume and pitch are those of the sound type, not constants; they differ from the table's 0.15 and 1.0 for types such as `METAL` (pitch 1.5).

### 4.3c The parrot's imitation map

`Parrot.getAmbient` is a static method: when the difficulty is not PEACEFUL and `nextInt(1000)` of the **level's** random (the first draw) is 0, a second draw `nextInt(size)` of the level's random indexes the list built from the keys of `MOB_SOUND_MAP`, and the sound is that mob's imitation event; otherwise it is `entity.parrot.ambient`. The map has **42 entries** (read from the static initialiser): every entity type below maps to `entity.parrot.imitate.<name>` with the same name except `cave_spider`, which maps to `entity.parrot.imitate.spider`; **`happy_ghast` maps to `EMPTY`**, which is never played. Types: `blaze`, `bogged`, `breeze`, `camel_husk`, `cave_spider`, `creaking`, `creeper`, `drowned`, `elder_guardian`, `ender_dragon`, `endermite`, `evoker`, `ghast`, `happy_ghast`, `guardian`, `hoglin`, `husk`, `illusioner`, `magma_cube`, `parched`, `phantom`, `piglin`, `piglin_brute`, `pillager`, `ravager`, `shulker`, `silverfish`, `skeleton`, `slime`, `spider`, `stray`, `vex`, `vindicator`, `warden`, `witch`, `wither`, `wither_skeleton`, `zoglin`, `zombie`, `zombie_horse`, `zombie_nautilus`, `zombie_villager` (that is the order of the static initialiser, not of the list the draw indexes). The list is built from a hash map keyed by entity types without a `hashCode` override, so the order of the keys, and therefore which mob a given draw picks, is **not reproducible**; an implementation may pick uniformly (each of the 42 keys has probability 1/42, so `cave_spider` and `spider` together make `imitate.spider` twice as likely as any other event, and `happy_ghast` gives silence with probability 1/42).

- **Playing.** Event: the note block's block event (30-5). The sound is `playSeededSound(null, centre, holder, RECORDS, volume 3.0, pitch, seed = nextLong of the level random)`. **Pitch**: for instruments of type `BASE_BLOCK` (`isTunable`): `2^((note - 12) / 12)` with `note` the state's `note` property (0 to 24; `getPitchFromNote`: `Math.pow(2, (note - 12) / 12.0)`, the result as float), and a `note` particle at `(x + 0.5, y + 1.2, z + 0.5)` with x-velocity `note / 24`; for the other types the pitch is **1.0** and no particle. - Pitch table: note 0 = 0.5, 12 = 1.0, 24 = 2.0 (exactly the clamp range of 59 §4.2); note 1 = 0.529732, note 6 = 0.707107, note 18 = 1.414214 (computed).

### 5.4 Respawn anchor (CC-0038)

- **Charge**: `block.respawn_anchor.charge` (BLOCKS, volume 1.0, pitch 1.0) at the block centre (x + 0.5, y + 0.5, z + 0.5) when a glowstone charges it (`RespawnAnchorBlock.charge`).
- **Set spawn** (`RespawnAnchorBlock.useWithoutItem`, on the server). The use returns PASS (no sound) when the block's `charge` is 0; CONSUME (no sound) when the level is not a server level; when `canSetSpawn` is false the anchor explodes (no sound here). Otherwise, for a `ServerPlayer`, the new respawn config (this dimension, the anchor position, yaw 0, pitch 0, not forced) is compared with the player's current one: **only when the current config is null or not the same position (`isSamePosition`)** is the config stored (`setRespawnPosition(config, true)`) and `block.respawn_anchor.set_spawn` played (`ServerLevel.playSound` with no excluded entity, at x + 0.5, y + 0.5, z + 0.5, BLOCKS, volume 1.0, pitch 1.0), and the use returns SUCCESS. A player who already has this anchor as respawn point gets CONSUME with **no sound**; a non-server player gets CONSUME.
- **Ambient** (`animateTick`, client): returns at once when `charge` is 0. Otherwise one draw `nextInt(100)` of the random passed to `animateTick`; when it is **0** (read: the sound is skipped for any other value) `playLocalSound(pos, block.respawn_anchor.ambient, BLOCKS, 1.0, 1.0, false)` plays (block centre, no distance delay). Then, on every call, one `reverse_portal` particle at (x + 0.5 + (0.5 - `nextDouble()`), y + 1.0, z + 0.5 + (0.5 - `nextDouble()`)) with velocity (0, `nextFloat()` x 0.04, 0); the draw order is `nextInt`, `nextDouble` (x), `nextDouble` (z), `nextFloat`.
- **Deplete**: `block.respawn_anchor.deplete` is referenced by exactly one class besides the event registry, `PlayerList.respawn(player, flag, reason)`; `RespawnAnchorBlock` does not play it (so the explosion path plays no deplete sound). The method runs after a death (the call in the client-command handler passes `flag` false with the removal reason KILLED; the End-exit path passes true with CHANGED_DIMENSION). It first calls `findRespawnPositionAndUseSpawnBlock(!flag, ...)` (which uses the spawn block: not read in detail) and copies the respawn config to the new player unless the transition reports a missing respawn block. At the end, when **`flag` is false**, the new player's respawn config exists, the level of its dimension exists and the block state at its position **is a respawn anchor**, a `ClientboundSoundPacket` is sent to the respawning player only: event deplete, BLOCKS, position = the anchor's **integer** block coordinates (no 0.5 offset), volume 1.0, pitch 1.0, seed = `nextLong` of the new level's random (the Sound packet of 59 §2.2). What the charge decrement does (Open question 7) is not read.

### 5.5 Lightning and thunder

`LightningBolt.tick`, at the first tick of the bolt's life (life counter equals 2), **on the client only and only when the bolt is not silent** (`isSilent`): `playLocalSound(x, y, z, entity.lightning_bolt.thunder, WEATHER, 10000.0, 0.8 + r x 0.2, false)` and `playLocalSound(x, y, z, entity.lightning_bolt.impact, WEATHER, 2.0, 0.5 + r x 0.2, false)` (r a `nextFloat()` of the bolt's random for each). Volume 10000 only widens the audible range: 59 §4.2 and §4.3 (the gain clamps to 1; the attenuation distance is 10000 x the sound's distance); `distanceDelay` is false (read), so the sound plays at once; any delay by distance for far thunder comes from the audio engine's attenuation only. Rain and snow ambient sounds, the rain splash and the sounds of the biome weather are in `ClientLevel`/the weather effect renderer: not decoded (Open question 4).

## 6. Worked examples

**A step sequence.** A player walks forward on a stone block at the steady horizontal speed of 0.2158 blocks per tick (about 4.32 blocks per second; derived in 13 §1.3); standing on ground, not sneaking, no passenger, not in water. Per tick `hwalk = 0.2158 x 0.6 = 0.1295`, so `moveDist` crosses `nextStep = 1.0` at tick 8 (8 x 0.1295 = 1.036 > 1): play `block.stone.step` with volume `1.0 x 0.15 = 0.15` and pitch 1.0 (source PLAYERS, position of the player), set `nextStep = floor(1.036) + 1 = 2.0`. The next sound is at tick 16 (16 x 0.1295 = 2.072 > 2), then 3.0 at tick 24 (3.108), and so on: one step sound every 7.72 ticks on average (0.386 s), each at volume 0.15. On `METAL` (rails) the same sequence has pitch 1.5. Sprinting at 0.2806 blocks per tick (about 5.61 blocks per second, 13 §1.3): `hwalk = 0.1684`, first step at tick 6 (1.010). While sneaking on the ground the player's emission is `NONE` (2.4): no step sound and no game event at all. **In water**: when the player is **on the ground in water and not swimming**, the block routine of 2.4 step 5 succeeds at each `nextStep` crossing and the player rule of 2.4 plays the swim sound (2.6) and then the muffled step (volume x 0.05, pitch x 0.8); when the player is swimming (the swimming pose) or floating without ground contact the routine returns false and only the in-water branch of step 4 runs, which plays the **swim sound alone** at the same crossings, with no muffled step.

**A fall.** Falling onto stone from 5 blocks (the accumulated `fallDistance` is 5.0): landing calls `causeFallDamage(5.0, 1.0, fall)`; `floor(5.0 + 1.0E-6 - 3.0) = 2`, not greater than 4, so the player plays `entity.player.small_fall` at volume 1.0 and pitch 1.0, then `block.stone.fall` at volume 0.5 and pitch 0.75 (stone: volume 1 x 0.5, pitch 1 x 0.75), then `hurt` applies 2 damage (its hurt sound follows 2.7 and 4.3b: the damage type `fall` has no `effects` member, so `entity.player.hurt`). A 9-block fall (`fallDistance` 9.0) gives `floor(6.000001) = 6`: `entity.player.big_fall`. A player whose `mayfly` ability is true (set for creative and spectator mode by `GameType.updatePlayerAbilities`) plays nothing.

**A note block.** A note block with state `note = 18` on a stone block (the block below is stone: `BASEDRUM`, tunable) with no head above plays `block.note_block.basedrum` with source RECORDS, volume 3.0, pitch `2^((18 - 12) / 12) = 1.414214`; the seed is the next `nextLong()` of the level random and the note particle is spawned at `(x + 0.5, y + 1.2, z + 0.5)` with x-velocity 0.75. With a skeleton skull above it, the instrument is `SKELETON` (not tunable): pitch 1.0, no particle.

**A block break and a place.** Breaking a `WOOD` block: break event `block.wood.break`, volume `(1.0 + 1) / 2 = 1.0`, pitch `1.0 x 0.8 = 0.8`; breaking `ANVIL`: `block.anvil.break`, volume `(0.3 + 1) / 2 = 0.65`, pitch 0.8; placing a `METAL` block (pitch 1.5): `block.metal.place`, volume 1.0, pitch `1.5 x 0.8 = 1.2`; the hit sound for `ANVIL`: volume `(0.3 + 1) / 8 = 0.1625`, pitch 0.5.

## 7. What this document does not cover

**Read for the questions named in the header**: the 131 block sound types and their use; the rules for place, break, hit (including the repeat while mining), step (the movement emission of every entity class, the player's combination rule, the crystal chime), swimming, splashing, landing, fall damage (with the seven `fallOn` rules) and the voice; the equip, item-break, eating and drinking sounds (2.8); the ambient, hurt, death, step, swim, splash and fall sounds of all 161 entity types (for those columns the table of 4.2 gives the value of the most derived definition, and every predicate cell names its test); the ambient interval; the horse step tree and angry sound; the wolf and cat rules; the parrot map; the player's hurt sound by damage type; the call sites of 4.5 (the cube mob attack, the villager and trader sounds); and the level events, note blocks, bells, respawn anchor and thunder of §5.

**Not in the table of 4.2** (a scope limit, not an Open question): an entity class plays more sounds than its table columns. The sound event registry holds **928** `entity.*` events (842 registered by literal name in the `SoundEvents` initialiser, 776 `register` plus 66 `registerForHolder`, plus the 86 variant events of 4.4 that the five `register<Family>SoundVariants` methods of the same class build by name concatenation, one name set per variant of the 16 of 4.4: cat 18, wolf 42, pig 12, cow 8, chicken 6; 46 §14.3 lists the same 928 keys); **350 of them are named nowhere in documents 59 and 60** (strict full-key match; 39 of those are the parrot imitation events, which 4.3c gives by a pattern). They belong to actions that no column lists: for example the warden's listening, roar, sniff, dig and emerge sounds, the ravager's attack, roar, stunned and celebrate sounds, the creaking's activate, deactivate, attack, freeze and twitch sounds, the hoglin attack and the hoglin and piglin conversion sounds, the sniffer's eating, scenting, sniffing and digging sounds, the goat's ram sounds, and the breeze, armadillo, copper golem and sulfur cube sounds beyond hurt and death. An implementation that needs one of them has no rule in this document.

**Not read** (each is a numbered Open question in §8): the item data behind 2.8, that is which item has which equip sound and which consume constant (1; the two `break_sound` overrides and the ominous bottle's constant are read); the call sites that decide when an entity plays a sound the table lists: the cat's `hiss` callers, the conditions of the callers of the horse's `makeMad`, the callers of the slime and cube mobs' `SoundPitch`, and the start conditions of the villager celebrate behaviour (2); the sounds of `FarmlandBlock.turnToBaseBlock` and `TurtleEggBlock.destroyEgg`, the setter of the impulse-fall flag, the bounce movement and the Jump Boost scaling (3); weather sounds (4); the tickable sound instances created by game code (59 §5.3; the bubble column handler is read, 59 §8.3) (5); the ambient block sounds (6); the charge decrement of the respawn anchor on respawn (7).

## 8. Open questions

1. **Item data behind the equip, break and consume sounds.** Which item carries which `equip_sound` (the `equippable` components and the armor materials), which item uses which `consumable` constant or its own values (the ominous bottle's constant and the two `break_sound` overrides, the shield and the wolf armor, are read in 2.8), and whether the client's copy of the slot still holds the broken stack when the break event of 2.8 arrives (the order of the entity event and the equipment update) were not read.
2. **Entity sound call sites.** The table of 4.2 and 4.5 list the events and the call sites read, not every call site: the callers of `Cat.hiss()`, the conditions inside the callers of `AbstractHorse.makeMad` (`RunAroundLikeCrazyGoal.tick` and the `mobInteract` of `Horse`, `ZombieHorse` and `AbstractChestedHorse`), where the `SoundPitch` of the slime, magma cube and sulfur cube is set from, and the start conditions of `CelebrateVillagersSurvivedRaid` (4.5) were not read.
3. **Fall rules outside the entity.** The sounds inside `FarmlandBlock.turnToBaseBlock` and `TurtleEggBlock.destroyEgg`, the callers of `setIgnoreFallDamageFromCurrentImpulse` (the code that sets the impulse flag), the bounce movement of blocks with a `bounceRestitution`, and the per-level scaling of the Jump Boost modifier of `safe_fall_distance` were not read (2.7).
4. **Weather sounds.** Rain, snow and the weather particle sounds (`ClientLevel`, the weather renderer) were not decoded; thunder is in 5.5.
5. **Tickable instances created by game code** (59 §5.3, 59 Open question 12): the volume ramps and conditions of the elytra, minecart, riding, bee, guardian and sniffer instances were not read; the bubble column handler is read (59 §8.3).
6. **Ambient block sounds.** The tag lists `triggers_ambient_*_block_sounds` and the classes `AmbientDesertBlockSoundsPlayer` and `AmbientLeavesBlockSoundPlayer` (`net.minecraft.world.level.block.sounds`) were seen but not read.
7. **Respawn anchor on respawn.** The charge decrement inside `ServerPlayer.findRespawnPositionAndUseSpawnBlock` and whether the deplete sound of 5.4 can play when the anchor was not actually used were not read; the guards of the sound itself (flag false, config present, dimension level present, block is an anchor) are in 5.4.
8. **Block name expansion of the colour and weathering families.** The family sound is read (§1.4); the per-colour and per-stage block names follow the naming of 24-1 §2.3 and were not re-derived here.
