## 1. Villages

### 1.1 There is no village object

The artifact keeps no village record. A "village" is derived from points of interest (POIs) every time a rule asks (`PoiManager`, `ServerLevel.isVillage`, `isCloseToVillage`). Everything below follows from three things: the POI types (1.2), the claim state of each POI (1.3) and the per-section distance field (1.4).

### 1.3 Claims, sections and the POI manager (`PoiManager`, `PoiSection`, `PoiRecord`)

A POI record is (block position, type, free tickets). A new record starts with `maxTickets` free tickets. `acquireTicket` fails when no ticket is free, else decrements; `releaseTicket` fails when all tickets are already free, else increments. Releasing a position with no record is an error (the manager throws), so callers check first.

| Predicate | Definition |
|---|---|
| `hasSpace` | free tickets above 0 |
| `isOccupied` | free tickets different from `maxTickets` (at least one ticket claimed) |
| Occupancy filter `HAS_SPACE` / `IS_OCCUPIED` / `ANY` | the record test applied by queries: has space, is occupied, always true |

A zero-ticket POI (beehive, portal, ...) is never "occupied" and always "has no space".

Storage: records are kept per section (a map from the section-relative position to the record, plus an index by type); a section also carries a validity flag. Adding a record of a different type at an occupied position is an error. Reconciliation with the blocks is described below. `ensureLoadedAndValid(level, pos, radius)` loads and validates the sections within `floorDiv(radius, 16)` chunks of the position's chunk (no +1 here; the +1 belongs only to `getInSquare`, below), over every section height from the level's minimum section to its maximum section, before a search.

**Reconciliation with the blocks (`PoiManager.checkConsistencyWithBlocks`, `PoiSection.refresh`, read; closes former Open question 2).** `refresh` does nothing when the section's validity flag is already true. It runs only on a section whose flag is false, in this order: (1) copy the section's record map; (2) clear the records and the by-type index; (3) rescan every block of the section (only when the chunk section may contain POI blocks, `mayHavePoi`; otherwise nothing is scanned and every record is dropped); for each block state that has a POI type, reuse the old record at the same section-relative position if there is one (its free tickets and its old type are kept, because reuse is by position only, even if the block now maps to a different type), else create a record with all tickets free; (4) set the flag true and mark the section dirty. Records at positions that are no longer POI blocks are therefore dropped. When no PoiSection is loaded for the section and the chunk section may contain POI blocks, a section is created and populated by the same scan (all records new, all tickets free). `onSectionLoad` and `setDirty` both feed the section's source level (village centre or not, 1.4) into the distance tracker.

Queries (all return only records inside the range):

| Query | Rule |
|---|---|
| `getInSquare(typePredicate, pos, r, occupancy)` | gather the records of every chunk in the chunk square of radius `floorDiv(r,16)+1` around the position's chunk, then keep those with `|dx| <= r` and `|dz| <= r` (y is ignored) |
| `getInRange(.., r, ..)` | `getInSquare` then keep `distSqr(record, pos) <= r*r` (full 3D distance) |
| `findClosest` | the record with the smallest `distSqr` among `getInRange` |
| `findAllClosestFirstWithType` | all matches of `getInRange`, ordered by ascending distance |
| `take(typePredicate, posPredicate, pos, r)` | the first record of `getInRange` with occupancy `HAS_SPACE` that also satisfies the position predicate (iteration order of the stream, not necessarily the closest); the matching ticket is acquired and the position returned |
| `getRandom(..)` | the matches of `getInRange` are shuffled with the given random source and the first one passing the position predicate is returned |
| `release(pos)` | releases a ticket of the record at the position |
| `exists(pos, typePredicate)` | a record exists at the position and its type satisfies the predicate |
| `existsAtPosition(key, pos)` | the same with a type key |
| `getCountInRange` | the count of `getInRange` |

### 1.4 The section distance field (`PoiManager$DistanceTracker`, `sectionsToVillage`)

The manager keeps, for every loaded section, a small integer "distance to the nearest village centre" in sections.

1. A section is a **village centre** when it holds at least one **occupied** record (1.3) of a POI type in tag `village` (job site, home or meeting). An unclaimed bed or an unclaimed workstation does not make a village; a bed that a villager has claimed, a workstation a villager holds, or a bell with at least one of its 32 tickets taken does.
2. The field is a bounded-level propagation: a centre has level 0; level of any other section = 1 + the smallest level among its 26 neighbours (the three nested -1..1 offsets in x, y and z, excluding itself), i.e. the Chebyshev (cube) distance in sections; the maximum level is 7, and levels above 6 are not stored, so 7 means "no village within 6 sections". The field is recomputed lazily (`runAllUpdates`) when `tick` or a query runs; it is updated when a section's records change or when a section is loaded.
   Read this round (closes the neighbour-rule part of former Open question 1): the tracker is a `SectionTracker` built with 7 levels (0 to 6 storable; the constructor arguments are 7, 16, 256) and a default level of 7; the source test is "is a village centre" (source level 0, else 7); the neighbour rule `computeLevelFromNeighbor` returns the source level when the neighbour is itself a source, else the neighbour's level + 1; the neighbourhood visited after a change is the 26 offsets of the -1..1 cube (`SectionTracker.checkNeighborsAfterUpdate`). So the Chebyshev reading above is confirmed, not inferred.
3. `sectionsToVillage(section)` returns that level (0 to 6, or 7).
4. `ServerLevel.isCloseToVillage(pos, n)` is false when `n > 6`, else true when `sectionsToVillage(section of pos) <= n`. `ServerLevel.isVillage(pos)` is `isCloseToVillage(pos, 1)`: the position's section is at most 1 section (Chebyshev) from a village centre section. (20 section 14.1 states the same tests; this is their source.)

Consequences (worked examples are in 7): a lone bed claimed by a sleeping villager makes the 3 x 3 x 3 sections around its own section "village" for `isVillage`, and the 5 x 5 x 5 sections "close to village" (n = 2) for patrol, cat and similar tests. The village boundary is therefore a union of cubes, not a radius, and moves when claims change.

### 1.4a Block-change hook that creates and removes POIs (`Level.setBlock`, `ServerLevel.updatePOIOnBlockStateChange`; closes former Open question 2)

1. At the end of a successful block change, `Level.setBlock` (after the neighbour updates and shape updates have run) calls `updatePOIOnBlockStateChange(pos, oldState, newState)`. The base `Level` method does nothing; only `ServerLevel` overrides it.
2. The override looks up the POI type of the old state and of the new state (`PoiTypes.forState`, the state-to-type map of 1.2; "none" when the state belongs to no type). When the two lookups are equal (both none, or the same type) it returns at once: replacing one bed colour with another, or changing a non-POI property, leaves the record and its tickets untouched. Note that the lookup is by block state, so a state change inside one type (for example a lectern changing from unpowered to powered, which stays in the lectern type) does nothing; a bed whose `part` flips from head to foot is a change from `home` to none.
3. Otherwise, in this order: if the old state had a type, a remove-task is queued; then if the new state has a type, an add-task is queued. Both tasks are queued on the server's main task queue (`MinecraftServer.execute`), not run inline, so the record changes at the next point where the server runs queued tasks. The remove-task calls `PoiManager.remove(pos)` (the record and its tickets are dropped, the section is marked dirty); the add-task calls `PoiManager.add(pos, type)` (a new record with all tickets free, 1.3). A villager that held a ticket on the removed POI is not told here: its own `ValidateNearbyPoi`/memory checks (2.2) notice the missing record.
4. Consequences: breaking and re-placing a workstation drops all claims on it (the villager must reacquire); placing a bed over an existing POI position first removes then adds, so the new record starts unclaimed.

### 1.6 Cat spawner (`CatSpawner`, a custom spawner of the overworld)

1. A counter `nextTick` (initial 0) is decremented on every call; while it is above 0 the spawner returns. When it reaches 0 or below it is set to **1200** (set, not added) and the attempt runs. (The first call after world start therefore runs at once.)
2. A random player is chosen (`getRandomPlayer`); none ends the attempt.
3. Offsets from the player's block: `x = (8 + nextInt(24)) * s1`, `z = (8 + nextInt(24)) * s2`, where each sign `s` is -1 when `nextBoolean()` is true and +1 otherwise (draw order: x amount, x sign, z amount, z sign); y offset 0. The chunks within +-10 blocks of that position must be loaded.
4. The position must pass the spawn placement check for the cat (`SpawnPlacements.isSpawnPositionOk(cat, level, pos)`). Then:
   - if `isCloseToVillage(pos, 2)`: **village case**: count the occupied `home` POIs within 48 blocks (`getCountInRange`, occupancy IS_OCCUPIED, range 48); if the count is **above 4** and fewer than **5** cats exist in the box of the position inflated by (48, 8, 48), spawn one cat there, not persistent;
   - else if a structure from structure tag `cats_spawn_in` (data, `data/minecraft/tags/worldgen/structure/cats_spawn_in.json`: `swamp_hut`) has a valid piece containing the position: **hut case**: if no cat exists in the box inflated by (16, 8, 16), spawn one cat, made persistent (`setPersistenceRequired`).
5. A cat is created with reason NATURAL, finalized with the difficulty at the position and reason NATURAL, snapped to the block with yaw 0 and pitch 0, and added with passengers. (Its coat variant comes from the finalize rules of 19 section 1.6.)

### 1.7 Zombie village siege (`VillageSiege`, a custom spawner)

State: `siegeState` (SIEGE_DONE initially, SIEGE_TONIGHT), `hasSetupSiege`, `zombiesToSpawn`, `nextSpawnTime`, and the chosen centre `(spawnX, spawnY, spawnZ)`. Per call (the second argument is the "spawn enemies" flag of the custom-spawner call):

1. If it is bright outside or the flag is false: state = SIEGE_DONE, `hasSetupSiege` = false, return. (A siege can therefore only run at night.)
2. If the dimension has a default clock and the clock is exactly at the time marker `roll_village_siege` (data: overworld day timeline `timeline/day.json`, marker `roll_village_siege` = **18000**, timeline `period_ticks` 24000): state = SIEGE_TONIGHT with probability 1/10 (`nextInt(10) == 0`), else SIEGE_DONE. `isAtTimeMarker` is `ClockTimeMarker.occursAt(totalTicks)` of the clock instance: with no period it is true only when `ticks == totalTicks`, otherwise when `ticks == totalTicks mod period` (33 section 3.3). `Timeline.registerTimeMarkers` builds every `ClockTimeMarker` with the timeline's own `period_ticks` (read: the constructor call passes the timeline's optional period field), and `day.json` has `period_ticks` 24000, so `roll_village_siege` has period 24000 and the roll happens once per day, when `total mod 24000 == 18000`, never only once at total tick 18000. The comparison is an equality, so it is evaluated on every call whose tick equals the marker.
3. If the state is SIEGE_DONE, return.
4. If the siege is not yet set up, call the setup (4a); if it fails return, else `hasSetupSiege` = true.
5. If `nextSpawnTime > 0`, decrement and return. Else `nextSpawnTime` = **2**; if `zombiesToSpawn > 0`, try to spawn one zombie (4b) and decrement the counter; otherwise state = SIEGE_DONE.

**4a Setup**: for each player in the level in order, skipping spectators: skip unless the player's block `isVillage`; skip if the biome at the player is in biome tag `without_zombie_sieges` (data: `mushroom_fields`); then make up to **10 attempts**: pick a random angle `nextFloat * 2pi`; `spawnX = floor(cos(a) * 32) + player.x`, `spawnY = player.y`, `spawnZ = floor(sin(a) * 32) + player.z` (the float cos and sin are multiplied by 32 as floats before flooring; `cos` and `sin` are the engine's `Mth.cos` and `Mth.sin`, specified in 1.7a); if `findRandomSpawnPos` (4c) around that point finds a position: `nextSpawnTime` = 0, `zombiesToSpawn` = **20**, and the setup succeeds (the first successful player and attempt wins). If no player yields a position the setup fails.

**4b Spawning one zombie**: `findRandomSpawnPos` around the stored centre; none: nothing is spawned (the counter is still decremented). Otherwise a zombie is created and finalized (difficulty at its block, reason EVENT, no group data); a failure is only logged. The zombie is placed at the position with a random yaw `nextFloat * 360` and pitch 0 and added with passengers.

**4c `findRandomSpawnPos(centre)`**: up to **10 attempts**; each picks `x = centre.x + nextInt(16) - 8`, `z = centre.z + nextInt(16) - 8`, `y` = the WORLD_SURFACE height at (x, z); the candidate is rejected unless `isVillage` is true at it and the zombie spawn rules for reason EVENT hold (`Monster.checkMonsterSpawnRules`: the standard monster light and placement tests of 18); the result is the bottom centre of the first accepted block.

So a siege is: 1 night in 10, only where a player stands in a village, a ring 32 blocks away, 20 zombies, one every 3 ticks (2 ticks of countdown plus the spawning tick), each within +-8 blocks of the ring point and inside the village cubes.

**1.7a `Mth.sin` and `Mth.cos` (read, `Mth`)**: a table of 65536 floats; entry `i` is the double-precision sine of `i / 10430.378350470453`, narrowed to float. Both functions take a double. `sin(x)` reads entry `((long)(x * 10430.378350470453)) & 65535`; `cos(x)` reads entry `((long)(x * 10430.378350470453 + 16384.0)) & 65535` (the cast truncates towards zero). Float angles are widened to double first. Notable entries: entry 16384 is exactly 1.0; entry 32768 is the sine of the double nearest pi, about +1.2246e-16 (tiny and positive).

### 2.1 `AcquirePoi(poiPredicate, firstMemory, secondMemory, onlyAdult, entityEvent, validity)`

Constants: scan range 48 blocks (`SCAN_RANGE`), at most 5 candidates, retry interval described below. It is a one-shot behaviour. The factory `create(predicate, memoryA, memoryB, onlyAdult, event, validity)` requires `memoryB` to be absent and stores the claimed position in `memoryB`; when `memoryA` is a different memory it additionally requires `memoryA` to be absent (it is never written). The single-memory forms use the same memory for both roles. The brain entries (read, `VillagerGoalPackages`): job = (`job_site`, `potential_job_site`, onlyAdult true), so it starts only while both are absent and stores the claim in `potential_job_site` (never directly in `job_site`, and the choice does not depend on whether the villager already has a job; 19 section 22.3); home = (`home`, onlyAdult false, event 14); meeting = (`meeting_point`, onlyAdult true, event 14), both single-memory.

Each evaluation:
1. If `onlyAdult` is set and the mob is a baby: do nothing.
2. A per-behaviour-instance timer `nextScan` (initially 0): on the very first evaluation it is set to `gameTime + nextInt(20)` and the evaluation ends; afterwards, if `gameTime < nextScan`, do nothing; otherwise `nextScan = gameTime + 20 + nextInt(20)` (a scan every 20 to 39 ticks per villager, spread over time).
3. A per-instance cache `Long2Object` maps a POI position (as long) to a retry object. First all cache entries older than 400 ticks since their last attempt (`isStillValid`: `now - lastAttempt < 400`) are dropped.
4. Candidates: `findAllClosestFirstWithType(poiPredicate, positionFilter, mobBlockPos, 48, HAS_SPACE)` (closest first). The position filter is an argument of that call, so it runs before the limit: rejected positions do not use up the slots. The stream is then limited to **5**, then filtered by the extra validity predicate (the bed check for homes: the block is in tag `villagers_can_sleep_on_bed` and not occupied, 19 section 22.8), which therefore runs after the limit. The position filter rejects a position when it has a cache entry and that retry object says "not yet" (`shouldRetry(now)` false). A position with no cache entry passes with no call at all. `markAttempt(now)` is called only for a position that already has an entry and whose `shouldRetry` passed (read: the filter calls `get`, then `shouldRetry`, then `markAttempt`). Retry objects are created only on a failed path (step 7), and the constructor itself marks the first attempt.
   The `onlyAdult` flag of step 1 per brain entry (read, `VillagerGoalPackages`): job site **true** (claim stored in `potential_job_site`, no entity event), meeting point **true** (event 14), home **false** (event 14).
5. Path: one path is requested to the whole set of candidate positions (`findPathToPois`): the target set holds the positions, the search radius is the largest `validRange` among the candidate types; no candidates means no path.
6. If a path exists and `canReach()`: the path's target position is the choice. The POI is claimed with `take(poiPredicate, (type, pos) -> pos equals target, target, 1)` (radius 1, so only that exact record), the global position is stored in `memoryB` (the storing memory above), the entity event byte is broadcast if one was configured (14 for homes and the meeting point, none for jobs), and the whole retry cache is cleared; the debug synchroniser is told of the POI change.
7. If there is no usable path, every candidate gets a retry object (created on first failure) so the next scan skips it for a while.
8. The behaviour returns "started" after a scan that reached step 4.

**Retry delay (nested class `AcquirePoi$JitteredLinearRetry`)**: each object remembers `previousAttempt` and `currentDelay` (initial 0). `markAttempt(now)`: `previousAttempt = now`; `currentDelay = min(currentDelay + nextInt(40) + 40, 400)`; the next allowed attempt is `now + currentDelay`. So the n-th consecutive failure for the same POI waits a delay that grows by 40 to 79 ticks each time up to 400 ticks, and an entry untouched for 400 ticks is forgotten.

### 2.2 `ValidateNearbyPoi(poiPredicate, memory)`

Runs every tick while `memory` is present. Steps: (1) if the stored position is in another dimension, or the villager is farther than 16 blocks (`closerToCenterThan(pos, 16)` false), do nothing (the memory is kept); (2) otherwise, if the POI manager has no record at that position whose type satisfies the predicate, erase the memory; (3) for the home memory case (the predicate pair given to it in the brain): if the bed block is in tag `villagers_can_sleep_on_bed`, has `occupied = true`, and the villager itself is not sleeping (`bedIsOccupied`), the memory is erased and, unless another villager is lying in it (any villager inside the block's box, `bedIsOccupiedByVillager`), the POI ticket is released. The claim is thereby handed back when a player or a non-villager sleeps in the villager's bed.

### 2.3 `PoiCompetitorScan` (core, priority 2; requires `job_site` and `nearest_living_entities`)

Each evaluation: the villager's job-site POI type is read from the POI manager; for every other villager in `nearest_living_entities` that has the same `job_site` position and a profession whose held-job-site predicate accepts that POI type (`competesForSameJobsite`), keep the one with the larger villager XP: the loser (compared pairwise by `getVillagerXp`) has its `job_site` memory erased. The reduction folds the competitor list together with this villager, so exactly one villager keeps the site. Exact rule (read, `PoiCompetitorScan.selectWinner`): the competitors are the other villagers in the list that are alive, are not this villager, have a `job_site` memory equal to this villager's and a profession whose held-job-site predicate accepts the POI type. The fold starts with this villager and combines it with each competitor in list order: the accumulated villager is kept only if its XP is strictly greater than the next one's; otherwise the next one wins and the accumulated one loses. So on equal XP the later villager wins. Each loser has its `job_site` memory erased.

### 2.4 `YieldJobSite(speed)` (core, priority 8)

Requires: `potential_job_site` present, `job_site` absent, `nearest_living_entities` present, `walk_target` and `look_target` registered. Steps (read, `YieldJobSite`):
1. Do nothing if the villager is a baby or its profession is not `none`.
2. Read the POI type at the potential site position from the POI manager. If there is none, the behaviour ends with no effect.
3. From `nearest_living_entities` take the first (list order) entity that is a villager, alive, not this villager, and for which `nearbyWantsJobsite(type, other, pos)` holds: (a) the other has no `potential_job_site`; and (b) its profession's held-job-site predicate accepts the POI type; and (c) either it has no `job_site` and `canReachPos` holds for it, or its `job_site` position equals this position. `canReachPos` asks the other villager's navigation for a path to the position with the type's `validRange` as accuracy and requires the path to exist and `canReach()`.
4. If found (the winner): this villager erases `potential_job_site`, `walk_target` and `look_target`; and if the winner has no `job_site`, the winner gets walk and look targets on the position (speed of the behaviour, closeness 1) and its `potential_job_site` is set to the position; the POI debug synchroniser is told.
The net effect: of two villagers that hold the same job-site claim, an unemployed one yields to another villager whose profession already matches the site and that wants it.

### 2.5 `GoToPotentialJobSite(speed)` (core, priority 7)

Requires `potential_job_site` present; maximum run time **1200** ticks. Start condition: the active non-core activity is IDLE, WORK or PLAY. While running (it continues while the memory is present) each tick sets the walk and look target to the site (closeness 1, the validity range of a job site). On stop (timeout or success) the memory is erased and, when the POI manager still has a record of a type satisfying the acquirable test at that position, the villager's ticket on it is released (so a villager that gives up on a potential site frees it).

### 2.6 `AssignProfessionFromJobSite` and `ResetProfession` (details beyond 19 section 22.7)

`AssignProfessionFromJobSite`: while `potential_job_site` is present and the villager is within 2 blocks (`closerToCenterThan(pos, 2.0)`) of it: erase `potential_job_site`, set `job_site` to the same global position, broadcast entity event 14; if the profession is `none`: iterate the villager-profession registry in registration order and pick the first whose held-job-site predicate accepts the POI type at that position; if found: `withProfession`, `setVillagerData`, `refreshBrain`. ### 2.7 `WorkAtPoi` and `WorkAtComposter`

`WorkAtPoi` (all professions; the farmer uses the subclass): requires `job_site` present and `look_target` registered.
- Start condition: at most once per 300 ticks per behaviour instance (`gameTime - lastCheck < 300` blocks it; `lastCheck` is set when the check passes the random gate below); `nextInt(2) == 0` must hold (a one-in-two gate evaluated after the 300-tick test; `lastCheck` is updated then); the job site must be in the villager's dimension and within **1.73** blocks (`closerToCenterThan(pos, 1.73)`).
- Start: `last_worked_at_poi` memory = game time; `look_target` = the job site block; `playWorkSound` (19 section 22.2); `useWorkstation`; then, if `shouldRestock` (19 section 22.4), `restock`.
- Continues while `job_site` is present, in the same dimension and within 1.73 blocks (no explicit timer other than the brain's default run limit).

`WorkAtComposter` (farmer) adds, in `useWorkstation`, when the block at the job site is a composter: `makeBread` first, then `compostItems`.
- `makeBread`: 1. if the inventory holds more than 36 bread, return. 2. `loaves = min(3, wheat / 3)` with integer division on the wheat count; if 0, return. 3. Remove `loaves * 3` wheat and add `loaves` bread to the inventory (3 wheat per bread, at most 3 bread per work cycle). 4. Bread that does not fit is dropped at the villager (`spawnAtLocation`, vertical offset 0.5).
- `compostItems`: the compostable list is exactly [wheat seeds, beetroot seeds] (wheat itself is not in it). 1. If the composter level is 8 the produce is extracted first (`extractProduce`, and the returned state is used from then on). 2. A budget of **20** items per cycle and a keep-level of **10** per seed type. 3. Scan the inventory slots from the last to the first while the budget is above 0. For a slot holding a listed seed: let `t` be the running total of that seed type including this slot (the totals accumulate over the slots already scanned); `n = min(min(t - 10, budget), slot count)`. So the villager keeps 10 of each seed type and composts only the excess. 4. If `n > 0`: budget -= n and `insertItem` is called `n` times (one item each); as soon as the state reaches level 7 the fill effect is played and the method returns. 5. When the scan ends otherwise, the fill effect is played too. The fill effect is level event 1500 at the composter with data 1 when the state changed since the start of `compostItems` (after the produce extraction), else 0.

### 2.8 `StrollToPoi`, `StrollToPoiList`, `SetClosestHomeAsWalkTarget`, `GoToClosestVillage`

- `StrollToPoi(memory, speed, closeEnough, maxDistance)`: if the stored POI is in the villager's dimension and the villager is not already within `maxDistance` of it (not `closerToCenterThan`), and the behaviour's cooldown has elapsed, set `walk_target` to the POI with the given speed and closeness and arm an **80-tick** cooldown (so a villager far from its job site or bell starts walking back at most once per 80 ticks).
- `StrollToPoiList(listMemory, speed, closeEnough, maxDistance, mainPoiMemory)`: requires the list memory; if the main POI is within `maxDistance` of the villager, pick a random entry of the list (`nextInt(size)`); if it is in the same dimension and the villager is not within `maxDistance` of it and a **100-tick** cooldown allows, set the walk target to it. Used with `secondary_job_site` (farmland) in the work activity.
- `SetClosestHomeAsWalkTarget(speed)` (rest activity; requires `walk_target` and `home` both absent). Constants read: batch size 5, rate 20, cache timeout 40, ok-distance-squared 4, scan radius 48. State per behaviour instance: `lastRun` (initially 0) and a map from POI position to an expiry time. Each evaluation:
  1. If `gameTime - lastRun < 20`, do nothing.
  2. Find the closest `home` POI within 48 blocks (any occupancy). If none exists, or its `distSqr` to the villager's block is at most 4, do nothing (`lastRun` is not changed by this exit).
  3. Otherwise set `lastRun = gameTime + nextInt(20)` (a jitter of 0 to 19 ticks, so the effective gap between runs that get this far is 20 to 39 ticks).
  4. Collect the `home` POIs within 48 blocks (any occupancy) through a position filter: a position that is already a key of the map is rejected; otherwise a per-run counter is incremented (starting from 0) and the position is rejected when the incremented value is 5 or more, so at most 4 positions per run are accepted (the test is `value < 5` after the increment); an accepted position is stored in the map with expiry `lastRun + 40` (the jittered `lastRun` of step 3, not the plain game time).
  5. One path is requested to the collected set (`findPathToPois`). If the path exists and `canReach()`: when the POI manager has a type at the path's target, `walk_target` is set to the target with the given speed and closeness **1** (a literal 1, not the home's valid range) and the debug synchroniser is told.
  6. If there is no usable path and the counter is below 5 (fewer than 5 positions were examined), the map entries whose expiry is below the current `lastRun` are purged (purging only happens on this failure branch).
- `GoToClosestVillage(speed, closeEnough)` (rest activity when there is no `home`): does nothing if the villager's block is a village (`isVillage`). Otherwise let `d0 = sectionsToVillage(own section)`; make up to **5** attempts: sample a land position with `LandRandomPos.getPos(villager, 15, 7, scoring)` where the scoring prefers positions with a smaller section distance (the lambda returns the section distance of the candidate); for each sampled position compute `d = sectionsToVillage(its section)`: if `d < d0` accept it and stop; if `d == d0` remember it as a fallback (the last such); at the end set `walk_target` to the accepted or fallback position with the speed and closeness. So a lost villager repeatedly moves towards sections closer to POIs.

### 2.9 Bed behaviours: `WakeUp`, `JumpOnBed`

- `WakeUp` (core): every tick, if REST is not the active activity and the entity is sleeping, `stopSleeping` (which stores `last_woken`, 19 section 22.8). It is separate from the 40-tick restart delay of `SleepInBed`.
- `JumpOnBed(speed)` (baby play and idle lists): requires `nearest_bed` present and `walk_target` absent. Constants read: walking budget 100, jump count 3 to 6, cooldown between jumps 5. Start condition: the mob is a baby AND (it is on or directly over a jumpable bed (`onOrOverBed`: the block at its position or the one below is in block tag `villager_babies_can_jump_on_bed`, data: `#beds`) OR a nearest bed exists). On start: target = the nearest bed; `remainingTimeToReachBed` = 100; `remainingJumps = 3 + nextInt(4)` (3 to 6 jumps); `remainingCooldownUntilNextJump` = 0 (no random draw for the cooldown); `walk_target` = the bed with the given speed and closeness 0. Each tick: (1) if the mob is not on or over a jumpable bed, decrement the walking budget and end the tick; (2) else if the cooldown is above 0, decrement it and end the tick (the cooldown therefore only runs down while on or over a bed); (3) else, if the mob's own block is jumpable (`onBedSurface`), make it jump (`JumpControl.jump`), decrement the remaining jumps and set the cooldown to the constant **5** (not redrawn). The behaviour keeps running while the mob is a baby, the target bed is still jumpable, and neither of these holds: tired of walking (not on or over a bed and the budget is 0 or below) or tired of jumping (on or over a bed and the remaining jumps are 0 or below); it has no time limit of its own. On stop the target, budget, jumps and cooldown are reset to 0.

### 2.10 `LocateHidingPlace(radius, speed, closeEnough)` (raid HIDE and RAID activities)

Memories: reads `home`; writes `hiding_place`, `walk_target`; erases `path`, `look_target`, `breed_target`, `interaction_target`. Requires `walk_target` absent. Per evaluation, the candidate position is the first present of three optional sources (read, `LocateHidingPlace`):
1. The `home` POI found by `PoiManager.find` (occupancy ANY, type `home`, any position) within `radius + 1` of the villager's block (the first match in iteration order, not necessarily the closest), kept only if the position is within `radius` of the villager (`closerToCenterThan(villager position, radius)`).
2. Otherwise a random `home` POI from `PoiManager.getRandom` (occupancy ANY, no position filter, `radius` around the villager's block, the villager's own random source).
3. Otherwise the position already stored in the `hiding_place` memory, reused with no distance check.
If none of the three yields a position nothing happens. Otherwise: the four memories above are erased; `hiding_place` is set to the position in the villager's dimension; and, if the villager is not within `closeEnough` of the position (`closerToCenterThan(villager position, closeEnough)` false), `walk_target` is set to it with the speed and closeness `closeEnough`.

### 2.11 `ReactToBell`, `RingBell`, `SocializeAtBell`

- `ReactToBell` (core, priority 0): runs when `heard_bell_time` is present (the memory is set to the game time by the bell block entity, `BellBlockEntity.updateEntities`: see 2.11a). If **no** raid is found at the villager's position (`getRaidAt` is null), the villager's active activity becomes HIDE (when possible). With a raid present, nothing changes (the raid activities are driven by `SetRaidStatus`).
- `RingBell` (pre-raid activity, priority 0): runs only when `meeting_point` is present. Ringing the bell is what the village then reacts to.
- `SocializeAtBell` (meet activity): requires `meeting_point`, `walk_target`, `look_target`, `interaction_target`, `nearest_visible_living_entities`. The start lambda performs exactly three writes on the acting villager, in this order: `interaction_target` = the other villager; `look_target` = an entity tracker on it (eye flag true); `walk_target` = an entity tracker on it (eye flag false) with speed **0.3** and closeness **1**. ### 2.11a The bell block entity side (`BellBlockEntity`, closes Open question 4)

Constants read: search radius 48, hear radius 32, highlight-raiders radius 48, glow duration 60, minimum ticks between searches 60, resonation delay 5, resonation maximum 40. When the bell is rung (and again while it is being hit): the entity list is refreshed only when the game time is more than 60 ticks past the last refresh or no list exists: it holds every living entity inside the box of the bell block inflated by **48** (box gathering radius, not a distance test). On the server, for each such entity that is alive and not removed and whose position is within **32** blocks (`closerToCenterThan(entity position, 32)`) of the bell centre, the entity's `heard_bell_time` memory is set to the current game time (any living entity with a brain, not only villagers; the villager reaction is 2.11). Separate from that: a raider test for the resonance start (`areRaidersNearby`: alive, not removed, within 32 blocks and in entity-type tag `raiders`) and the raider highlight (`isRaiderWithinRange`: the same three conditions but within **48** blocks) which gives the glow effect (`glow`, 60 ticks) and the particles. Constant `DURATION` = 50. Timing per tick of the bell block entity (client and server run the same logic; only the resonance end action differs): (1) a ring (block event 1, or `onHit`) sets `shaking` = true, `ticks` = 0, `resonationTicks` = 0 (on the event also refreshing the entity list as above); a hit while already shaking only resets `ticks` to 0. (2) Each tick while `shaking`, `ticks` increases by 1; when `ticks` reaches 50 or more, `shaking` = false and `ticks` = 0. (3) When `ticks >= 5` and `resonationTicks == 0` and a raider is nearby (`areRaidersNearby`, above), `resonating` = true and the sound `bell_resonate` (BLOCKS, volume 1, pitch 1) plays. (4) While `resonating`: if `resonationTicks < 40` it increases by 1; otherwise the end action runs once on the cached entity list and `resonating` = false (`resonationTicks` stays at 40, so resonance cannot restart until the next ring resets it). The end action on the server is the raider glow (every raider within 48 blocks gets the Glowing effect for 60 ticks, amplifier default); on the client it is the bell particles. Worked timing: if resonance starts on tick `s`, `resonationTicks` goes from 0 to 1 within that same tick (step 4 runs after step 3), reaches 40 on tick `s+39`, and on tick `s+40` (already 40) the end action runs. So resonance starts 5 ticks after the ring at the earliest and the end action runs 40 ticks after it starts (not 41). The tag data read: `villagers_can_sleep_on_bed` = `#beds`; `villager_babies_can_jump_on_bed` = `#beds`; `mob_interactable_doors` = `#wooden_doors` plus the eight copper door blocks (plain, exposed, weathered, oxidized and the four waxed ones); `candidate_for_iron_golem_gift` = villager plus `#accepts_iron_golem_gift`; `accepts_iron_golem_gift` = copper golem (Open question 5 is closed by this).

### 2.15 `InteractWithDoor` (core), `PlayTagWithOtherKids`, `InteractWith`

- `InteractWithDoor` (every tick): works on the villager's current path (`path` memory). The countdown resets on node equality (not on a node change). The behaviour also does nothing when the path has not started or is done. ### 2.17 Farmer behaviours and movement helpers read in this round

**`SetWalkTargetFromBlockMemory(memory, speed, closeEnough, tooFar, giveUpAfter)`** (a one-shot behaviour; argument order read from the factory and its lambdas). Registered memory `cant_reach_walk_target_since`; requires `walk_target` absent and the global-position memory present. Per evaluation, with `p` the remembered position and `d` the Manhattan distance (`distManhattan`, |dx|+|dy|+|dz| of block coordinates) from the villager's block to `p`:
1. If `p` is in another dimension, or `cant_reach_walk_target_since` exists and `now - since > giveUpAfter`: the villager releases the POI of that memory (`releasePoi`), the memory is erased, `cant_reach_walk_target_since` is set to `now`, and the behaviour reports success (no walk target).
2. Else if `d > tooFar`: up to 1000 attempts to draw a random position (`DefaultRandomPos.getPosTowards` with horizontal range 15, vertical range 7, towards the bottom centre of `p`, angle 1.5707963705062866 rad = pi/2 as a float widened to double) until one is found whose Manhattan distance to the villager is at most `tooFar`; the first such position becomes the walk target (speed, `closeEnough`). If all 1000 attempts fail, step 1's release-erase-mark is applied instead.
3. Else if `d > closeEnough`: the walk target is the block `p` itself (speed, `closeEnough`).
4. Else nothing happens (the villager is already there).
Instances in the villager brain (positional values are `closeEnough`, `tooFar`, `giveUpAfter`; all at speed `s`, except the pre-raid one at 1.5 s): `job_site` (9, 100, 1200); `home` (1, 150, 1200); `meeting_point` in the meet activity (6, 100, 200); `meeting_point` in pre-raid (2, 150, 200). This is the meaning of the unlabelled numbers of 19 section 22.3 for these entries.

**`SetHiddenState(stayHiddenSeconds, closeEnough)`** (HIDE activity, `(15, 3)`; requires `hiding_place` and `heard_bell_time`). `maxTicks = stayHiddenSeconds * 20` = 300 and an internal counter starts at 0. Per tick: (a) if `heard_bell_time + 300 <= now` (the bell was heard at least 300 ticks ago) or the counter is above `maxTicks` (it must exceed 300, so the erase fires at the first evaluation with the counter at 301, i.e. after 301 near-ticks; the behaviour keeps hiding while the counter is 300 or less): erase `heard_bell_time` and `hiding_place`, run `updateActivityFromSchedule` (the villager returns to its scheduled activity), reset the counter to 0, return success; (b) else, when the villager is within `closeEnough` (3) blocks of the hiding place (`closerThan` on the block position), increment the counter. So a villager counts only the ticks it spends near its hiding place: the counter must exceed 300 before the hiding ends, and in any case at most 300 ticks after the bell was last heard.

**`MoveToSkySeeingSpot(speed)`** (raid activity, weight 5, speed 1.1 s per 19 section 22.3; gated by raid active and not victorious): runs when `walk_target` is absent. If the villager's block already sees the sky (`canSeeSky`) it does nothing. Otherwise up to 10 attempts: offset the villager's block by (`nextInt(20) - 10`, `nextInt(6) - 3`, `nextInt(20) - 10)` (draw order x, y, z), and accept the first position that `hasNoBlocksAbove`: the position sees the sky and the motion-blocking height-map block y at that column is at most the villager's current y (compared as double). The accepted position's bottom centre becomes the walk target with closeness 0. No position found: no target this evaluation. Success is reported either way once the sky check failed.

**`HarvestFarmland`** (work activity of farmers; requires `look_target` and `walk_target` absent and `secondary_job_site` present; the constants `HARVEST_DURATION` 200 ticks, speed 0.5).
- Start condition: the game rule `mob_griefing` is true and the profession is farmer. The behaviour then lists the valid cells: every block in the 3 x 3 x 3 cube centred on the villager's block position (offsets -1..1 on x, then y, then z, the positions computed from the villager's exact coordinates plus the integer offset and floored), where a cell is valid when it holds a fully grown crop (`CropBlock.isMaxAge`), or it is air and the block below is farmland. One valid cell is chosen uniformly (`nextInt(size)` on the level random, 1 draw); no valid cell means no start.
- Start (only if `now > nextOkStartTime`, initially 0, and a cell is chosen): `look_target` and `walk_target` are set to the cell (speed 0.5, closeness 1). Stop: both memories erased, `timeWorkedSoFar` = 0, `nextOkStartTime` = now + 40. Continues while `timeWorkedSoFar < 200`.
- Each tick: when a cell is set and the villager is not within 1.0 block of the cell centre, nothing else happens (the counter does not advance either, the early return skips it). Otherwise, when `now > nextOkStartTime`: (1) a fully grown crop at the cell is broken with drops (`destroyBlock(pos, true, villager)`); (2) if the cell is now air with farmland below and the villager holds farm seeds (`hasFarmSeeds`), the first inventory slot, in slot order, whose stack is in item tag `villager_plantable_seeds` and is a block item has its block's default state placed (`setBlockAndUpdate`), a block-place game event is emitted, the crop-planted sound is played at the cell (block category, volume 1, pitch 1, no source entity) and one item is removed from the stack (an emptied stack is replaced by the empty stack); only the first plantable slot is used per tick; (3) if the block at the cell is a crop that is not fully grown (this includes a crop just planted), the cell is removed from the valid list, a new cell is chosen from the remaining list (1 `nextInt` draw), and when one exists `nextOkStartTime` = now + 20 and walk and look targets are set to it (speed 0.5, closeness 1). Finally `timeWorkedSoFar` increases by 1 (only on ticks that did not return early at the distance test).

**`UseBonemeal`** (work activity of farmers; requires `look_target` and `walk_target` absent; `BONEMEALING_DURATION` 80).
- Start condition: `tickCount % 10 == 0` (the villager's own age counter) and (`lastBonemealingSession == 0` or `lastBonemealingSession + 160 <= tickCount`) and the villager's inventory holds at least one bone meal; then a target is chosen by the scan below, and the behaviour starts only when one exists.
- Target scan (`pickNextTarget`): visit the 3 x 3 x 3 cube of block offsets -1..1 around the villager's block, in x, y, z nesting order. Each cell that is a crop that is not fully grown (`CropBlock`, not `isMaxAge`) increments a counter `c` (starting at 0) and then replaces the current choice when `nextInt(c) == 0` (a reservoir draw: the first such cell is chosen with certainty, the k-th replaces it with probability 1/k, one draw per qualifying cell, drawn from the level random). The result is uniform over qualifying cells.
- Start: look and walk target set to the chosen cell (speed 0.5, closeness 1); the main hand holds a bone meal item; `nextWorkCycleTime` = now; `timeWorkedSoFar` = 0. Continues while `timeWorkedSoFar < 80` and a target exists. Stop: main hand emptied, `lastBonemealingSession` = `tickCount`.
- Each tick: when `now >= nextWorkCycleTime` and the villager is within 1.0 block of the cell: the first bone meal stack in slot order is used (`BoneMealItem.growCrop`, which consumes one bone meal as a player's use would: growth rule in 29b section 1); if it grew, level event 1505 with data 15 is sent at the cell, a new target is chosen by the scan (the old one may be picked again if it is still not fully grown), the look and walk targets are set to it, and `nextWorkCycleTime` = now + 40. Then `timeWorkedSoFar` increases by 1 (on every tick that passed the time-and-distance test, whether or not growth happened; ticks that returned early do not count). Note: when the start condition holds but no bone meal remains by the time of the tick, the tick only counts time.

### 2.18 Sensor timing shared by all sensors (closes former Open question 29)

Every sensor has a scan interval: the default constructor sets 20 ticks, another constructor sets an explicit number. `randomlyDelayStart` sets the countdown to `nextInt(interval)` when the brain is created. Per tick the countdown is decremented first; when it is at most 0 it is reset to `interval` and the sensor first refreshes its targeting-condition ranges (the follow range of the entity) and then runs its scan. So a sensor scans on its first tick with probability 1/interval and thereafter every `interval` ticks exactly. `hurt_by` and `visible_villager_babies` therefore scan every 20 ticks; `secondary_pois` (explicit constructor) every 40 and `nearest_bed` every 20 (4.1, 4.5).

## 3. Villager internals

### 3.1 Schedule (closes 19 Open question 27, first part)

The schedule is not interpolated. The two timeline tracks (`gameplay/villager_activity`, `gameplay/baby_villager_activity`) have no easing and string values, so the active activity at day tick `t` is the value of the last keyframe at or before `t` (wrapping at 24000). ### 3.2 Restock persistence (closes the "stored number of restocks" part)

### 3.3 `TradeWithVillager` (villager to villager sharing)

Requires `interaction_target` and `nearest_visible_living_entities`. Start: the interaction target is a valid villager target. On start both villagers face and walk toward each other (speed 0.5) and the villager works out the set of items it is willing to trade: the profession's requested items (for farmers: wheat, wheat seeds, beetroot seeds, bone meal, 19 section 22.2) that the other villager's profession does not itself request. Each tick: when the target is farther than squared distance 5 the tick does nothing more (the walking comes from the start and the gaze lock below); otherwise it calls `lockGazeAndWalkToEachOther` (speed 0.5, closeness 2) and then the steps below, which do not exclude each other (no early return: each of up to three throws can happen on one tick, in this order): it first calls `gossip(level, other, time)` (19 section 22.5) and then (a) when this villager has excess food (24 or more food points, 19 section 22.6) AND (this villager is a farmer OR the partner wants more food), throws half a stack of food items (items with the villager food component); (b) when this villager is a farmer and holds more wheat than half of wheat's default max stack size (more than 32 for a default stack of 64: `countItem(wheat) > maxStack / 2`), throws half a stack of wheat; (c) if the willing-to-trade set is not empty and the inventory has any item of it, throws half a stack of those items. `throwHalfStack(predicate)` scans the inventory slots in order for the first non-empty slot whose stack matches the predicate, then: if the stack count is above `maxStackSize / 2` (integer division), the split is `count / 2`; otherwise, if the count is above 24, the split is `count - 24` (24 is a keep-level); otherwise the slot is skipped and the scan continues with the next slot. The first split stack found is thrown toward the partner (`BehaviorUtils.throwItem`, from the villager's position). Closes Open question 22. On stop the interaction target is erased.

### 3.4 `ShowTradesToPlayer(minWait, maxWait)` and `LookAndFollowTradingPlayerSink`

- `ShowTradesToPlayer`: requires `interaction_target` = a living player (alive villager, not baby, squared distance at most 17). On the start `lookTime` is 40 and each tick the look time decreases towards 0 (the behaviour continues while the look time is above 0 and the start conditions hold). The displayed item has drop chance 0 and, when cleared, the main hand is emptied and its drop chance restored to 0.085.
- `LookAndFollowTradingPlayerSink(speed)`: while the villager has a trading player (a player with the merchant screen open), the villager is alive, not in water, not hurt recently and the player is within 4 blocks (squared distance 16), every tick `walk_target` and `look_target` are set to the player (speed as given); the run time is unbounded (the timeout is the maximum int). While it runs, ground navigation is allowed to path to targets below the surface (and reset on stop).

State machine (`TransportItemState`): TRAVELLING (initial), QUEUING, INTERACTING. Each tick: first validate the target (`updateInvalidTarget`): if there is no valid target (see below) the current one is dropped and a new one is searched (`getTransportTarget`); if none is found, the golem enters a **140-tick cooldown** (memory `transport_items_cooldown_ticks` = 140; both position memories are erased) and the behaviour stops; if one is found the travel callback runs and its position is added to the visited set. Then by state: QUEUING: if no other mob is using the target, resume TRAVELLING; TRAVELLING: when within **3.0** blocks of the target's centre (box test with the mob's hit box and the block's collision shape bounds inflated 0.5) check whether another mob is interacting with it (`shouldQueueForTarget`: for a chest the test is that a player or other entity has it open) and queue, else when within the interaction range (1.0 when the path is finished, else 0.5 expressed as the box inflation) start the interaction; else keep walking to it (walk target at the golem speed). INTERACTING: look at the target; the golem stays; the interaction continues only while the mob is within **2.0** blocks of the target (constant `CLOSE_ENOUGH_TO_CONTINUE_INTERACTING_WITH_TARGET` = 2.0, the distance within which the golem stays in the INTERACTING state); the interaction state is applied on the first tick; after **60 ticks** since reaching the target (`ticksSinceReachingTarget >= 60`) the container interaction completes (the interaction callbacks for the four interaction states run) and the golem travels on.

**Target search** (`getTransportTarget`): the search box is the golem's block inflated by the horizontal (32, or 1 when the golem is a passenger of another entity: `getHorizontalSearchDistance` returns 1 for a passenger) and vertical (8, or 1 for a passenger) distances; for every loaded chunk in that range, every chest block entity (class check `ChestBlockEntity`) inside the box is a candidate; candidates are tried in the order of increasing squared distance from the golem to the block centre (`distToCenterSqr`, scanning with a running minimum); a candidate is valid when: its block state satisfies the wanted predicate for the current mode (when the golem's main hand is empty the wanted blocks are those of the **source** predicate, otherwise the **destination** predicate), it was not visited in this search cycle (the visited set stores global positions of the block and of its double-chest partner, `getConnectedTargets`), the container is not locked, and (for the chosen one) there is a usable path or a line of sight to some face.

**Validity of the current target** (each tick): the target block still exists with the same block entity; its state is still wanted; it is not blocked (`ChestBlock.isChestBlockedAt`: a solid block above or a sitting cat); while TRAVELLING the golem must still have a path (or can create one) that ends within interaction range; a target with no usable path is moved from the visited set to the unreachable set. Both sets have expiry **6000 ticks**; the visited set may hold at most **10** entries and the unreachable set **50** before the 140-tick cooldown is entered.

**Pick-up and put-down**: the interaction mode is decided on reaching the container: a golem with an empty hand and a **non-empty** container does PICKUP_ITEM; empty hand and empty container PICKUP_NO_ITEM; a golem holding an item and a container that is non-empty and contains a stack of the same item (`isSameItem`) does PLACE_ITEM; otherwise PLACE_NO_ITEM (as `matchesGettingItemsRequirement` and `matchesLeavingItemsRequirement` read). PICKUP: take from the first non-empty slot `min(16, stack count)` items (`removeItem(slot, min(16, count))`), put them in the main hand, set the guaranteed drop of the hand, mark the container changed, and clear both position memories. PLACE: merge the held stack into the container: for each slot in order, an empty slot receives the stack (hand emptied), a slot with the same item and components below its max stack size takes up to the free space; leftover stays in the hand; when the hand becomes empty the memories are cleared and targeting stops. A failed attempt (no item or no space) also ends the targeting and the golem moves to another container.

Visual and sound states (`CopperGolemState`): the interaction states map to GETTING_ITEM (sound `copper_golem.item_get`), GETTING_NO_ITEM (`item_no_get`), DROPPING_ITEM (`item_drop`), DROPPING_NO_ITEM (`item_no_drop`). When the interaction begins the chest is opened (`startOpen`) and the opened-chest position is stored; at interaction tick 9 the interaction sound plays; at tick 60 the chest is closed (`stopOpen`) if the golem has it open, and the opened-chest position is cleared; travelling resets the state to IDLE.

## 9. Wandering trader and trader llama (closes 19 Open question 29)

- **UseItem conditions**: the invisibility potion (sound `wandering_trader.disappeared`) is drunk when it is **dark outside** (`isDarkOutside`) and the trader is **not** invisible; the milk bucket (sound `wandering_trader.reappeared`) is used when it is **bright outside** and the trader **is** invisible. (Item use mechanics are those of the goal in 18.)
- **WanderToPosition(stopDistance 2.0, speed 0.35)**: the trader keeps a `wanderTarget` block set by the spawner (19 section 23). `canUse`: the target exists and the trader is farther than `stopDistance` from its centre. `tick` (while the target exists): when the navigation is finished: if the trader is farther than **10** blocks from the target (`closerToCenterThan(target, 10)` false) a point is computed as the trader's position plus the normalised direction to the target scaled by 10 and navigation is started towards that point at the goal speed; otherwise navigation goes to the target block directly. `stop`: clear the wander target and stop navigation.
- **Despawn**: the trader discards itself when its `despawnDelay` (counting down while above 0 and not trading) reaches 0 (19 section 23).
- **Trader llama** (`TraderLlama`): `despawnDelay` starts at **47999** (saved as `DespawnDelay`). Goals: the llama goals plus p1 Panic(2.0); targets: defend the wandering trader (below), NearestAttackable(Zombie, excluding zombified piglin), NearestAttackable(abstract illager). It cannot be ridden while leashed to a wandering trader (`doPlayerRide` is skipped in that case). Each server tick `maybeDespawn` (read): 1. Return unless the llama may despawn: not tamed, not leashed to something other than a wandering trader, not carrying exactly one player passenger, age not locked, not persistence-required. 2. A single assignment: when leashed to a wandering trader, `despawnDelay` = the trader's `getDespawnDelay()` minus 1; otherwise `despawnDelay` = its own `despawnDelay` minus 1. There is no second decrement. 3. If `despawnDelay` is 0 or below, remove the leash and discard the llama. A llama leashed to a trader therefore takes the trader's remaining delay minus 1 on every tick and vanishes as soon as that value is 0 or below (when the trader's delay is 1 or less), and an unleashed one after at most 47999 ticks.
- **`TraderLlamaDefendWanderingTraderGoal`** (target goal, flag TARGET, no sight requirement): `canUse` requires the llama to be leashed to a `WanderingTrader`; it takes the trader's `getLastHurtByMob` and `getLastHurtByMobTimestamp`, and is true only when the timestamp differs from the one the goal stored and the attacker passes `canAttack` with the default targeting conditions. `start` sets the llama's target to that attacker, stores the trader's current timestamp and runs the base target-goal start.
- **Trader llama breeding** produces a trader llama made persistent (`makeNewLlama`, reason BREEDING); a trader llama finalised with reason EVENT gets the usual age group.

## 10. Trade-side engines (closes 19 Open question 28 where possible)

### 10.1 Exploration maps (`ExplorationMapFunction`, `MapItem`)

This is the item function (a loot-style function type `exploration_map`) that the cartographer trades call through `given_item_modifier`. Fields and defaults: `destination` (a structure tag, required), `decoration` (default: the woodland mansion decoration type), `zoom` (byte, default 2), `search_radius` (int, default 50; the shipped cartographer trades use 100), `skip_existing_chunks` (boolean, default true). The shipped cartographer trades chain it with a filter that discards the trade when the result has no `map_id` component (so a failed search removes the offer from the trade set draw).

Run (inputs: the result stack and the context origin = the villager's position):
1. Do nothing when the stack is empty or the origin is absent.
2. Let `pos` be the origin block. If `skip_existing_chunks` is true, first "claim" the structure at `pos`: if a valid structure start of the destination set exists at `pos` and `canBeReferenced`, add a structure reference there (so that the nearest-structure search with the skip flag does not return the structure the villager stands in).
3. Ask the level for the nearest structure of the destination set within `search_radius` (`ServerLevel.findNearestMapStructure(destinationSet, pos, radius, skipKnown)`, which forwards to the chunk generator). No result: return the unchanged stack.
4. Create a new filled map at the found position: `MapItem.applyNewSavedData(stack, level, x, z, zoom, trackingPosition = true, unlimitedTracking = true)`: a fresh `MapItemSavedData` is created (`createFresh`, read) centred by this rule: `size = 128 << zoom`; `ix = floor((x + 64.0) / size)`; `centreX = ix * size + size / 2 - 64` (integer division); the same for z with `iz`. Worked example: zoom 2 (size 512), x = 1000: ix = floor(1064 / 512) = 2, centreX = 1024 + 256 - 64 = 1216; x = -10: ix = floor(54 / 512) = 0, centreX = 0 + 256 - 64 = 192. Zoom 0 (size 128), x = 100: ix = floor(164 / 128) = 1, centreX = 128 + 64 - 64 = 128, a free map id is allocated (`getFreeMapId`, stored in the level) and set as the stack's `map_id` component.
5. Render the biome preview into the map (`renderBiomePreviewMap`): the 128 x 128 map is filled by sampling the biome at the block coordinates with a sample step of the map scale; water biomes of tag `water_on_map_outlines` are drawn as water colour with a depth pattern; land is drawn with the `COLOR_ORANGE` family and brightness chosen from a smooth function (`sin`-based stripes of period 7) with the constants 7, 8, 16384, 64, 127 read; the pixel colour tables (map colours and brightness) are item-rendering data (Open question 16).
6. Add a target decoration: a map decoration entry of the configured decoration type at the found position with rotation 180 degrees, named with the text "+" (the entry key is `+`), added to the stack's `map_decorations` component.

**Search algorithm** (`ChunkGenerator.findNearestMapStructure`): returns nothing if feature generation is disabled by the debug flag or the world option `generate_structures` is false. Otherwise the structure holders of the destination set are grouped by their placement; for each placement (a concentric-ring placement such as strongholds: the nearest generated position among the stored ring positions, checked against the radius by block distance in units of 8-block chunks scaled by 32; a random-spread placement: scan outward by increasing ring, using `spacing` and the `getPotentialStructureChunk` of the placement, and checking `getStructureGeneratingAt`); the nearest result by squared distance wins, with ties settled by iteration order. The ring-by-ring scan and the structure-start checks belong with structure generation (the structure document of the structure round, when it exists, section 36); only their existence is stated here (Open question 17).

## 11. Worked examples

1. **Section distance.** A villager sleeps in a bed whose head block is at (35, 70, 3). The bed's section is (2, 4, 0); the home POI there has `freeTickets` 0 of 1, so it is occupied and that section is a village centre (level 0). The sections within one step in each axis (x 1 to 3, y 3 to 5, z -1 to 1) get level 1, those two steps away get level 2. A player at (80, 70, 3) is in section (5, 4, 0): `sectionsToVillage` = 3, so `isVillage` and `isCloseToVillage(pos, 2)` are both false and a patrol may spawn there. A player at (3, 70, 3) is in section (0, 4, 0): level 2, so `isVillage` is false, `isCloseToVillage(pos, 2)` is true (patrols are suppressed, cats count it as village), and a Bad Omen effect does not trigger a raid. A player at (20, 70, 3) is in section (1, 4, 0): level 1: `isVillage` is true.
2. **Siege.** It is night, game time of day 18000, a player stands in a village; the 1-in-10 roll succeeds. Setup attempt 1: `nextFloat` = 0.25, so the float angle is 0.25 * 2pi = 1.5707964 (widened to double 1.5707963705062866). Sine index: `(long)(1.5707963705062866 * 10430.378350470453)` = 16384, entry 16384 is 1.0, so `sin(a) * 32` = 32.0 and `spawnZ = pz + 32`. Cosine index: `(long)(1.5707963705062866 * 10430.378350470453 + 16384.0)` = 32768 (the product is about 16384.0005), whose entry is about +1.2e-16, so `cos(a) * 32` is about 3.9e-15 and `floor` gives 0: `spawnX = px`. Then 10 random points within +-8 of that centre are tried for a village block with valid monster spawn rules. On success, 20 zombies spawn one every 3 ticks (2 ticks of countdown plus the spawning tick), so the siege takes 60 ticks.
3. **Cat spawn.** Counter at 0; offsets draws give x = +17, z = -21 from the player; the point passes `isSpawnPositionOk`; it is 1 section from a village centre so `isCloseToVillage(pos, 2)` is true; 6 home POIs within 48 blocks are occupied (above 4) and 3 cats are in the box: one cat spawns and the counter becomes 1200; the next attempt is 1200 ticks later.
4. **POI claim retry.** A villager's first scan finds a lectern 30 blocks away but no path: its retry object is created at time T with delay `min(0 + nextInt(40) + 40, 400)` = 55 (say). The next scan of that lectern is allowed at T + 55; if it fails again the delay becomes at most 55 + 79 = 134, and so on to the cap of 400; if the lectern is not tried for 400 ticks the entry is forgotten.
5. **Raid phase switch.** A raid at the villager's position has `groupsSpawned = 2`, no raiders alive and `raidCooldownTicks = 120`: `isBetweenWaves` is true so `SetRaidStatus` (1 in 20 ticks) puts the villager in PRE_RAID (rings the bell in 5% of ticks near it); when the next wave spawns the cooldown is 0 and raiders live, so the villager switches to RAID (hide, 19 section 22.3).
6. **Golem transport.** A copper golem with an empty hand and a copper chest 20 blocks away holding 40 cobblestone: it travels, opens the chest at tick 1 of the interaction, takes `min(16, 40) = 16` cobblestone at the end of the 60-tick interaction window, then searches the destination set (chests and trapped chests within 32 x 8): the nearest one with a stack of cobblestone or an empty slot receives them; the chest is closed at tick 60 and the golem walks to the next target; if no matching target exists it waits 140 ticks.

7. **Bonemeal target scan.** A farmer has 3 immature crops in its cube, found in scan order A, B, C. Draws `nextInt(1)` (always 0, so A is chosen), `nextInt(2)` (0 replaces A with B, 1 keeps), `nextInt(3)` (0 replaces with C). Each cell ends with probability 1/3.
8. **Walk target helper.** A villager is 160 blocks (Manhattan) from its home with `cant_reach_walk_target_since` absent: `d` 160 > `tooFar` 150, so up to 1000 random positions towards the bed (range 15 x 7) are tried until one is within 150; the villager then walks to it with closeness 1. After 1200 ticks of being unable to reach it the home POI claim is released and the home memory erased.
9. **Hiding.** A villager hears a bell at tick T (`heard_bell_time` = T) and its near-place counter has reached 200 when the game time is T+300: the bell is now old, so both memories are erased and the schedule resumes, without waiting for the counter to reach 300. If instead the bell is re-heard every 100 ticks, only the counter limit applies: the counter must exceed 300, so the memories are erased at the evaluation with 301 ticks spent near the hiding place.
10. **Player-created golem.** A player-made golem next to a villager that hates a player (reputation -150): `DefendVillageTarget` runs its combat-conditions search; the player is rejected by `canAttack`, so the golem stays passive towards that player and still attacks hostile monsters. A village-summoned golem in the same place attacks the player.
