# Contract: `shim` additions (`shim` -> `formats`, `content`, `core`, `client`, `extract`)

**Status**: frozen at plan time; amends `specs/001-cobolcraft-complete/contracts/shim-abi.md`. Materialized in
Foundational as `contract/include/ccshim.h` and `contract/copy/CCSHIM.cpy` additions. Every addition is glue for
a reason Principle I names; none contains game or protocol logic. Everything COBOL can call cleanly stays a direct
call (OpenSSL digests, `CBL_*`, libm through glue only where a C double crosses the ABI).

| Function / constant | Reason it is glue | Behaviour | Consumer |
|---|---|---|---|
| `cc_f64_add`, `cc_f64_sub`, `cc_f64_mul`, `cc_f64_div`, `cc_f64_floor`, `cc_f64_sqrt`, `cc_f64_from_text`, and the libm functions documents 10, 11, 15 and 18 call for (named by the Foundational docs round) | COBOL cannot receive a C double return value; `COMPUTE` on doubles costs 1.17 microseconds per statement (research R5). | All operands and the result by reference, returns nothing; `add` and `mul` are `fma(a,1,b)` and `fma(a,b,-0.0)` (a `+0.0` addend turns a product of `-0` into `+0`) so the results are exactly IEEE binary64 (spike `spike_f64`: `0.1 + 0.2` gives `343333333333D33F`). `from_text` is `strtod` of a decimal text, the only way to get the nearest double for a constant. | `core` (noise, density, climate, features, entity physics), `client` where bit-exactness matters |
| `cc_vk_texture_ex(tex_id, w, h, rgba, mip_levels)` | Vulkan image creation, blit chain and sampler objects. | Uploads the RGBA texture with `mip_levels` levels generated by box filter from the base level, and sets the sampler to the filter of 12 §2.4 (`mip_levels` 1 keeps today's behaviour). `cc_vk_texture` stays and calls it with 1. | `client` (atlas, US5) |
| `cc_vk_texture_update(tex_id, x, y, w, h, rgba)` | Staging buffer and copy command. | Replaces one rectangle of the base level and regenerates the mip levels it touches; the animation frame update (14, FR-010). | `client` |
| `cc_vk_texture_update_begin(void)`, `cc_vk_texture_update_end(void)` | Command buffer batching. | The `cc_vk_texture_update` calls between them are recorded into one command buffer, submitted once at the end and not waited for (each alone waits for the queue to be idle: tens of animated sprites cost most of a frame; the queue runs the copy before the next frame, and the staging buffers are freed once the frames after it have completed); pixels read back as for single updates. | `client` (SUBMIT-FRAME) |
| `cc_vk_clear_depth(void)` | Render pass control. | Clears the depth attachment between the world pass and the hand pass (the first-person hand of 12 §6 is drawn over the world). | `client` (US20) |
| `cc_open_path(opener, path)` | `posix_spawn` and argument vector. | Starts `opener` (production: `/usr/bin/open`) with `path` as its only argument and returns 0 at once, or `CC-NOTFOUND` when the opener cannot be started. Does not wait. | `client` (US4) |
| `cc_png_write(path, w, h, rgba)`, `cc_vk_screenshot(path)`, `cc_vk_screenshot_result()`, constant `CC-FAILED` (8) | The swapchain image copy, the PNG chunks, CRC32 and deflate (zlib) cannot be done from COBOL. | `cc_png_write` writes the 8-bit RGBA image as a PNG (filter 0, one IDAT, zlib level 6) and returns 0 or `CC-FAILED`. `cc_vk_screenshot` asks for the frame the next `cc_vk_frame_end` presents to be saved at `path` (the pixels as presented, in RGBA order, alpha forced to 255) and returns 0, or `CC-AGAIN` while an earlier request waits. `cc_vk_screenshot_result` is `CC-AGAIN` while the request waits for its frame, then 0 (written) or `CC-FAILED`; 0 when there never was a request. | `client` (`screenshot.cob`: key.screenshot / F2, `--screenshot-after-frames`) |
| Key codes `CC-KEY-F` (70), `CC-KEY-F3` (292), `CC-KEY-F5` (294) and the others 13 §5.1 and §7.3 name | constants of GLFW | Added to `CCSHIM.cpy`; the existing key-down path delivers them. | `client` |

**Contract tests.** `shim/tests/contract_shim_provider.c` extends the existing provider test: `cc_f64_*` against
IEEE vectors computed independently (Python `struct`), texture calls against the real MoltenVK device (readback of
mip level 1 and of an updated rectangle), `cc_png_write` and `cc_vk_screenshot_result` outcomes (content: `test_cc_png.c`, `test_cc_vk_screenshot.c` on the real device), `cc_open_path` with an opener that exists (`/usr/bin/true`, the Q-2 sanctioned double) and with a
missing opener (`CC-NOTFOUND`). Consumer side: `contract_shim_consumer.cob` in `core`, `client`, `formats` assert
the COBOL `CALL` shapes of `CCSHIM.cpy` (as today).

**Frame loop (lane perfpresent; no ABI change).** A macOS `sample` of a running game showed the main thread blocked in
`cc_vk_frame_end` for two thirds of its time (waiting for a drawable inside `vkQueueSubmit`, and for the frame's fence). The
frame loop of `cc_vk.c` therefore runs two frames in flight: `cc_vk_frame_end` submits and presents without waiting, and
`cc_vk_frame_begin` waits for the fence of the slot it reuses (the frame before the previous one), so the CPU records frame n + 1
while the GPU draws frame n. Resources replaced meanwhile (meshes, textures) are destroyed once the frame that could use them has
completed. The swapchain has at least three images. `cc_vk_draw` sends the push constants in one command and rebinds the pipeline and
the texture only when they change. Environment variables read by `cc_vk_init` (all optional; unset gives the defaults):

| Variable | Effect |
|---|---|
| `CC_GPU_STATS=1` | Prints one line to standard error once a second (and at shutdown): frames per second; CPU milliseconds per frame in `app` (everything outside the shim between two frames: simulation, meshing, building the render list), `fence` (waiting for the GPU), `acquire`, `record`, `submit` (MoltenVK encodes the Metal commands here, on the calling thread, and waits for a drawable here), `present`, `idle` (waits for an idle queue: one-shot uploads, screenshots), `upload`; the GPU milliseconds of the render pass (timestamp queries, when the queue supports them); per frame the draw calls, vertices, texture updates, full texture uploads, mesh uploads and idle waits; the image count, present mode (`VkPresentModeKHR`: 0 immediate, 1 mailbox, 2 FIFO) and frames in flight. |
| `CC_VK_PRESENT=mailbox` or `immediate` | Asks for that present mode; used when the surface offers it, else FIFO (the default). MoltenVK offers FIFO and IMMEDIATE (display sync off: frames are shown without waiting for the display, with tearing). |
| `CC_VK_INFLIGHT=1` | One frame in flight (default 2). |

MoltenVK's own `MVK_CONFIG_*` environment variables apply as usual (for example `MVK_CONFIG_SYNCHRONOUS_QUEUE_SUBMITS=0` moves the
Metal encoding of `vkQueueSubmit` off the calling thread).

`cc_stat_phase(phase)` (diagnostics, ABI addition; constants `CC_PHASE_*` / `CC-PHASE-*`): with `CC_GPU_STATS=1` the program tells the shim which part of its frame it enters (input, pump, coretick, clienttick, controls, net, world, ui, rlist, submit); the statistics line is followed by `cc_gpu: phases ms/frame (entries/frame): ...` (the phases entered in the window; `coretick` entries per frame are the core ticks run). `cc_vk_frame_begin` ends the running phase. Without `CC_GPU_STATS` the call returns at once.
