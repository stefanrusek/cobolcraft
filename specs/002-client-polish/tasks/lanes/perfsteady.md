## Lane 002-lane-perfsteady (T59000-T59299)

Operator report on try16 (db901a9a, release build): "really bad" performance, the operator gave up testing (earlier: village very laggy, 44 fps in a stronghold, 0 fps for the first minute after a load or a respawn (lane bugstall), shaking over height differences (lane bugstep)). Base: origin/002-client-polish db901a9a, plus bugstall's fix dba39f8c (a fluid tick at a chunk edge, cherry-picked for the measurement: without it a standard world does not finish loading in the bench; the same patch, so the merge is clean). Measured, not guessed: user CPU (C clock()), release build (-O2, FPFAST=1), the load average is printed with every result.

- [x] T59000 [US3-client] (lane perfsteady) Measurement program `tests/convergence/bench_steady_client.cob` (not an acc test, built by hand: scratchpad/perfsteady/mkbench.sh against the static libraries, mkbench2.sh against the dylibs so that `sample` names the programs; prints `BS ...` lines). A survival player (Resistance infinite: stays alive) at night with the clock stopped, natural spawning on, at render distance 12 (the simulation distance of this core is the view distance: play.cob), teleported to BS_X BS_Y BS_Z (BS_AUTOY 1: the nearest cavity below y 50, a stronghold corridor or a cave), 14 mobs of a village's company summoned round the player (iron golem, cat, cow, zombie x3, pig, skeleton, sheep, creeper, chicken, spider, villager, wolf), then BS_FRAMES frames standing and BS_WALK_FRAMES frames walking (W held), each frame the whole of CL-STEP with the core tick (a game at 40 frames a second: a tick every other frame). Reports mean, p50, p99, max, mean of the frames with a tick and of those without, the 10 longest frames, the core tick alone (CORE-TICK timed one by one), and the client phases run again on the same state.
